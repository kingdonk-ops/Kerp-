Edge spec §6 amendments define the projects/memberships policy as 'project in app.allowed_project_ids or app.is_system_admin'. app.allowed_project_ids (T-0010) holds only the projects of portfolio personas and also widens project-scoped reads, and requests bind no project yet (TD-122). Taken literally, a PER-02/PER-09/PER-15 member could not read their own project's row (GET /projects, /me/projects, membership admin all 404 on PostgreSQL). T-0014 reading: a row is visible when its described project is app.current_project_id, in app.allowed_project_ids, in the new setting app.member_project_ids (every project of the caller's memberships, any persona, bound server-side in the same unit of work), or app.is_system_admin; memberships also to their own user (TD-152). app.member_project_ids widens only the membership-based tables, never project-scoped records, so a client-portal user of A still cannot list or fetch B. Confirm or amend the spec text.

- 2026-11-14 (implementer, T-0014 review): Also for the decision: the membership-table write policies are visibility-based. Updates and deletes need the exact scope (tenant, `project_id IS NULL`) plus row visibility, and inserts only the exact scope; neither checks persona or capability. So at DB level any session that sees A's rows (any member of A through `app.member_project_ids`, including a PER-15 client-portal user or a PER-16 viewer) could update A's project row or A's memberships with raw SQL. The role checks (PER-09 / `system_admin` for membership admin, capability `admin` for project edits) live only in the routers and services. Confirm this is acceptable or decide on a DB-level guard (e.g. write policies keyed to an admin-persona setting).

- 2026-11-16: Decision (product owner, 2026-11-16, TODO triage): app.member_project_ids reading confirmed (spec text to be amended), and add a DB-level write guard: membership-table and project-row writes require an admin-persona/system_admin session setting, not only row visibility. Needs a follow-up task.
