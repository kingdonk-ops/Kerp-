The shared field-type registry (quality-and-inspection.md §One field-type registry) has a single-value `measurement` only. Many ITR checks record several readings per spot or area and accept on statistics of the set, e.g. coating dry film thickness (several gauge readings per spot, individual minimum plus mean), surface profile, holiday test points, bolt tension samples. Today these need a repeating group (one row per reading), which is heavy on a tablet and awkward to write acceptance rules against.

Proposal (planner to confirm):
- New field type `measurement_set`: `{unit, values: number[]}` stored as a JSONB array (no fixed ceiling such as ERPNext's reading_1..reading_10). Template settings: unit, `min_count` / `max_count`, optional instrument reference (calibration gate applies as for `measurement`).
- Acceptance stays CEL. Standard CEL has list macros (`values.all(v, v >= 200)`, `size(values)`) but no aggregates: register `mean`, `min`, `max`, `stddev` (and maybe `percent_below(values, limit)`) as custom functions in the rule engine, available identically to the server and the live form check.
- Optional authoring shortcut: template min/max/target value generates the CEL rule (no separate evaluation modes).
- PDF/ITR rendering: list the readings and the computed statistics.

Questions: exact function set and rounding; does an offline device evaluate the same functions (one shared implementation)? Example values in seeds and tests must be synthetic.
