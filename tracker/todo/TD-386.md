Seen on `dev` c809cc8 and PR #130 (SQLite backend run):
`tests/test_auth_password_reset.py::test_two_concurrent_confirms_one_wins_one_gets_410` got
`{..: 200, ..: 500}` with `sqlite3.IntegrityError: UNIQUE constraint failed: audit_ledger.tenant_id,
audit_ledger.scope_id, audit_ledger.chain_key, audit_ledger.seq`. Timing-dependent.

Root cause: `backend/app/core/audit/service.py` `_lock_chain` was a no-op off PostgreSQL ("SQLite
serialises writers itself"). SQLite only serialises writers from their first write: the test DB is
a file database (`sqlite:///<tmp>/kerp.db`, rollback journal, not WAL) on SQLAlchemy's default
pool, one connection per session, and pysqlite opens the transaction lazily (deferred `BEGIN`
right before the first DML). So the tail `SELECT` in `append` ran under no lock; both confirm
requests (winner: `password_reset_confirmed`, loser: the refusal from `_invalid`) read the same
tail of `auth:password-reset`, the second INSERT waited on the first writer's lock, then hit
the unique `seq` after it committed, and the loser's unit of work returned 500 instead of 410.

- 2026-11-20: Fixed: on SQLite `_lock_chain` runs `UPDATE audit_ledger SET seq = seq WHERE 0`,
  which opens the transaction and takes the database write lock (held until commit) before
  the tail read; same pattern as `_SQLITE_WRITE_LOCK` in `app/core/auth/service.py`.
  `BEGIN IMMEDIATE` was rejected (cannot be issued inside the caller's already-begun unit of
  work), a process-level per-chain lock too (not released at commit, not cross-process). The
  PostgreSQL advisory-lock path is unchanged. Deterministic regression test
  `tests/test_audit_ledger.py::test_two_writers_racing_on_one_chain_serialise_instead_of_colliding`
  (barrier between tail read and insert) failed with the IntegrityError before the fix.
