POST /api/v1/devices/{device_id}/wipe-confirmed takes no bearer because every session of a revoked device is dead (diff 4.3: the client wipes, then confirms). The device_id is a client-generated random UUID that only the device, its user and admins see, the call only works on revoked devices, sets wipe_confirmed_at once and is audited; it cannot un-revoke or change anything else. Risk: a leaked id lets someone mark a wipe that did not happen, so admins may trust a false confirmation. Mitigations if needed: a per-device wipe secret issued at enrolment (stored hashed, presented with the confirmation) or device-bound attestation (TD-204).
