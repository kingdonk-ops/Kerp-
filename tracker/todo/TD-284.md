oe_identity_device uses the standard project-scoped policy: as a tenant-level row every session of the tenant can read and write any device row at the database level, and the API (device_api.py) decides who may list or revoke which device (owner, system_admin, PER-09 of a project the owner belongs to; same as auth_user today). A dedicated policy (own rows + system_admin + rows of users sharing a project where the caller holds PER-09) would add defence in depth; it needs a membership-aware owner check in SQL (like the membership policy) and an ORM-scope mirror.
