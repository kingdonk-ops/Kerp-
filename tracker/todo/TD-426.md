The user's 2026-11-21 paste ('T-0076', id taken by PER-16 Project Viewer; now T-0277-T-0280) asks for POST /api/v1/admin/users/{id}/impersonate: a short-lived impersonation JWT (sub = target, impersonator claim = admin, exp <= impersonation_max_minutes, default 30, no refresh token), RLS bound exactly from the target's memberships with is_system_admin = false, a central guardrail (403 IMPERSONATION_ACTION_FORBIDDEN for A/S authority, signing, client co-sign, inspection submit/approve, hold release, override decisions, password/PIN/device/admin-grant mutations), dual-identity audit (acted_as_user_id + impersonated_by_user_id) and a persistent banner with Exit.

Re-assessed after ADR 0016 (user, 2026-11-21: system_admin has global read/admin visibility in the tenant). Visibility is no longer the conflict: the target's view is a subset of what the admin already sees, and the impersonation session binds is_system_admin = false, so it narrows the admin's RLS, never widens it. What remains is (1) mutations written under another person's name (BaseRecordMixin created_by/updated_by = target; only the ledger carries the admin), which an admin no longer needs because ADR 0016 lets them create and edit under their own identity on every project, and (2) A/S authority of the target (hold release, sign-off, co-sign), which the guardrail blocks. Draft: docs/decisions/0015-system-admin-impersonation.md (Proposed).

Options: (a) impersonation as specified: mutations allowed and attributed to the target with impersonated_by in the ledger, guardrails as listed; (b) impersonation only of users in projects where the admin is a member (moot since ADR 0016: an admin sees every project, so (b) narrows nothing); (c) read-only 'view as': the admin sees the target's exact UI, personas, capabilities and site scope, every mutating request is refused with 403 IMPERSONATION_ACTION_FORBIDDEN (fail-closed, enforced centrally), only the impersonation.started/ended/denied events are written; (d) the target must consent with a one-time code sent to them (combinable with (a) or (c); breaks the 'user is locked out / unreachable' support case).

Planner default: (c) read-only view-as. Least privilege: it serves the support need ('what does this user see and why can they not press X'), adds no visibility beyond ADR 0016, never writes a record under someone else's name, and keeps A/S authority unreachable by construction rather than by an enumerated list. The guardrail, the contract test and the dual-identity ledger (hash v3, impersonated_by_user_id) are still built, so moving to (a) later is a relaxation of the central guard's allow-list, not a redesign. Not a safe default to build without the user, because the user's text explicitly asks for mutations (AC 'Mutations are attributed to the target'): T-0277, T-0278, T-0279 and T-0280 are blocked until decided. Also asked: (1) may a target holding create_projects be impersonated (planner: yes, but project creation is blocked while impersonating); (2) may PER-15 Client Representatives (external) be impersonated (planner: yes, read-only); (3) should the target be told (planner: an e-mail notice to the target after impersonation ends, through core mail, §4.6).
