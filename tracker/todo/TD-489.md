Non-blocking suggestions from the PR #152 (T-0053) review, not covered by TD-458..TD-461:

- `frontend/src/pages/LoginPage.tsx:201`: no test pins the post-login race fix (a known invite outcome wins over `from`); reverting it to `<Navigate to={from}>` keeps all InvitePage tests green. Add a deterministic test (`/auth/me` resolving before the post-login navigation).
- Wrong-user after a password sign-in or the SSO return (`invite_error=INVITE_WRONG_USER`): the pending invite is already cleared (`LoginPage.tsx:214`, `SsoReturnPage` effect), so "Sign out" leads to a plain sign-in, not back into the invite sign-in as `src/invite/README.md` says. Either narrow the README wording or keep the invite on those two wrong-user paths (with a test).
- `frontend/src/admin/PendingInvites.tsx`: the resend mutation's `data` (`invite_token`, `invite_link`) stays in the mutation cache until its gcTime, so the README's "never cached" is not exact. Call `act.reset()` on Close (or keep the token out of the mutation result, as UsersPage does) and assert the mutation cache holds no token.
- After a wrong-user refusal, leaving by browser navigation leaves the invite in `sessionStorage` until the next plain `/login`. Acceptable (tab-scoped); document it in `src/invite/README.md`.
