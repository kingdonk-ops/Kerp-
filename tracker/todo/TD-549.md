Product intake 2026-11-21, items 16–19. The notifications module (T-0019) has kinds, priority, pins and a channel interface, but no shared model of notification rules or of delivery outcomes across channels. Each module hard-codes its events and recipients (for example the RFI table in quality-and-inspection.md §inspection_requests §9.2).

Planner defaults to spec (user to confirm):
1. **Rule model** (item 16): trigger (domain event) + recipients by role/persona or relation (requester, named witness, custodian) + delay (send now or N minutes after the event, cancelled if a condition stops holding) + channel set + template key + CEL conditions. Code-declared defaults per module, project copies editable like rule sets (ADR 0004); the existing post-submit `notify_users` action (T-0256) becomes one consumer.
2. **Delivery log per notification** (item 17): one row per notification × recipient × channel with `pending | sent | failed | skipped` and a reason (`no_consent`, `no_address`, `suppressed`, `condition_excluded`, `template_missing`, `too_late`, provider error class). Extends TD-238 (persisted per-channel log after commit). An **Outbox card** on the ITR and RFI detail screens lists the notifications sent about that record and their delivery state (no message bodies, no addresses for external readers).
3. **Issued vs amended** (item 18): separate triggers for first issue and for a revised/re-issued record (report re-issue, TD-514 void-and-reissue, RFI PDF revision), so a recipient never gets "here is your report" twice; the amended template names the revision.
4. **Never late** (item 19): a time-bound notification (reminder) that cannot be sent before its deadline is logged `failed` / `too_late` and not sent. Applied to the RFI reminder already (§inspection_requests §9, planner default); the rule model should make it general.

Related: TD-238, T-0335, T-0228, T-0226 (delivery ledger for e-mail).

- 2026-11-22: (planner, PR #177 review round 2) To confirm: a recipient's own opt-out of a channel (if notification preferences ever apply to RFI call-outs) is logged as `skipped` for that attempt and therefore counts toward a party's `notice_delivery = failed`, which is blamed on `contractor` by default (quality-and-inspection.md §inspection_requests §9; T-0350). Planner default: yes, it counts as skipped. Alternative: RFI call-out e-mail ignores opt-out as a transactional message.
