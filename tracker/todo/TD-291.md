From the PR #89 round-1 review (T-0043). service.refuse_revoked_device checks the revoked status of whatever device id X-KERP-Device-Id names, for any user of the tenant, before credentials are checked on login: an unauthenticated 'is this device id revoked' oracle. wipe-confirmed similarly answers 404 for an unknown id and 409 for an active one. Low risk: device ids are client-generated random UUIDs seen only by the device, its user and admins. Related: TD-286 (unauthenticated wipe-confirmed). Mitigations if needed: check credentials first and answer uniformly, or a per-device secret.

- 2026-11-15: (planner) Product owner, 2026-11-15: risk accepted for development only; must be fixed before pilot go-live. Covered by T-0080 (per-device wipe secret, credentials-first login device check, uniform answers; phase 0, order 10; diff §4.3). Stays open until T-0080 merges, then resolve with its PR.

- 2026-11-15: (implementer) T-0080: password login authenticates before refuse_revoked_device; magic-link redeem peeks the link (unspent), then checks the device, then spends it; wrong credentials or an invalid link get the same 401 for unknown, active and revoked device ids. wipe-confirmed no longer answers 404/409 by device state (one uniform 404). Remaining authenticated-only oracle: TD-299. PR: #94.
