User addendum 2026-11-21 (pasted as a 'T-0014 addendum', now T-0243) asks for a stored status VARCHAR(24) invited|active|deactivated on the user table ('oe_identity_user' in the paste; the real core table is auth_user). auth_user already has is_active (T-0008/T-0014: deactivation blocks sign-in and every token path at once, last System admin protected, TD-274).

Planner default (not blocking): no second source of truth. status is computed: deactivated when is_active is false; invited when first_login_at IS NULL; else active. New nullable columns first_login_at, last_login_at, last_active_at on auth_user (core table: ADR, additive). Existing accounts at migration time: first_login_at backfilled to created_at for accounts that could already sign in (password_hash set or entra_oid linked), NULL otherwise (synthetic dev data only; no deployment yet).

Confirm with the user, or name a case where a stored status must differ from this derivation.
