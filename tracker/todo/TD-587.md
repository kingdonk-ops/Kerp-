Carried over from TD-549 when TD-549 was resolved by the user decision on opt-out (user, 2026-11-22). The rest of TD-549 is still unspecified, so it continues here. The notifications module (T-0019) has kinds, priority, pins and a channel interface, but no shared model of notification rules or of delivery outcomes across channels.

Planner defaults (product intake 2026-11-21, items 16–19; user to confirm), unchanged from TD-549 except for the opt-out rule:
1. **Rule model:** trigger (domain event) + recipients by role/persona or relation (requester, named witness, custodian) + delay (send now or N minutes after the event, cancelled if a condition stops holding) + channel set + template key + CEL conditions. Code-declared defaults per module, project copies editable like rule sets (ADR 0004); the existing post-submit `notify_users` action (T-0256) becomes one consumer.
2. **Delivery log per notification:** one row per notification × recipient × channel with `pending | sent | failed | skipped` and a reason (`no_consent`, `no_address`, `suppressed`, `condition_excluded`, `template_missing`, `too_late`, provider error class). Extends TD-238. An **Outbox card** on the ITR and RFI detail screens lists the notifications sent about that record and their delivery state (no message bodies, no addresses for external readers).
   - **Opt-out (user, 2026-11-22, TD-549):** `no_consent` (opt-out / unsubscribe) applies to **optional** notifications only. Transactional notices (RFI call-outs and inspection-request notices, invites, password resets, access-request decisions) ignore opt-out and are never logged `skipped` / `no_consent`. A missing address (`no_address`) or a bounce / suppression is still recorded per recipient.
   - The rule model must therefore mark each notification kind `transactional` or `optional` (code-declared, not project-editable).
3. **Issued vs amended:** separate triggers for first issue and for a revised/re-issued record (report re-issue, TD-514 void-and-reissue, RFI PDF revision); the amended template names the revision.
4. **Never late:** a time-bound notification that cannot be sent before its deadline is logged `failed` / `too_late` and not sent (already applied to the RFI reminder, quality-and-inspection.md §inspection_requests §9).
