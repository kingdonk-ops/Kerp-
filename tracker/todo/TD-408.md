User addendum 2026-11-21 (image derivative tiers) reconciled with the spec; planner defaults applied (not blocking), confirm with the user:

1. Keys: T-0016 stores content at {tenant}/{project}/{module}/{sha256} (TD-213 resolved), not <...>/original.<ext>. Derivatives go to derivatives/{tenant}/{project}/{module}/{sha256}/{tier}_{max_px}_{quality}.jpg, shared like the content object; a settings change affects new derivatives only.
2. Status: the upload model has 'available' (no 'complete'). An image file stays 'verifying' until the scan passed AND both derivatives exist; an undecodable or over-large image (decompression-bomb pixel cap) is 'rejected' with image_decode_failed / image_too_large.
3. Metadata: the pasted columns (tablet_proxy_key, report_proxy_key, sizes) become rows of a derivative table (file id, tier, key, size, width, height, params) plus width_px/height_px on oe_uploads_file (the paste's oe_upload_attachment is oe_uploads_file).
4. Annotation frame: quality-and-inspection.md says coordinates are normalised 'against the original image'. Originals keep their EXIF Orientation tag while proxies are auto-oriented; the frame is defined as the original after applying EXIF orientation (= the proxy's frame), so the same JSON fits original, tablet proxy and report rendition.
5. Patch path: ADR 0005 per-field mutations name changed paths; an annotation edit is one path keyed by attachment id (answers.<question_key>.<attachment_id>.annotation), never a list index and never the attachment id or sha256 itself.
6. Derivatives strip EXIF (incl. GPS) and colour-convert to sRGB JPEG; the original keeps everything.
