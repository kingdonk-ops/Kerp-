Product owner, 2026-11-14 asked for re-send to 'issue a new invite link and code'. The spec and tasks have no invite code today (the project code of the lobby, diff §4.1, is a different thing: it leads to an access request, not a membership). Planner deferred the code: re-send of the link is specified now (diff §4.1 Invites, T-0052, T-0059, T-0053) and the code waits for this decision, because a short code is brute-forceable and adds a second redeem path to secure. If adopted, the safe shape is: random code of at least 8 characters from an unambiguous alphabet (no 0/O/1/I), stored only as a hash on the invite, single-use, short expiry (planner default 24 h, never longer than the invite), bound to the invited e-mail, entered on the /invite page together with that e-mail, redeem rate-limited per invite (invite revoked after 5 wrong attempts), per client and deployment-wide, one neutral answer for an unknown e-mail, wrong code or expired code (no account enumeration), rotated with the link on every re-send and revoked with the invite. Open points: (1) is the code shown to the inviter (then it must not set a first password, like the copied link) or only e-mailed (then it is a typeable setup_token)? (2) is it needed at all, given the e-mailed link plus re-send? Planner default until decided: link only, no code. Not blocking: T-0052, T-0053 and T-0059 proceed without a code.
