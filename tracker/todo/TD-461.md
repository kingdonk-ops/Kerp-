Diff §4.1: a brand-new invitee with a copied link runs the self-service reset and 'then accepts the invite after sign-in'. The SPA keeps the pending invite_token in the tab's sessionStorage only (T-0053 security rule), so it survives the reset only when the reset link is opened in the same tab; otherwise the user signs in without it and lands in the lobby. The screen tells the user to sign in or open the invitation link again. A seamless path would bind the invite reference to the reset token server-side (like the magic-link record of T-0052) and accept it on the first sign-in after the reset; backend + frontend change, product decision whether worth it.
