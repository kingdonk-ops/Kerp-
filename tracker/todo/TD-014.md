## Context
Diff §2.1 defines the unified `oe_inspections_inspection` record with `kind IN ('inspection','itp','rfi')` **and** a separate `inspection_requests` module whose workflow is `draft → requested → confirmed → witnessed | waived | no_show | failed` with automatic client delay attribution. The master spec (MOD-08 line 299, lifecycle line 656) uses "RFI" to mean **Request for Inspection / call-out**.

So the same concept ("request for inspection") appears to be modelled twice: as a `kind='rfi'` row in the unified table (T-0111) and as the `inspection_requests` module (T-0115).

## Question for human
What is the intended relationship?
- (a) `inspection_requests` is the call-out *workflow/state machine* and it drives/creates a `kind='rfi'` inspection record as its backing store; or
- (b) they are disjoint — `kind='rfi'` is something else (e.g. an RFI = Request for *Information*) and `inspection_requests` is the only call-out store; or
- (c) `kind='rfi'` should be dropped and all call-outs live only in `inspection_requests`.

Default assumed if no answer before T-0111/T-0115 build: (a) — `inspection_requests` owns the request workflow and, on `confirmed`, materialises/links a `kind='rfi'` inspection record. No `blocked_by` set; implementers should confirm.
