Residual of TD-142 after T-0038. A session bound at sign-in (X-KERP-Device-Id naming an enrolled device) carries the did claim from the start, and every rotation carries it, so the PIN gate and the re-enrolment counter rule do not depend on Redis for those. A session bound by its enrolment (first sign-in on a new device, or a sign-in without the header) has a first refresh token without did: until its first rotation the gate reads only kerp:auth:device:sid:<sid>. If an allkeys-* maxmemory policy evicts that key, /auth/refresh rotates after idle without the PIN, and a re-enrolment from that session counts as a new binding and clears the device's PIN failures (incl. a PIN_EXHAUSTED stop). Options: (a) re-issue a token pair with did in the enrolment response (needs the cookie/native transport on /devices/enrol); (b) require maxmemory-policy noeviction for the auth Redis in the startup check (cf. TD-124); (c) clients always send X-KERP-Device-Id at sign-in once enrolled (already the contract, does not cover the first sign-in on a device). Today: README tells operators to run noeviction.

- 2026-11-16: Decision (product owner, 2026-11-16, TODO triage): do both (a) re-issue a token pair carrying did in the enrolment response and (b) refuse to start unless the auth Redis uses maxmemory-policy noeviction.
