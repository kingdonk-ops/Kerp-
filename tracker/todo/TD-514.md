The master spec says a `LOCKED_FOR_TURNOVER` record is "verified and immutable. No modifications permitted" (KERP-MASTER-SPEC.md, inspection state machine), and quality-and-inspection.md defines `PENDING → INSPECTION_REQUESTED → INSPECTED_PASSED → LOCKED_FOR_TURNOVER`. Neither says what happens when a signed inspection (`INSPECTED_PASSED` or `LOCKED_FOR_TURNOVER`) is later found to be wrong: a wrong reading, anchor, instrument or date.

Proposal to decide (modelled on ERPNext cancel-and-amend; pattern only, no code copied):
- A signed record is never edited. It is **voided** (new status, reason required, kept for audit, number kept) and a **reissue** is created as a copy with a `supersedes_id` link and a revision suffix on the number (e.g. `…-0042-1`).
- The void and the reissue are sign-off ledger entries (T-0119, hash chain); the reissue is signed again and runs `run_checks` as usual, evaluated as of its `inspection_date` (ADR 0004 C–D).
- Hold points, RFIs and gates treat a voided record as absent until its reissue passes.
- The MDR / handover dossier includes only the latest revision; the void appears in the audit trail.

Questions:
1. Who may void (persona), and does it need a second approver (separation of duties, like ADR 0004 Amendment B)?
2. Is voiding `LOCKED_FOR_TURNOVER` allowed, or only before turnover? What happens to a dossier already compiled or PAdES-sealed?
3. Does a client co-signed record need the client to co-sign the void/reissue?
4. Does the reissue pin the original `template_revision_id` or the latest revision?

This changes a core state machine and the turnover dossier, so the answer likely needs an ADR in docs/decisions/.
