title: Password-change revocation can miss tokens when server clocks drift (iat compared with password_changed_at from another clock)

password_changed_at is stamped by the API process clock (utcnow) and tokens are rejected when issued before it; tokens minted by another process whose clock runs behind can carry an iat before the change yet be issued after it, or the reverse. Fix: compare against a database-clock timestamp or a per-user token generation counter rather than wall-clock iat; add a test with skewed clocks.

Source: docs/reviews/2026-11-21-codebase-audit.md (Smaller findings).

- 2026-11-21: T-0345 (implementer): left open, not small. A fix needs a per-user token generation (new column + claim, so a migration and every token path) or stamping both sides from the database clock (iat comes from the API process); neither is a safe drive-by in this PR. T-0345 only moves the refresh's lock_user before consume_refresh, which does not change the iat comparison.
