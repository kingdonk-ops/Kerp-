The pasted 'T-0178' (now epic E-01-02) asks for 'Restore as New Project' with a deterministic remap of project and entity UUIDs, and for a legal-hold check 'before deleting any project without a verified archive'.

1. The audit ledger hash covers tenant_id, project_id and created_by (diff §4 ledger design); remapped ids cannot be re-hashed into the original chains without forging them. Planner default (not blocking): restore-as-new verifies the archived chains, stores them as read-only evidence with the archive SHA-256, and starts new chains whose genesis entry references the archive id and hash; no ledger row is rewritten. Restore of a soft-deleted project (same ids) needs no ledger writes beyond the restore event. Needs an ADR (T-0240).
2. KERP has only soft delete for projects; there is no hard purge anywhere in the spec (retention rules: TD-175, later). Planner default: no purge in this epic; legal hold blocks soft delete and archive deletion.

Questions for the user: accept (1); is a hard purge of project data after a verified archive wanted, and under which retention rule?
