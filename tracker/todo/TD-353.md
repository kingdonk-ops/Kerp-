Raised in PR #121 review (T-0079). Migration `0026` (`backend/migrations/versions/0026_tenants_directory.py`, `_backfill`) lifts `FORCE ROW LEVEL SECURITY` on each tenant-scoped table so the owner can read the `tenant_id` values in use, then restores it. `ALTER TABLE ... [NO] FORCE ROW LEVEL SECURITY` takes `ACCESS EXCLUSIVE`, held until `0026` commits.

Scope: all 20 tables in `0026.TABLES` are locked `ACCESS EXCLUSIVE` (no reads, no writes) for the whole `UNION` scan of their `tenant_id` columns — a full scan of every table, at best index-only on `ix_<table>_tenant_id` — and until the revision commits. Accepted for phase 0 (one tenant per deployment, no populated production database), documented in ADR 0011 §3 and `docs/deploy/tenants.md`; not acceptable once a deployment holds real data.

Offline `--sql`: when raised, `migrations/env.py:run_migrations_offline` had no `transaction_per_migration`, so offline SQL ran `0026` and `0027` in one transaction and `0027`'s `VALIDATE` would have run under `0026`'s locks too. Fixed in the same PR: offline mode now sets `transaction_per_migration=True` like online mode (`tests/test_migrations.py::test_offline_sql_commits_each_revision_apart` asserts a `COMMIT;` between the two revisions). The online risk above remains.

Possible ways out (pick before any populated deployment, or before the next revision that needs the same RLS-bypassing read):
- A `SECURITY DEFINER` census function with a pinned `search_path` that reads the tenant ids in use without toggling `FORCE` (the way `0025`'s `kerp_live_team_link_grant_count()` does), so the read takes only `ACCESS SHARE`.
- A pre-deploy step that provisions the directory rows (`python -m app.core.tenancy.provision` / T-0023 first-run) so the in-migration backfill finds nothing to read for a known tenant set.
- A `SET LOCAL lock_timeout` guard in `0026` so the migration fails fast instead of queueing behind (and blocking) live traffic.
