User-supplied spec (2026-11-21, pasted task 'T-0073', now T-0221/T-0222) asks for a tenant-wide upload quarantine table and a global audit explorer for system_admin. Diff §4.1: System admins 'read no project-scoped records without a membership like any other user'.

Planner default applied (not blocking; revised in PR #137 review round 1): (a) quarantine monitor: full upload rows only for projects where the admin holds a membership, read under the normal RLS of `oe_uploads_file`; for every other project **counts only** per project, status and reason code, from a count-only `SECURITY DEFINER` function of the T-0219 pattern (pinned `search_path`, `EXECUTE` revoked from `PUBLIC`, numbers only, ADR; filters project, status and reason only, never file id, hash or filename). The orphan sweep is housekeeping and exempt. This is count-only, not row-level metadata: the uploads RLS policy is not widened and no bypass role is used. (b) Audit explorer reads under normal RLS: tenant-level chains in full, project chains only of projects where the admin holds a membership. A wider read needs a policy on a core table (audit_ledger) and therefore an ADR. (c) Project archive (E-01-02; documents-and-mdr §Access; revised in round 2): export (T-0233), download (T-0237) and restore from a registry `archive_id` in **either** mode, deleted (T-0239) or new (T-0240), need `system_admin` and a membership of the requesting admin on the project: live project, a live membership; deleted project, a membership held when it was deleted (the `revoked_memberships` payload of the project's `delete` entry in `project:<id>`, read by `admin.service.memberships_at_deletion`; earlier removals never count and are never revived). A non-member System admin gets 404. Restore from an uploaded `.zip` (`file_id`) needs `system_admin` only, because the caller already holds the bytes. A System admin may grant themselves PER-09 on a live project through the existing membership API (T-0014), audited in `project-members:<project>`; the archive endpoints never grant it implicitly. Restore as new (T-0240) makes the restoring admin PER-09 of the new project, audited. The registry list, storage-tier changes and deep-archive restores expose no content and need `system_admin` only. In every case the user may relax the default.

Question for the user: keep the defaults (membership required for rows, audit chains and archive contents; self-grant of PER-09 is the audited way in), or allow System admins a full cross-project read for these surfaces (with an ADR, a policy change and an audit entry per read)? Also: a System admin who was not a member of a deleted project (at deletion) cannot download or restore its registry archive at all today; the only path left to them is restoring from a copy of the zip they already hold (uploaded zip). Should such an admin be able to reach a deleted project's archive, e.g. with an audited break-glass grant?
