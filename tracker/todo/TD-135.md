Diff §4 says only 'magic-link + 6-digit PIN as a local session unlock only, with progressive lockout throttling'. T-0009 implemented: a magic link (15 min, single use, sha256 digest in Redis) starts a new session on the device and sets its PIN (scrypt hash in Redis keyed by sid); /auth/refresh refuses PIN-gated sessions, only /auth/pin/unlock (refresh token + PIN) rotates them, so the worker re-enters the PIN whenever the 15-minute access token lapses. PIN alone can never start or refresh a session. Lockout: PIN 4 immediate tries (no lock after failures 1-3, failure 4 arms 30 s), then 30 s doubling to 15 min, and the 10th wrong PIN revokes the session (the counter lives as long as the session's refresh token, not per day); password login 6 immediate tries then the same escalation, never permanent; magic-link requests 4 immediate per hour then 1 min doubling. Weak PINs (one digit repeated, straight runs) are refused. Confirm or change: (a) PIN on every token renewal vs only after idle/app-lock, (b) the numbers, (c) whether the PIN should instead be purely client-side (no server hash) with a server-side attempt counter only.

- 2026-11-13: Decision (user, 2026-11-13): 8a. Hybrid PIN: the device unlocks locally with the PIN (works offline, key in the device keystore); the server asks for the PIN only when a session is renewed after idle. Keep the lockout numbers and the server-side attempt counter. Rework T-0009 behaviour in a follow-up task.

- 2026-11-13: (planner) Applied: diff §4.2; T-0038, T-0143; note on T-0009. The 30-minute idle default is a planner choice exposed as a setting.

- 2026-11-13: (planner, PR #48 review) The 30-minute idle limit and the 10th-PIN behaviour (ends PIN unlock, no revoke, never wipes) were confirmed by the user (Q2a, Q3a, 2026-11-13) and are written as decisions in diff §4.2.
