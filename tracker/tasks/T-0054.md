## Goal
Entra ID SSO for staff as a second `AuthProvider`, identity only (product owner, 2026-11-14; diff §4.5; TD-043). Gates Pilot-0 (T-0146).

## Acceptance criteria
- [ ] `EntraOidcProvider` behind the existing `AuthProvider` seam (TD-003); enabled only when `KERP_ENTRA_TENANT_ID` and `KERP_ENTRA_CLIENT_ID` are set; the client secret or certificate comes from the secret store / environment, never the repo; a public auth-config response tells the client whether SSO is offered
- [ ] `GET /api/v1/auth/sso/entra/start` creates `state`, `nonce` and a PKCE S256 verifier, stores them in Redis (single-use, ≤ 10 min) with the optional `invite_token`, the enrolling `device_id` and (native flow) the app verifier's S256 hash, sets a random pre-auth cookie (`httpOnly; Secure; SameSite=Lax`, path `/api/v1/auth/sso`, same lifetime) whose hash is stored in the state entry, and redirects to the tenant-pinned authority `https://login.microsoftonline.com/<tenant>/v2.0` (never `common` / `organizations`); scopes `openid profile email` only
- [ ] `GET /api/v1/auth/sso/entra/callback` rejects unknown, reused or expired `state`, and rejects (consuming the state) when the pre-auth cookie is missing or does not match the stored hash; it clears the cookie either way (login-CSRF binding, diff §4.5); exchanges the code with the verifier; verifies the ID token signature against the tenant JWKS (cached; on an unknown `kid` refetched at most once per minute deployment-wide), `iss` = pinned issuer, `tid` = configured tenant, `aud` = client id, `exp`/`nbf`/`iat` with ≤ 2 min leeway, `nonce` = stored nonce; any failure refuses the sign-in, creates nothing and logs no token contents
- [ ] Members only: a token whose `acct` claim is not `0` (missing = not proven) or that carries an `idp` claim different from the pinned issuer is a guest and is refused with a translated "sign in with the method from your invitation"; guests are never linked and never become internal (diff §4.5)
- [ ] Account matching by **verified** e-mail: the first sign-in matches an existing **active** account by the `email` claim (case-insensitive) only when `xms_edov` is `true` or the domain is on `KERP_INTERNAL_EMAIL_DOMAINS`; there is no `preferred_username` fallback; a missing or unverified `email` → refused; on match it stores `entra_oid` / `entra_tid` (T-0049); later sign-ins match by `oid` only; an account linked to another `oid` → refused; no account → refused with a translated "No KERP account for this e-mail, ask your administrator" (no auto-create, diff §4.5); deactivated → refused
- [ ] No group-to-role mapping: group and app-role claims are ignored; a test with a token carrying group claims shows no persona, grant or team change. A successful sign-in recomputes `is_internal` (true) and nothing else about access (T-0049)
- [ ] Success issues the same KERP session as password sign-in: 15-min access token, refresh ending 12 h after sign-in, cookie transport for the web origin and native body transport only for allow-listed origins (T-0037, T-0043), `session_expires_at` in the response (T-0038); field clients enrol the device as after any sign-in. Accepting an `invite_token` carried in `state` is T-0052's criterion
- [ ] Native handoff (diff §4.5): for a native flow the callback never puts tokens in a redirect; it issues a single-use exchange code (random, stored hashed, ≤ 60 s, bound to user, `device_id` and the app verifier hash) and redirects to the verified App Link `https://<deployment>/app/sso-return`; `POST /api/v1/auth/sso/entra/exchange` (`code`, `verifier`, `device_id`) from an allow-listed native origin (T-0043) returns the native body transport; the deployment serves `/.well-known/assetlinks.json` from configuration (app id + signing-certificate fingerprint)
- [ ] Optional-claim prerequisite (diff §4.5): a refusal because `acct` is missing is logged with the distinct reason `acct_claim_missing`; with SSO enabled the server logs a start-up warning naming the required optional claims (`email`, `acct`, `xms_edov`); the health check reports a warning when an SSO sign-in was refused for `acct_claim_missing` in the last 24 h; deploy docs state that without the `acct` optional claim every SSO sign-in is refused
- [ ] SSO is promoted but not enforced (product owner, 2026-11-14; diff §4.5 *SSO promoted, password kept*): the public auth-config response reports SSO as the **preferred** method when enabled (e.g. `sso: {provider: "entra", preferred: true}`) and password as available; password login (`POST /auth/login`) keeps working for every active account with a password, internal or not; there is no SSO-only setting and no refusal of password login by e-mail domain or `is_internal` (test: an internal user, domain on `KERP_INTERNAL_EMAIL_DOMAINS` and linked `entra_oid`, still signs in with a password)
- [ ] Link, sign-in and every refusal reason are written to the audit ledger / security log (no token contents)
- [ ] Tests with a fake OIDC provider (local JWKS and signed tokens, no network): happy path, bad signature, wrong `iss` / `tid` / `aud`, expired, nonce mismatch, replayed `state`, PKCE mismatch, unknown e-mail, deactivated user, `oid` mismatch, JWKS key rotation and the unknown-`kid` refetch limit; guest token (`acct` = 1, `acct` missing, foreign `idp`) refused; unverified `email` (`xms_edov` false, domain not listed) refused; `preferred_username`-only token refused; callback with valid `state` but missing or foreign pre-auth cookie refused; exchange code redeemed twice, after 60 s, with a wrong verifier or another `device_id` refused
- [ ] `app/core/auth/README.md` documents the app registration (single-tenant, the web redirect URI, scopes, optional claims `email`, `acct`, `xms_edov`, no API permissions), the App Link / `assetlinks.json` set-up, the configuration variables and the matching rule; deploy docs list the secrets
- [ ] All quality gates green (see CLAUDE.md §Quality gates)
