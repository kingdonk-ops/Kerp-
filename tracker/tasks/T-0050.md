## Goal
The stateful access-request lifecycle of diff §4.1 (product owner, 2026-11-14): a requester files, follows, withdraws and re-files requests; the project's PER-09 holders approve or reject with an optional reason; the non-member requester learns the outcome in the lobby.

## Acceptance criteria
- [ ] `access_requests` table (`BaseRecordMixin`, RLS): requester user, project, optional message (≤ 1000 chars), status `pending | approved | rejected | withdrawn`, decided by/at, optional rejection reason (≤ 500 chars), granted persona(s) and site scope on approval; a partial unique index allows at most one `pending` row per (user, project); decided and withdrawn rows are kept as history
- [ ] `POST /api/v1/access-requests` (project id, optional message) creates a `pending` request; a second pending request for the same project → 409; a project the user already has effective access to → 409; unknown or deleted project → 404; a **first** request for a project must carry a valid lookup ticket from the code lookup (T-0040) for that user and project when the caller is external (not `is_internal`), or internal and the project is not lobby-visible, else 404 (a leaked project id alone is not enough); an internal user may name a lobby-visible project without a ticket; a new request on a project where the caller already has an earlier `rejected` or `withdrawn` request needs **no ticket** (the earlier row proves legitimate discovery; coordinator decision, PR #73 review round 2), so "Request again" works after the cooldown (diff §4.1)
- [ ] Re-request cooldown: after a `rejected` request, a new request for the same project before `rejected_at + KERP_ACCESS_REQUEST_COOLDOWN_HOURS` (deployment configuration, default 24, 0 disables; product owner 2026-11-14, default chosen by the planner) → 409 with `code: ACCESS_REQUEST_COOLDOWN` and `retry_after`; a `withdrawn` request has no cooldown
- [ ] `GET /api/v1/access-requests/mine` returns the caller's active requests for the lobby panel: every `pending` request plus the latest decided request per project from the last 30 days, each with project code and name (through the narrow lobby read path, not the `projects` policy), status, the rejection reason for `rejected`, and `request_again_at` (null when a new request is allowed now)
- [ ] `POST /api/v1/access-requests/{id}/withdraw` moves the caller's own `pending` request to `withdrawn` (someone else's → 404; not pending → 409)
- [ ] The project's PER-09 holders (and `system_admin`s) list pending requests for their projects, approve (choosing persona(s) and site scope; the PER-09 + hold-authority `sod_warning` / `confirm_sod` rule of T-0014 applies) or reject with an optional reason; only `pending → approved | rejected` is allowed (409 otherwise); others get 403/404; approval creates the direct membership in the same transaction
- [ ] PER-09 holders are notified in-app of a new request (T-0019). The requester gets no project-scoped notification (not a member); `/mine` is the authoritative outcome channel. Outcome e-mail: follow-up T-0056 (TD-084)
- [ ] Request, withdrawal, decision, decider, reason and resulting membership are written to the audit ledger
- [ ] RLS: requests are visible to the requester, the project's PER-09 holders and `system_admin` sessions only (edge §6 amendments); PostgreSQL test as `kerp_app` shows another user and a PER-09 of a different project see nothing
- [ ] Tests: an external user's first request without a ticket, with an expired one, or with another user's or project's ticket refused (404); an internal user's first request for a non-lobby-visible project without a ticket refused; re-request without a ticket after a rejection (once the cooldown has passed) succeeds; re-request without a ticket after a withdrawal succeeds; full lifecycle, one-pending rule, cooldown boundary (just before / at `retry_after`; 0 = disabled), withdraw then re-request immediately, approval creates the membership and the project appears in `/me/projects`
- [ ] Module `README.md` and docs updated
- [ ] All quality gates green (see CLAUDE.md §Quality gates)
