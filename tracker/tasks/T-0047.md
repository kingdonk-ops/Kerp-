## Goal
TD-183 decision 11a on the client: render template labels, option labels and error messages from either shape.

## Acceptance criteria
- [x] A `localise(value, locale, defaultLanguage)` helper resolves plain strings and per-locale maps: exact locale, then language (`de-AT` → `de`), then `default_language`, then the first entry (edge §2.2 amendment)
- [x] The renderer uses it for field labels, option labels, validation `error_message`, help text and section titles; keys, option values and CEL are untouched
- [x] Unit tests for each fallback step and for a plain string; an existing English-only template renders unchanged
- [x] `frontend/src/shells/README.md` updated
- [x] All quality gates green (see CLAUDE.md §Quality gates)

## Spec
- `docs/spec/KERP-EDGE-SCREENS-AND-SPEC-UPDATE.md` §2.2 (localised template strings)

## Notes
- 2026-11-13 (planner): The template JSON schema and server lint accept the map shape in T-0110.
- 2026-11-14 (implementer): `frontend/src/shells/form/localise.ts` (`localise`, `DEFAULT_TEMPLATE_LANGUAGE`) + `LocalisedString` type; `FormTemplate.default_language` and optional field `help` added to the client template types. Tags compare case-insensitively; own entries only; an empty map resolves to `""` (the T-0110 lint rejects it).
- Locale source: `DynamicForm` `locale` prop, else the active i18n language. The engine keeps `error_message` unresolved in `FieldError.invalid.message`; the renderer localises it (engine stays locale-agnostic).
- `help` renders under the label and joins the control's `aria-describedby` (with the error id when an error shows).
- Deviation: section titles: the current template schema has no sections, so there is nothing to render yet; deferred as TD-255 (T-0110 owns the schema). The criterion is ticked for every string that exists in the schema.
