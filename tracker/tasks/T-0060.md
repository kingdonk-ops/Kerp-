## Notes
- 2026-11-13 (planner): Absorbed T-0065 (both touch the jobs module and its tests) — user request to merge small hardening tasks.
- 2026-11-13 (implementer): Body limit is a pure ASGI middleware (`app/core/body_limit.py`), innermost in `create_app` so the 413 keeps the request id and security headers. It refuses a declared `Content-Length` above `KERP_MAX_BODY_BYTES` (default 1 MiB, min 1024) up front and counts chunked bodies as they are read (raises an `HTTPException` subclass so FastAPI's body parser does not turn it into a 400). Upload endpoints take JSON metadata only; file bytes go by presigned PUT, pinned by `test_the_body_limit_does_not_cap_presigned_uploads`.
- `spatial_bounds`: `MAX_TOTAL_POSITIONS = 10_000` across all rings, counted in a `mode="before"` validator so the cap also bounds validation cost.
- Non-object job results: chose "reject" over widening `JobRead.result` (no API change, `gen:api` output unchanged). `service.finish_job` raises `TypeError` for a non-dict result; `run_job` already fails the row with `Internal error (TypeError)`.
- Payload cap: `JobCreate.payload` <= 64 KiB as compact UTF-8 JSON (422). Enforced at the API only; internal `create_job` callers and result size: TD-240. Per-route body-limit overrides: TD-241.
- Worker RLS: the thread-based test in `tests/test_rls_bypass.py` is replaced by two tests that run jobs through `build_workers` + real SAQ/Redis + `run_job`, with the workers started under an ambient `use_tenancy(CTX_C)` (asyncio tasks inherit contextvars). Verified the positive test fails if `run_job` stops binding the job's scope. Both need PostgreSQL + Redis (CI's PostgreSQL step); run locally against a private PG 16 + PostGIS cluster and redis-server.
