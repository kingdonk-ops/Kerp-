## Goal
Close the two device-registry risks the product owner accepted for development only (2026-11-15) and that **must be fixed before pilot go-live**: anyone who knows a revoked `device_id` can mark its wipe as done (TD-286), and login and `wipe-confirmed` tell an unauthenticated caller whether a device id is unknown, active or revoked (TD-291). Diff §4.3 (Device hardening before the pilot).

## Acceptance criteria
- [ ] Enrolment (`POST /api/v1/devices/enrol`) issues a per-device **wipe secret** (random, >= 256 bits) once, returned only in the response of the enrolment that creates the device row, never again (re-enrolling or listing the device never returns it); stored only as a hash (no plaintext in the database, logs, audit payloads or Sentry); test reads the row and the logs
- [ ] Additive migration (nullable hash column). A device enrolled before this task has no secret, so its wipe cannot be confirmed by the device (it gets the uniform refusal below); acceptable because no device is in production before the pilot (planner default; stated in the README)
- [ ] `POST /api/v1/devices/{device_id}/wipe-confirmed` requires the wipe secret; a wrong or missing secret, an unknown device id and an active (not revoked) device all get the **same** answer (status code, body and comparable work, constant-time hash compare); only a revoked device with the right secret records `wipe_confirmed_at` (once) and is audited; tests for each case. The endpoint's OpenAPI `responses` drop the documented 404 and 409 and list only the one uniform refusal (plus success); `frontend/src/api` is regenerated and committed
- [ ] Sign-in (password login, magic-link redeem) checks the credentials **before** any device-revocation check: with wrong credentials the answer is the same for an unknown, an active and a revoked `X-KERP-Device-Id` (no device-status oracle to unauthenticated callers); tests for the three device states with wrong credentials. The SSO exchange (not built yet) gets the same rule in T-0054
- [ ] Magic-link redeem validates the link **without spending it**, then runs the device check; the link is spent only when the device check passes. A valid link with a revoked device answers `401 {code: DEVICE_REVOKED}` and leaves the link unspent (test: the same link then redeems from an active device); an invalid, expired or spent link gets the uniform refusal whatever the device state
- [ ] With valid credentials a revoked device is still refused with `401 {code: DEVICE_REVOKED}` so the client wipes (diff §4.3); `DEVICE_REVOKED` behaviour for authenticated or device-bound sessions (refresh, PIN unlock of a bound session, any authenticated request, enrol) is unchanged; the T-0043 tests keep passing unweakened
- [ ] Wipe confirmations and refused confirmations are written to the audit ledger (never the secret)
- [ ] The client contract for T-0143 (store the wipe secret in the keystore-backed store per account, present it with the wipe confirmation) is documented in `app/core/auth/README.md`
- [ ] TD-286 and TD-291 resolved with a pointer to this task's PR
- [ ] Module/README.md and docs updated (`app/core/auth/README.md`, identity README, `frontend/src/api` regenerated if the API schema changed)
- [ ] All quality gates green (see CLAUDE.md §Quality gates)
