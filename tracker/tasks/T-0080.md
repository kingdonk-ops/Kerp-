## Goal
Close the two device-registry risks the product owner accepted for development only (2026-11-15) and that **must be fixed before pilot go-live**: anyone who knows a revoked `device_id` can mark its wipe as done (TD-286), and login and `wipe-confirmed` tell an unauthenticated caller whether a device id is unknown, active or revoked (TD-291). Diff §4.3 (Device hardening before the pilot).

## Acceptance criteria
- [x] Enrolment (`POST /api/v1/devices/enrol`) issues a per-device **wipe secret** (random, >= 256 bits) once, returned only in the response of the enrolment that creates the device row, never again (re-enrolling or listing the device never returns it); stored only as a hash (no plaintext in the database, logs, audit payloads or Sentry); test reads the row and the logs
- [x] Additive migration (nullable hash column). A device enrolled before this task has no secret, so its wipe cannot be confirmed by the device (it gets the uniform refusal below); acceptable because no device is in production before the pilot (planner default; stated in the README)
- [x] `POST /api/v1/devices/{device_id}/wipe-confirmed` requires the wipe secret; a wrong or missing secret, an unknown device id and an active (not revoked) device all get the **same** answer (status code, body and comparable work, constant-time hash compare); only a revoked device with the right secret records `wipe_confirmed_at` (once) and is audited; tests for each case. The endpoint's OpenAPI `responses` drop the documented 404 and 409 and list only the one uniform refusal (plus success); `frontend/src/api` is regenerated and committed
- [x] Sign-in (password login, magic-link redeem) checks the credentials **before** any device-revocation check: with wrong credentials the answer is the same for an unknown, an active and a revoked `X-KERP-Device-Id` (no device-status oracle to unauthenticated callers); tests for the three device states with wrong credentials. The SSO exchange (not built yet) gets the same rule in T-0054
- [x] Magic-link redeem validates the link **without spending it**, then runs the device check; the link is spent only when the device check passes. A valid link with a revoked device answers `401 {code: DEVICE_REVOKED}` and leaves the link unspent (test: the same link then redeems from an active device); an invalid, expired or spent link gets the uniform refusal whatever the device state
- [x] With valid credentials a revoked device is still refused with `401 {code: DEVICE_REVOKED}` so the client wipes (diff §4.3); `DEVICE_REVOKED` behaviour for authenticated or device-bound sessions (refresh, PIN unlock of a bound session, any authenticated request, enrol) is unchanged; the T-0043 tests keep passing unweakened
- [x] Wipe confirmations and refused confirmations are written to the audit ledger (never the secret)
- [x] The client contract for T-0143 (store the wipe secret in the keystore-backed store per account, present it with the wipe confirmation) is documented in `app/core/auth/README.md`
- [x] TD-286 and TD-291 resolved with a pointer to this task's PR
- [x] Module/README.md and docs updated (`app/core/auth/README.md`, identity README, `frontend/src/api` regenerated if the API schema changed)
- [x] All quality gates green (see CLAUDE.md §Quality gates)

- 2026-11-15 (implementer): done on `task/T-0080-device-hardening`.
  - **Wipe secret**: `devices.new_wipe_secret()` (32 bytes, `secrets.token_urlsafe`), returned only in the `201` of the creating enrolment (`DeviceEnrolled.wipe_secret`; `null` on re-enrolment; not in `DeviceRead`). Stored as SHA-256 hex in `oe_identity_device.wipe_secret_hash` (migration `0018`, nullable, additive). A fast hash is enough for a 256-bit random secret.
  - **Uniform refusal = `404 {"detail": "Not Found"}`** (the task named no code; chosen to match every other out-of-scope answer). The body is optional so a missing secret (no body, `{}`) gets the same `404`, not a `422`; only a malformed body (non-object, extra field) is `422`, which does not depend on the device. Comparable work: one lookup, one SHA-256, one `hmac.compare_digest` against the stored or a fixed dummy digest, and one audit append, whatever the case. A second confirmation with the right secret is `204` and changes nothing.
  - **Audit**: refusals are `wipe_refused` with `reason` (`unknown_device | no_secret | wrong_secret | not_revoked`) on `device:<device_id>` (admins only; the caller never sees it); refusals of unknown ids create chains too, so the endpoint can grow the ledger without limit: TD-298 (rate limit before pilot).
  - **Credentials first**: login authenticates, then `refuse_revoked_device`; a correct password on a revoked device resets the password lockout (the guess was right) and answers `DEVICE_REVOKED`. Magic-link redeem: `RevocationStore.peek_magic_link` (new, `GET` on Redis), then the device check in the link's tenant, then `take_magic_link` (atomic `GETDEL`; a link spent in between is the uniform `401`).
  - The device check on sign-in still looks at any device of the tenant, so with valid credentials one can learn another account's device is revoked: TD-299 (risk, low).
  - Changed T-0043 tests only where the contract changed by design: `test_the_revoked_device_confirms_its_wipe` (404/409 by state, no secret) became the secret-based tests; `test_migrations` head `0016` → `0017`, renumbered to `0018` after T-0044 merged its `0017`. Every other T-0043 test passes unchanged.
  - Migration number: T-0044 merged `0017_deployment_settings` first, so this migration was renumbered to `0018` (down_revision `0017`) at rebase (coordinator).
