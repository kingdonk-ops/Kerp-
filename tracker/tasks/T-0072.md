## Goal
Duplicated or parallel tabs must not sign each other out. After T-0037 the web SPA's refresh
token is an httpOnly cookie that every tab of the browser shares (TD-203, diff §4.2). Two tabs
refreshing at about the same time would both present the same cookie: the second request is
refresh-token reuse and the server revokes the whole session. Serialise refresh across tabs
and hand the new **access token** to the other tabs; the refresh token never leaves the
cookie (owner decision 2026-11-13: keep TD-203's cookie plan).

## Context
Repo review 2026-11-13 (quality + security), owner-accepted.
Finding 3: with the token in `sessionStorage`, a duplicated tab copies it and the second
tab's refresh is treated as reuse (both tabs signed out). With T-0037's shared cookie the same
failure happens whenever two tabs refresh concurrently.

## Acceptance criteria
- [x] Refresh runs under a Web Lock (`navigator.locks`, name `kerp-refresh`) shared by all tabs of the origin
- [x] The tab that refreshed broadcasts the new access token (and its expiry) on `BroadcastChannel("kerp-auth")`; other tabs adopt it instead of refreshing; no refresh token is ever posted on the channel or held in JS
- [x] Inside the lock, a tab that received a fresh access token while it waited uses it instead of calling `/auth/refresh` again
- [x] Logout in one tab is broadcast, and every tab drops its access token
- [x] Without `navigator.locks` / `BroadcastChannel`, behaviour is T-0037's single-tab behaviour
- [x] Unit tests: two API clients on a shared fake lock + channel; concurrent 401s in both tabs produce exactly one `/auth/refresh`; the second tab retries with the broadcast token
- [x] All quality gates green

## Notes
- 2026-11-16: `src/auth/crossTab.ts` (`connectCrossTab`, `browserCrossTab`, `singleTab`); `createApiClient({ crossTab })` runs `/auth/refresh` under the `kerp-refresh` Web Lock and posts `{type:"token", access_token, expires_in}` on `kerp-auth`; `AuthProvider.logout` posts `{type:"logout"}`. A tab adopts a posted token only while it has a session; adopted state is never re-posted. A message delivered after the lock is released costs at most one extra refresh, which is a valid rotation (the shared cookie was already rotated), never a reuse. `AppServices.crossTab` is optional, so test fixtures stay single-tab. Gates: lint, typecheck, 491 tests, build.
