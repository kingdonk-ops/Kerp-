## Goal
One queue for every document QA must verify before a record becomes active (quality-and-inspection.md §QA verification queue). Backend half of the pasted T-0181; the equipment, credential and MTR lanes are T-0260, T-0261 and T-0265; the two-lane window is T-0262.

## Acceptance criteria
- [ ] `oe_qms_verification_item` (`BaseRecordMixin` + project RLS): `target_kind` (`equipment_calibration | staff_credential | material_mtr | material_shelf_life_extension | material_substitution`; the target-kind list is open to providers registered later), `target_id`, `parent_entity_id`, `document_id`, `status` (`pending | approved | rejected | reassigned | escalated | superseded`, default `pending`), `submitted_by_user_id`, `assigned_persona` (default the project's QA reviewer persona), `assigned_user_id`, `decision_by_user_id`, `decision_at`, `rejection_reason`, `follow_up_task_id`; indexes `(project_id, status, target_kind)` and `(project_id, parent_entity_id)`
- [ ] A provider seam: the owning module registers a provider per `target_kind` in its `service.py` (details, OCR values, history of superseded documents, `apply_approved`, `apply_rejected`); qms never reads another module's tables (test with a fake provider)
- [ ] Project setting `qa_reviewer_persona` (default PER-06; a QA-capable persona only, others 422); QA authority = holding that persona on the project; admin grants never confer it (diff §4.1)
- [ ] `GET /api/v1/qms/verifications` (inbox: mine, my persona, all for QA), `GET /{id}` (with provider details and a presigned URL per document, T-0016)
- [ ] `POST /{id}/approve` calls the provider's `apply_approved` in the same transaction (target active/verified, prior superseded and locked); `POST /{id}/reject` needs a non-blank `reason` (422 otherwise), target stays inactive, optional rectification follow-up; `POST /{id}/reassign` to a user or persona with a note; only QA authority may approve or reject (403), nobody decides an item they submitted unless the project allows self-approval (T-0140 setting)
- [ ] A newer submission for the same target supersedes the older pending item (`superseded`)
- [ ] Every create and decision notifies through the notifications service (uploader on decision, assignee on create/reassign; deep link to the item) and is a T-0006 ledger entry
- [ ] Another project's item → 404 (test)
- [ ] Module `README.md` and docs updated
- [ ] All quality gates green (see CLAUDE.md §Quality gates)
