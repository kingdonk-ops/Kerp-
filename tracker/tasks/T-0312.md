## Goal
The issue record and the punch workflow (issues.md §3, §4.1, §4.3, §9). Replaces the punch part of the dropped T-0117 and the anchor/numbering part of the dropped T-0116. Closes the defect loop of TD-167 (owner and due, rectified, verified closed optionally by a re-inspection).

## Acceptance criteria
- [ ] `oe_issues_issue` (`BaseRecordMixin` + project RLS) with the fixed fields of issues.md §3; `answers` validated against the pinned `template_revision_id` with the forms CEL rules (422 with the path); the revision stays pinned for life
- [ ] Anchor: exactly one of `anchor_node_id` / `anchor_item_id` with `anchor_role` recorded (`work_anchor`, `inspection_anchor`, `physical` or `item`; ADR 0003 §2); never a BOQ anchor; a retired node → 422
- [ ] Raise resolves `work_anchor_node_id` through `asset_management.service.work_anchor_for` (T-0101); a path without a work-anchor node → 422 until one is picked or created (TD-113; TD-125)
- [ ] `number` from the project's per-type numbering pattern (pack numbering, defaults `{project}-NCR-{seq:4}` / `{project}-PL-{seq:4}`), assigned by the server, unique per project, never reused; concurrent raises get distinct numbers (test); a voided issue keeps its number
- [ ] Punch: `punch_category` A/B/C required; `open → rectified → verified → closed`; every transition calls `run_checks(context, "issue.punch.<transition>")` with system-default rule sets shipped by the module; verify-reject needs a non-blank reason and returns to `open`; verify may link a passed re-inspection of the same anchor scope (`closed_by_inspection_id`, checked through the inspections service, else 422)
- [ ] Verifier ≠ rectifier enforced in `service.py` whatever `allow_self_approval` says (test); rectify by the owner or PER-03/PER-04, verify by PER-06, PER-07 within site scope, or PER-15 for a client-origin punch; others 403
- [ ] Void from any non-terminal state with a mandatory reason by QA authority or PER-09; terminal states `closed`, `void`, `upgraded`, `escalated` are not open
- [ ] `issues.service.open_issues(scope)` returns the open issues of a work-anchor node, its descendants, its Items and its lineage predecessors through the `asset_management` service (no cross-module table access), and counts by type and Cat A/B/C (for T-0160)
- [ ] `source_inspection_id` is validated through the inspections service; `GET /api/v1/issues?...` and `GET /api/v1/issues/{id}` with filters type, category, status, punch category, origin, assignee, overdue
- [ ] Offline: raise and step mutations carry a client UUIDv7 id (T-0148) and the time evidence of diff §6.4.1; the server assigns the number at sync; a transition failing `run_checks` at sync fails that mutation, keeps the earlier state and notifies the user (test); published issue templates and categories are in the project reference data of the pull scope (T-0147)
- [ ] Every create, transition, assignment and void is a T-0006 ledger entry in chain `issue:<id>`
- [ ] Module `README.md` and docs updated
- [ ] All quality gates green (see CLAUDE.md §Quality gates)
