## Goal
Remove the connection-pool deadlock found in the 2026-11-15 repo review (finding 1). `get_current_user` runs `load_active_user` on the request session (which then holds a pooled connection until the request ends) and *then* `resolve_request_device` opens a second unit of work on the same pool. Any request carrying `X-KERP-Device-Id` (every field-app call; any UUID works) needs two connections at once, so ~15 concurrent requests (default pool 5 + 10 overflow) each hold one and wait for another until `pool_timeout` (30 s) and all return 500. The PER-09 device revoke has the same pattern (`user_has_projects_beyond`).

## Acceptance criteria
- [x] `get_current_user` resolves the request's device (`resolve_request_device`) before the request session runs its first query; behaviour is otherwise unchanged (revoked device: 401 `DEVICE_REVOKED`; header naming another device than the session's binding: 401)
- [x] `user_has_projects_beyond` in the PER-09 revoke path no longer takes a second connection from the request pool while the request session holds one
- [x] Regression test (PostgreSQL suite): an app whose `Database` has `pool_size=1, max_overflow=0` and a short `pool_timeout` serves an authenticated request with a valid device header and one with a random UUID header without a pool timeout
- [x] Regression test (PostgreSQL suite): the same pool serves a PER-09 device revoke (cross-project warning path)
- [ ] All quality gates green

## Context
Repo review 2026-11-15 (quality + security), owner-accepted (finding 1, security: medium).

## Notes
- 2026-11-16: `get_current_user` now resolves the device (own short unit of work) before `load_active_user` touches the request session; `user_has_projects_beyond` reads on the separate side-write pool. Regression tests in `tests/test_devices.py` (`one_connection` fixture: request pool of exactly one connection) fail with a `QueuePool` timeout (500) before the fix and pass after, on SQLite and PostgreSQL.
- 2026-11-16: Side effect of the new order: a request from a revoked device of a user who is also deactivated now gets 401 `DEVICE_REVOKED` (wipe) instead of the plain 401; the device's `last_seen_at` is touched before the user check.
