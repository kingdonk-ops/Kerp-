## Goal
Administration surface for the access model of diff §4.1 (TD-120 3a, TD-184, TD-151): user accounts,
project memberships managed by each project's PER-09 holders, the tenant-level admin grants
(`system_admin`, `create_projects`), and the stricter membership-based visibility of tenant-level
rows decided in TD-053. The tenant stays in code and RLS but is never exposed through this API.

## Acceptance criteria
- [ ] Admin grants table (tenant-level, `BaseRecordMixin`, RLS): one row per user and grant, grant in `system_admin | create_projects`; neither grant is a persona or a project membership (diff §4.1). The appointment API is T-0039; this task creates the table and the `is_system_admin` check
- [ ] User administration: a `system_admin` lists, creates and deactivates user accounts; a PER-09 can invite a user to one of its projects by e-mail, which creates the account if none exists (diff §4.1)
- [ ] Membership administration: a PER-09 of project P (or a `system_admin`) lists, assigns and removes users on P with persona(s) and Asset-Site scope, including PER-09 for co-admins; a PER-09 of P cannot touch memberships of a project where it is not PER-09 (403/404); nobody but a `system_admin` grants tenant-level grants
- [ ] Assigning PER-09 together with a hold-authority persona (PER-02, PER-06, PER-07, PER-11) on the same project succeeds but the response carries a `sod_warning` the UI must confirm (`confirm_sod: true` on the request, else 409), and the assignment is written to the audit ledger with `sod_warning: true` (TD-151, edge §5 Admins)
- [ ] No admin grant or PER-09 confers `A`/`S`: assignment never adds hold or signing capability beyond the personas' own (TD-151)
- [ ] `GET /api/v1/me/projects` lists the caller's non-deleted projects (id, code, name, personas) for the project picker (T-0042)
- [ ] Every membership and grant change is written to the audit ledger
- [ ] Admin endpoints refuse non-admin callers (403; 404 where the project is not visible to them); no endpoint takes or returns a tenant id (diff §4.1)
- [ ] At authentication the server loads the caller's `system_admin` grant from the grants table (security-definer lookup of the caller's own grants, in the same unit of work that derives `app.allowed_project_ids`) and binds it as `app.is_system_admin`; it also binds `app.current_user_id` from the verified token's `sub`. Neither is ever read from token claims, request parameters or headers (edge §6 amendments)
- [ ] The `projects` table and the tenant-level tables that describe a project (memberships) use a membership-based policy: a row is visible only when its project is in `app.allowed_project_ids` or `app.is_system_admin` is true (edge spec §6 amendments, TD-053, TD-120)
- [ ] Admin grants have their own policy: a user reads their own grant rows (`user_id = app.current_user_id`); `app.is_system_admin` sessions read and write all; only those may insert, update or delete grants (edge §6 amendments)
- [ ] PostgreSQL test as `kerp_app`: a non-admin user sees only their own grant rows (another user's `create_projects` row is invisible and cannot be inserted, updated or deleted); a `system_admin` session sees all grant rows; a session with `app.is_system_admin` unset and no grant row sees none
- [ ] PostgreSQL test as `kerp_app`: a client-portal user (PER-15) bound to project A cannot list or fetch project B's row (404); a `system_admin` lists both but reads no project-scoped record of B without a membership
- [ ] `tenant_id` FK added (TD-032)
- [ ] Module `README.md` and `app/core/tenancy/README.md` updated
- [ ] All quality gates green (see CLAUDE.md §Quality gates)
