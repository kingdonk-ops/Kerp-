## Goal
The fixed NCR steps of issues.md §4.2 with template fields per step, CAPA child records and the effectiveness verification as a formal sign-off of the new kind `ncr_close_verify`. Replaces the workflow part of the dropped T-0116.

## Acceptance criteria
- [ ] NCR states `containment → disposition → root_cause → corrective_action → effectiveness → closed`; each transition calls `run_checks(context, "issue.ncr.<step>")` and requires the template's fields of the step; a completed step's fields are read-only (test)
- [ ] Disposition `scrap | rework | repair | use_as_is` with `concession_ref`, recorded by QA authority (403 otherwise); a shipped, not locked default rule requires `concession_ref` for `use_as_is` and `repair` (finding, 422); a project can edit that rule
- [ ] Root cause: `root_cause_category` from a value list `oe_issues_root_cause_category` (`BaseRecordMixin` + RLS) with the same three copied layers as the category list (system seed → tenant/client pack, PER-13 → project copy, QA authority or PER-09; used keys deactivated, never deleted or re-keyed) (seed `workmanship, material, design, procedure, equipment, training, subcontractor, other`) and a non-blank `root_cause_statement`; the optional 5-whys section works as an ordinary template section
- [ ] `oe_issues_action` (`BaseRecordMixin` + project-scoped RLS policy): `kind` (`corrective | preventive`), `description`, `owner_user_id`, `due_date`, `status` (`open | done | cancelled`), `completed_by/at`, `evidence` (attachment ids that are `complete`, T-0016), `cancel_reason` (required to cancel); the owner is notified on assignment (T-0019)
- [ ] The corrective-action step completes only with at least one corrective action and every action `done` or `cancelled`; for `rework` / `repair` a default (not locked) rule requires a linked passed re-inspection before effectiveness
- [ ] Effectiveness verification is a T-0119 sign-off ledger entry of kind `ncr_close_verify` (registered with an intent i18n key and `intent_version`), by the project's QA authority only (403); nobody who recorded the disposition or completed an action may verify (enforced in `service.py`, regardless of `allow_self_approval`; tests); ineffective returns to `corrective_action` with a reason
- [ ] All new tables use `BaseRecordMixin` and have a project-scoped RLS policy (cross-project access → 404, test)
- [ ] `issues.service` exposes open NCR counts and NCR step status for dashboards (T-0160)
- [ ] Module `README.md` and docs updated
- [ ] All quality gates green (see CLAUDE.md §Quality gates)
