## Goal
Close TD-274 and the admin part of review finding 8. Deactivating a user (`PATCH /api/v1/admin/users/{id}`) never checks the last-admin rule, and `revoke` counts `system_admin` grants of deactivated users, so the deployment can be left without an active System admin (recovery needs direct database access). Concurrent duplicate grants and user creations pass the check-then-insert and hit the unique index as a 500.

## Acceptance criteria
- [ ] Deactivating the last active System admin (self or another) is refused with 409, nothing changes; deactivating one of two active System admins works
- [ ] Revoking `system_admin` counts only grants held by active users (the active flag read through `app.core.auth.service`, e.g. `users_by_id`): with admin B deactivated, admin A cannot revoke A's own grant (409)
- [ ] Both checks lock the live `system_admin` grant rows in the same order, so two admins acting at once cannot both pass (PostgreSQL)
- [ ] A concurrent duplicate `POST /admin/grants` answers 200 (already held), never 500; a concurrent duplicate `POST /admin/users` answers 409, never 500 (unique-violation mapping, as `projects/service.py` does)
- [ ] Tests for each case; all quality gates green
