## Goal
One small CEL rule must not be able to tie up a server thread (audit item 1) and a rule accepted at save must be able to run (audit item 11). Bound the cost of every CEL expression with static caps checked at compile time (nested loop macros, nesting depth) and a step budget in the server evaluator, and apply the same static caps in the client runtime so a rule behaves the same in the form and on the server.

## Acceptance criteria
- [x] The limits are defined once: a top-level `limits` block in `tests/contract/conformance_fixtures.json` (`max_expression_bytes` 4096, `max_macro_nesting` 3, `max_nesting_depth` 100, `max_eval_steps`; exact values may be tuned in the PR and recorded in Notes) or a generated constant; `backend/app/core/cel/runtime.py` and `frontend/src/lib/cel/evaluate.ts` read or are asserted equal to it by `tests/test_cel_conformance.py` and `conformance.test.ts` (same pattern as `error_codes`); today the 4096 is copied in both runtimes, which is replaced by this single source
- [x] `_check_tree` refuses an expression with more than `max_macro_nesting` nested loop macros (`all`, `exists`, `exists_one`, `map`, `filter`, counted along one path, not in total) with the existing `PARSE_ERROR` code; sibling (non-nested) macros are still allowed (test for both)
- [x] `_check_tree` measures AST nesting depth iteratively and refuses more than `max_nesting_depth` levels with `PARSE_ERROR` (test: 1500 nested parentheses is `PARSE_ERROR` at compile-on-save and at evaluate, never "maximum recursion depth"; 100 levels still evaluates)
- [x] The strict evaluator (`core/cel/strict.py` / the evaluation path in `runtime.py`) counts evaluation steps and stops after `max_eval_steps` with the existing `EVAL_ERROR` code and a stable message (e.g. `evaluation step budget exceeded`); no new error code is added (test: three nested macros over lists big enough to exceed the budget return `EVAL_ERROR` within a bounded wall time, asserted with a generous timeout)
- [x] Regression test from the audit: the 172-byte four-nested-`.all()` rule and a six-nested one are refused at save (`compile_expression`) and in the validation "Try it" endpoint (`validation/router.py`) with `PARSE_ERROR` in well under a second
- [x] Rule save and `run_checks` use the same compile path, so a refused rule cannot be stored; existing stored rules that exceed a cap fail closed as before (documented in the validation README)
- [x] The client runtime applies the same macro-nesting and depth caps before compiling (cel-js) and returns `{ok: false, code: "PARSE_ERROR"}`; the step budget is applied on the client too if cel-js exposes a hook, otherwise this is recorded as a `known_gap`/TODO (server is the hard gate)
- [x] Conformance fixtures under `category: limits` for: macro nesting at and above the cap, depth at and above the cap; both runtimes pass them. `gap.long_addition_chain` (TD-471) is re-checked: if the depth cap now rejects it on both runtimes it becomes a parity fixture with `PARSE_ERROR` and TD-471 gets a dated note
- [x] `backend/app/core/cel/README.md`, `frontend/src/lib/cel/README.md` (Limits) and `tests/contract/README.md` document the limits
- [x] Module/README.md and docs updated

## Notes
- 2026-11-21 (planner): Created from the 2026-11-21 codebase audit; one PR with T-0342..T-0349 on branch `task/T-0341-audit-hardening`. Module `platform` because `core/cel` was built by T-0017 (platform); the "Try it" route is in `validation`.
- 2026-11-21 (planner): Planner defaults: static caps answer `PARSE_ERROR` (as the audit asks and as the existing macro-argument refusals do); a spent step budget is `EVAL_ERROR` (a runtime failure, fail closed); the length cap stays `INVALID_ARGUMENT`. No new error code, so `error_codes` and both enums are unchanged.
- 2026-11-21 (implementer): Limits live in `backend/app/core/cel/limits.py` and `frontend/src/lib/cel/limits.ts`, asserted equal to the new top-level `limits` block of `tests/contract/conformance_fixtures.json` by both conformance suites (constants rather than reading the JSON at runtime: `tests/` does not ship with the app). Values: `max_expression_bytes` 4096, `max_macro_nesting` 3, `max_nesting_depth` 100, `max_eval_steps` 50000 (planner left the last open; 100k steps took up to ~0.8 s on identifier-heavy bodies here, 50k keeps the worst case around 0.4 s while a 25-node predicate still covers ~2,000 list items).
- 2026-11-21 (implementer): Macro nesting counts only through a macro's arguments (evaluated per element), not its receiver (evaluated once), so chained macros are not "nested"; data growth through chains is bounded by the step budget instead. Depth is two measures, both capped at 100: syntax-tree depth (catches left-deep `1 + 1 + ...` and `!!!...` chains) and parser depth, which is exactly cel-js's `limits.maxDepth` (parentheses, arguments, list/map elements, selection chains). The client sets `maxDepth` and walks the AST for the other two; the server computes all three in one iterative pass over the lark tree. A randomised cross-check (~3,000 expressions) agreed on all three measures except comparison chains mixing `==` with `in`/`<`, which the two parsers group differently (one tree level; noted in TD-471 and `tests/contract/README.md`).
- 2026-11-21 (implementer): celpy recurses ~3 Python frames per parse-tree node, so at-cap expressions (100 nested list literals) need ~4,000 frames; celpy sets the recursion limit to 2,500 and 80 parentheses already failed. `evaluate` now raises it to `RECURSION_LIMIT` = 10,000 if lower (frames are heap-allocated on 3.11+; checked in 256 KiB threads). Tests evaluate every at-cap shape starting from a limit of 1,000.
- 2026-11-21 (implementer): The step budget is counted in `StrictEvaluator._visit_tree` (same body as lark's, so no extra frame per level) and raises `StepBudgetExceededError` (not a `CELEvalError`), so `true || <heavy>` and macros cannot absorb it: the whole evaluation is `EVAL_ERROR` `evaluation step budget exceeded`. Client: cel-js has no step hook -> TD-533 (server is the hard gate).
- 2026-11-21 (implementer): `gap.long_addition_chain` is now the parity fixture `limits.depth_long_addition_chain` (`PARSE_ERROR` on both); `edge.sc.long_and_chain` (450-term `&&`) changed from `true` to `PARSE_ERROR` on both for the same cap. TD-471 has a dated note. The 172-byte audit rule is `AUDIT_RULE` in `backend/tests/test_cel_limits.py` (synthetic, built to the audit's description; the audit did not quote it).
