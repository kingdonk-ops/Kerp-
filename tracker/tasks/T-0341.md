## Goal
One small CEL rule must not be able to tie up a server thread (audit item 1) and a rule accepted at save must be able to run (audit item 11). Bound the cost of every CEL expression with static caps checked at compile time (nested loop macros, nesting depth) and a step budget in the server evaluator, and apply the same static caps in the client runtime so a rule behaves the same in the form and on the server.

## Acceptance criteria
- [ ] The limits are defined once: a top-level `limits` block in `tests/contract/conformance_fixtures.json` (`max_expression_bytes` 4096, `max_macro_nesting` 3, `max_nesting_depth` 100, `max_eval_steps`; exact values may be tuned in the PR and recorded in Notes) or a generated constant; `backend/app/core/cel/runtime.py` and `frontend/src/lib/cel/evaluate.ts` read or are asserted equal to it by `tests/test_cel_conformance.py` and `conformance.test.ts` (same pattern as `error_codes`); today the 4096 is copied in both runtimes, which is replaced by this single source
- [ ] `_check_tree` refuses an expression with more than `max_macro_nesting` nested loop macros (`all`, `exists`, `exists_one`, `map`, `filter`, counted along one path, not in total) with the existing `PARSE_ERROR` code; sibling (non-nested) macros are still allowed (test for both)
- [ ] `_check_tree` measures AST nesting depth iteratively and refuses more than `max_nesting_depth` levels with `PARSE_ERROR` (test: 1500 nested parentheses is `PARSE_ERROR` at compile-on-save and at evaluate, never "maximum recursion depth"; 100 levels still evaluates)
- [ ] The strict evaluator (`core/cel/strict.py` / the evaluation path in `runtime.py`) counts evaluation steps and stops after `max_eval_steps` with the existing `EVAL_ERROR` code and a stable message (e.g. `evaluation step budget exceeded`); no new error code is added (test: three nested macros over lists big enough to exceed the budget return `EVAL_ERROR` within a bounded wall time, asserted with a generous timeout)
- [ ] Regression test from the audit: the 172-byte four-nested-`.all()` rule and a six-nested one are refused at save (`compile_expression`) and in the validation "Try it" endpoint (`validation/router.py`) with `PARSE_ERROR` in well under a second
- [ ] Rule save and `run_checks` use the same compile path, so a refused rule cannot be stored; existing stored rules that exceed a cap fail closed as before (documented in the validation README)
- [ ] The client runtime applies the same macro-nesting and depth caps before compiling (cel-js) and returns `{ok: false, code: "PARSE_ERROR"}`; the step budget is applied on the client too if cel-js exposes a hook, otherwise this is recorded as a `known_gap`/TODO (server is the hard gate)
- [ ] Conformance fixtures under `category: limits` for: macro nesting at and above the cap, depth at and above the cap; both runtimes pass them. `gap.long_addition_chain` (TD-471) is re-checked: if the depth cap now rejects it on both runtimes it becomes a parity fixture with `PARSE_ERROR` and TD-471 gets a dated note
- [ ] `backend/app/core/cel/README.md`, `frontend/src/lib/cel/README.md` (Limits) and `tests/contract/README.md` document the limits
- [ ] Module/README.md and docs updated
- [ ] All quality gates green (see CLAUDE.md §Quality gates)
