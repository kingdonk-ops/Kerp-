- 2026-11-13 (implementer): `app/modules/uploads/` (manifest depends on jobs + projects, not toggleable), table `oe_uploads_file` (BaseRecordMixin, project RLS, migration `0009`), API under `/api/v1/uploads/projects/{project_id}/files`. Flow: presign (`C`) → client PUT to `staging/{tenant}/{project}/{file_id}` (Content-Type and Content-Length signed) → `complete` (`C`: HEAD, size, magic bytes; mismatch → `rejected` with a reason code) → job `uploads.verify` (interactive: streamed SHA-256, scan stub, copy to `{tenant}/{project}/{module}/{sha256}`, `available`) → presigned download (`V`) with the served type and Content-Disposition forced (H-10). Orphan sweep `uploads.sweep_orphans` (batch) per project.
- Decisions: (1) Inspection-ERP source is not in this repo; the storage helpers and their tests are written from ADR 0007's description. (2) Uploads land in a staging key and only the verify job writes the content-addressed key, so a client cannot overwrite a verified object by declaring someone else's hash; the spec's `{hash}.ext` is `{hash}` (task brief; filename and type live on the row). (3) Request project binding (TD-122 still open): the router checks membership/capability with `load_grants`/`project_access`, then rebinds the request session to the path's project with `resolve_scope` (after `expunge_all`, since the principal's user is loaded in it). (4) `JobContext` gained `db` (the worker's `Database`) so handlers can open their own short units of work; `verify_upload` holds no transaction while hashing. (5) boto3 added (runtime, lazily imported, on the T-0022 banned list with botocore); `boto3-stubs[s3]` for mypy; lock regenerated with uv (python-dateutil pinned back to 2.9 by botocore). (6) Rejection reasons are codes for client-side i18n.
- Follow-ups: TD-206 (real malware scanner), TD-207 (scheduled sweep, needs TD-155), TD-208 (bucket provisioning, CORS, staging lifecycle, compose env, MinIO in CI), TD-209 (delete + content GC, stuck `verifying`). The real-MinIO test skips unless `KERP_TEST_S3_ENDPOINT` is set (CI has no MinIO, TD-208).
- 2026-11-13 (implementer): S3 region criterion added from TD-171 decision 13a / PR #48. `s3_region` now defaults to `ap-southeast-2` (`KERP_S3_REGION`, set per deployment); the endpoint is `KERP_S3_ENDPOINT_URL`. Documented in the uploads README and the backend README settings table. The repo has no `.env.example` (local overrides go in the git-ignored `.env`), so none was added. A test checks the configured region reaches both boto3 clients and the signing scope.
