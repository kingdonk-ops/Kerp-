## Goal
Add **PER-16 "Project Viewer"** to the core persona and capability model (edge spec §5.2
amendment, user 2026-11-13, TD-251). It is a read-only internal persona: Viewer tier (`V`
only), single-project scope, read access across modules, and no hold, approval or signing
authority. It has no separation-of-duties implications. A project's PER-09 can assign it
individually through the existing membership paths, and team links can carry it (T-0073,
T-0013).

## Acceptance criteria
- [x] `app/core/auth/access.py`: `Persona.PROJECT_VIEWER = "PER-16"`, a `Tier.VIEWER` with `TIER_CAPABILITIES[Tier.VIEWER] = {V}`, and `PERSONAS[PER-16] = PersonaSpec(Tier.VIEWER, Scope.SINGLE)` (no holds, no commercial approval, no signatory). `sod_violations()` stays empty. PER-16 is not in `SOD_BLOCKED` and is not a hold-authority persona for the PER-09 SoD warning
- [x] `app/core/auth/models.py`: `PERSONA_CODES` covers PER-01..PER-16. Additive migration (next free revision) replaces the `persona` CHECK on `auth_project_membership` so it allows PER-16. Existing rows are unaffected. The downgrade refuses to run, with a clear error, while non-deleted PER-16 rows exist (it never deletes memberships silently). The migration is covered by ADR 0008 (core-table change, accepted)
- [x] Behaviour: a PER-16 member gets `project_access(P)` with capabilities `{V}` only. `require_capability(C|E|A|S|admin)` returns 403 for them, and `can_release_hold` is False for every kind. PER-16 is not a portfolio persona, so the allowed project list stays unchanged. The bound project reads the same as for other single-scope personas
- [x] Every place that lists or validates personas accepts PER-16 (e.g. membership create paths and any persona enum in schemas/OpenAPI). `npm run gen:api` is re-run and committed if the OpenAPI schema changes. Any frontend persona label goes through i18n `t()`
- [x] Tests: persona matrix test updated (16 personas, PER-16 = `{V}`). A capability guard matrix row for PER-16 (reads 200, writes 403). PostgreSQL migration test: a PER-16 membership row inserts after the upgrade, and a PER-17 row is still rejected
- [x] Module/README.md and docs updated (`app/core/auth/README.md` persona table; the spec is already amended)
- [x] All quality gates green (see CLAUDE.md §Quality gates)

Because the table's RLS is forced and CI migrates as `kerp_app` (not a superuser), the check runs inside the migration transaction with `NO FORCE ROW LEVEL SECURITY` and `FORCE` is restored afterwards. Without that it would see no rows.
