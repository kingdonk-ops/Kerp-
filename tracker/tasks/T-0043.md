## Goal
TD-164 decision 17a: know every field device, revoke it remotely (sessions killed, local data wiped on next contact) and record the device in the audit ledger.

## Acceptance criteria
- [x] `oe_identity_device` (tenant-level, `BaseRecordMixin`, RLS): user, client-generated `device_id`, platform, OS and app version, `enrolled_at`, `last_seen_at`, `last_sync_at`, status `active|revoked`, revoked by/at, `wipe_confirmed_at` (diff §4.3)
- [x] A field client enrols on sign-in (`POST /api/v1/devices/enrol`); the session (`sid`) is bound to the device; requests from a device send its id and update `last_seen_at`
- [x] Revoke (`POST /api/v1/devices/{id}/revoke`) by a `system_admin`, a PER-09 of a project the device's user belongs to, or the user (user, 2026-11-13); others get 403/404; revoke kills every session of the device immediately
- [x] Planner addition (mitigation for Q4a): when the revoker is a PER-09 (not the user or a `system_admin`) and the device's user belongs to other projects, the revoke API returns a warning that unsynced work of those other projects on the device will be wiped and needs `confirm_cross_project_wipe: true` (else 409); the revoke is written to the audit ledger with the actor, the role used (`system_admin` / `per_09` + project / `self`) and whether the warning was confirmed (diff §4.3)
- [x] Any later call from a revoked device (incl. refresh and sync) returns 401 with `code: DEVICE_REVOKED`; `POST /api/v1/devices/{id}/wipe-confirmed` records the wipe
- [x] Ledger entries written through a device carry `device_id`: additive nullable column included in the content hash from ledger `v` = 2, existing v1 rows still verify; the core-table change is recorded in a short ADR in `docs/decisions/` (CLAUDE.md §6, diff §4 ledger design)
- [x] List devices per user (admin) and own devices (user) with last-seen and last-sync times
- [x] Android refresh-token body transport (TD-203): login and refresh return the refresh token in the JSON body (and accept it in the body) **only** when the request `Origin` is on an explicit native-app allow-list in deployment configuration (`KERP_NATIVE_APP_ORIGINS`, e.g. the Capacitor app origin); every other request, including one with no `Origin`, gets the cookie transport of T-0037. The choice never depends on the client-reported device `platform` or any request flag (diff §4.2)
- [x] Startup fails when `KERP_NATIVE_APP_ORIGINS` contains the deployment's own web origin (or any origin the SPA is served from); CORS for the native origins is configured from the same allow-list, without credentials (body transport needs no cookies)
- [x] Test: a login and a refresh from the deployment's web origin never receive the refresh token in the body, even when the session's device is enrolled with `platform: android`; the same calls from an allow-listed native origin do; a non-allow-listed origin falls back to the cookie
- [x] `app/core/auth/README.md` documents the native-origin allow-list next to the API CORS settings (optional later hardening: device-bound attestation, e.g. Play Integrity)
- [x] `app/core/audit/README.md` and the identity README updated
- [x] All quality gates green (see CLAUDE.md §Quality gates)

## Notes
- 2026-11-13 (planner): Biometric unlock, certificate pinning and per-device sync-health views come after the pilot: TD-204. The client wipe is T-0143.

- 2026-11-13 (planner, PR #48 review round 1): Who may revoke is a user decision (Q4a). The cross-project wipe warning and audit criterion are a planner addition (mitigation for Q4a), not part of the user's answer.

- 2026-11-13 (planner, PR #48 review round 2): Android JSON-body transport moved here from T-0037: selected only by an allow-listed native `Origin`, never by the client-reported platform, so script on the web origin (XSS) cannot obtain the refresh token in a body.

- 2026-11-15 (implementer): Built in `app/core/auth/` (the identity module lives in core, as in T-0008/T-0010): `oe_identity_device` in `models.py` (migration `0016`, standard tenant-level RLS; authorisation in the API, dedicated policy: TD-284), registry + session binding in `devices.py`, endpoints in `device_api.py`, the `DEVICE_REVOKED` signal in `device_signal.py`. Sessions are bound to a device in the revocation store (`device:sid:<sid>`, `device:sids:<device_id>`); revoke kills every bound session with a `revoked:device-sid` marker so its next access, refresh or PIN unlock answers `401 {code: DEVICE_REVOKED}`; any call naming a revoked device in `X-KERP-Device-Id` (login, redeem, refresh, unlock, enrol, any authenticated request) does too and kills that session. Paths use the client `device_id` (unique per tenant; another account's id is 409, shared tablets: TD-283). `wipe-confirmed` takes no bearer (the device's sessions are dead; risk TD-286). Revoke authority: self first, then `system_admin`, then PER-09 of a shared project; a member of a shared project without PER-09 gets 403, everyone else 404. The cross-project check reads the owner's full project list server-side (`access.user_project_ids`, own-rows unit of work like `resolve_request_scope`) and never names those projects in the 409. Ledger: `device_id` + `hash_version` (v2 hashes `device_id`; v1 rows keep verifying), ADR 0010; `append` takes the device explicitly or from `current_device_id`, set at authentication only from the session binding or an enrolled device of the same user. Native transport: `KERP_NATIVE_APP_ORIGINS` (normalised origins); readings raised as spec-gap TD-285 (KERP_WEB_ORIGIN required with it; body transport also on magic-link redeem and PIN unlock, the Android field-worker path). CORS only for the native origins, no credentials. `last_sync_at` is set by `devices.record_sync`, which the future sync endpoints must call (TD-282). Size: above the M guideline (about 1,500 added lines of Python under `app/` and `migrations/`, much of it docstrings and the migration's frozen SQLite table, plus tests, docs and the regenerated `frontend/src/api`); not split because enrolment, revoke, the wipe signal and the body transport share the session-binding code and their tests.
