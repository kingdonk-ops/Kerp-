## Goal
Product-owner decision 2026-11-14 (diff §4.1 *External invitees create their own password*): clients and subcontractors never use Microsoft sign-in; a brand-new invitee creates their own password from the e-mailed invite link while accepting the invite.

## Acceptance criteria
- [x] Creating an invite (T-0052) enqueues the invite e-mail through T-0058 (never synchronous): project code and name, inviter name, expiry, link `/invite#<invite_token>.<setup_token>` (both in the fragment); the inviter's response still returns the copyable link once with the `invite_token` only (fallback)
- [x] `setup_token`: ≥ 256-bit random, stored only as a hash on the invite, single-use, same expiry as the invite, revoked with it (re-invite and revoke); never in the invite response, logs or Sentry (test asserts)
- [x] `POST /api/v1/invites/setup-preview` (not signed in; both tokens in the body) returns project code and name and whether a first password can be set (the account has no credentials); otherwise a neutral answer telling the client to sign in
- [x] `POST /api/v1/invites/accept-with-password` (not signed in; `invite_token`, `setup_token`, new password): only for an active account without credentials whose e-mail is the invited one; enforces the T-0077 policy, sets the password and issues the session **through core auth's public functions** (T-0077 policy plus a core set-password / issue-session API; the admin module never writes the users table), accepts the invite (membership); the session is the normal one (cookie or native body transport, `session_expires_at`, `joined_project_id`) in one transaction; any token problem → the neutral 410 of T-0052; an account that already has credentials → 409 `code: INVITE_SIGN_IN_REQUIRED` (sign in instead)
- [x] With only the `invite_token` (copied link) no password can be set; the client offers the T-0077 reset ("Send me an e-mail to set my password") and accepts through T-0052 carry-through after sign-in
- [x] Re-send (product owner, 2026-11-14; diff §4.1 Re-send): the T-0052 re-send also rotates the `setup_token` (old one invalid, new hash, new expiry equal to the invite's) and enqueues a fresh invite e-mail with the new `/invite#<invite_token>.<setup_token>` link; the re-send response never carries the `setup_token`
- [x] Audited: invite e-mail queued, first password set, acceptance; the PER-09 never sees or can set the invitee's password
- [x] Tests (fake mail transport): two parallel `accept-with-password` calls with the same tokens → one 200, one 410; brand-new external invitee sets password from the e-mailed link and lands in the project; copied link cannot set a password; wrong/expired/revoked/used tokens; account with existing password gets 409; re-invite revokes the old setup token; after a re-send the old e-mailed link gets 410 from `setup-preview` and `accept-with-password`, the new e-mailed link sets the password, and the re-send response contains no `setup_token`; policy rejection leaves the invite pending
- [x] Module `README.md` and docs updated
- [x] All quality gates green (see CLAUDE.md §Quality gates)
