## Goal
Follow-up tasks from post-submit rules and the tagout gate on equipment (quality-and-inspection.md §Post-submit automation; diff §5 *Out of service and tagout*).

## Acceptance criteria
- [ ] `oe_inspections_follow_up` (`BaseRecordMixin` + RLS): `inspection_id`, `equipment_id`, `anchor_node_id`, `anchor_item_id`, `kind` (`tagout_confirmation | repair_request | supervisor_review`), `title`, `status` (`open | tagout_confirmed | resolved | cancelled`), `blocks_return_to_service`, `assigned_persona`, `assigned_user_id`, `due_at` (SLA hours from the config), `tagout_confirmed_by/at/notes`, `tagout_photo_attachment_id`, `resolved_by/at`, `resolution_notes`
- [ ] `create_action_task` creates the follow-up after submit; with `tagout_confirmation` + `blocks_return_to_service`, the target is set `out_of_service` in the same transaction through the equipment service (or node/Item through the asset service)
- [ ] The assigned supervisor (PER-04/PER-03) gets a pinned high-priority notification 'Confirm physical tagout applied' (pin cleared by confirmation through `clear_pins`)
- [ ] `POST /follow-ups/{id}/confirm-tagout` (timestamp, user, optional photo via T-0016, notes) and `/resolve`, `/cancel` (PER-03/04/06 of the project; cancel needs a reason)
- [ ] The inspections module registers a check provider used by the `equipment.activate` rule set: equipment with an open blocking follow-up cannot return to `active` (422 from `run_checks`, test); closing it lets the gate pass (test)
- [ ] A critical defect on a pre-start: status `out_of_service` at once, supervisor notified, tagout follow-up created (integration test)
- [ ] Every step is an action-log row and a ledger entry (`source = "automation"` for automatic steps, the user's for confirmations)
- [ ] Module `README.md` and docs updated
- [ ] All quality gates green (see CLAUDE.md §Quality gates)
