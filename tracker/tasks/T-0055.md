## Goal
"Sign in with Microsoft" in the web SPA (diff §4.5), returning to the same landing as any other sign-in.

## Acceptance criteria
- [x] The sign-in screen shows "Sign in with Microsoft" only when the server reports SSO as enabled (T-0054) and starts `/auth/sso/entra/start` by a top-level navigation (so the pre-auth cookie of T-0054 is set in this browser) (passing a pending `invite_token` once T-0053 exists)
- [x] After the callback the SPA lands per diff §4.1 (one project → in, several → last used, none → lobby; `joined_project_id` → that project) on the session the server set (cookie transport, no token in JavaScript storage)
- [x] Refusals (no KERP account, deactivated, verification failure) show the translated server message with a hint to ask the administrator; no token or claim content is shown or logged
- [x] SSO promoted, password kept (product owner, 2026-11-14; diff §4.5): when SSO is enabled, "Sign in with Microsoft" is the **primary, default** action on the sign-in screen (first, visually primary, focused by default) with a short hint for company staff; password sign-in stays on the same screen as a secondary option for everyone, internal users included (no hiding or disabling it by e-mail domain or internal status; a component test enters an internal-domain e-mail and still submits a password login); the magic-link request stays available (Field Workers only, decided server-side with a neutral response, T-0057); with SSO disabled the screen shows password (and magic link) only, as before
- [ ] All strings through `t()`; component tests with a mocked server; one e2e journey against the fake OIDC provider of T-0054 (sign in → lands in the project)
- [x] Module `README.md` and docs updated
- [x] All quality gates green (see CLAUDE.md §Quality gates)
