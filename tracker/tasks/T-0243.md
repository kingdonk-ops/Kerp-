## Goal
System admins see each account's state, sessions and presence (diff §4.8).

## Acceptance criteria
- [ ] Additive migration on `auth_user` (core table; an ADR in `docs/decisions/` (next free number) is written in this PR): nullable `first_login_at`, `last_login_at`, `last_active_at`; backfill per TD-406
- [ ] `start_session` sets `first_login_at` once and `last_login_at` every time for password, SSO and magic-link sign-ins (PIN unlock and refresh do not)
- [ ] `last_active_at` updated on refresh and authenticated requests at most once per 5 minutes per user via a Redis claim, after the response path's DB work (no extra pooled connection, T-0210)
- [ ] Revocation store keeps a per-user index of live sessions (id, expiry) maintained at sign-in, logout, password change, device revoke and deactivation; `active_session_count` excludes revoked/expired
- [ ] Derived `status` (`invited | active | deactivated`) and `presence` (`online | idle | offline`) per §4.8 (fake-clock tests for each boundary)
- [ ] `GET /api/v1/admin/users` (`system_admin`) adds status, presence, session count, first/last login, last active, project count and tenant grants; filters status, presence, grant, project; search by name or e-mail; paged
- [ ] Module `README.md` and docs updated
- [ ] All quality gates green (see CLAUDE.md §Quality gates)
