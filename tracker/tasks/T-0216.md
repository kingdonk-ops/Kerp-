## Goal
Review finding 8 (validation part): `request_unlock` checks for a pending request and then inserts, with no unique index, so two concurrent requests create two pending rows for the same rule.

## Acceptance criteria
- [x] Additive migration: older duplicate `pending` unlock requests of one rule are set `cancelled` and their ids logged by the migration (a migration does not append to the audit ledger), then a partial unique index on `rule_id` where `status = 'pending'` is created; downgrade drops it
- [x] A concurrent duplicate request answers 409 (unique violation mapped to `RuleStoreError`), never 500
- [x] Tests: migration upgrade/downgrade, duplicate request 409
- [ ] All quality gates green

## Context
Repo review 2026-11-15, owner-accepted (finding 8).

## Notes
- 2026-11-16: Migration `0020` keeps the oldest pending request per rule and cancels the rest (decided by their own requester, i.e. a withdrawal; ids logged), with RLS lifted for the owner during the data step as in `0012`. `request_unlock` inserts inside a SAVEPOINT; the pending check is `_pending_unlock_of` (stubbed in the race test). `tests/test_migrations.py` pins the head revision: now `0020`.
- 2026-11-16: Review round 1 (PR #103): on SQLite, `begin_nested()` before any write made the SAVEPOINT the outermost transaction, so the unlock request was committed before its audit entry. `request_unlock` now flushes without a savepoint and a duplicate raises `RuleStoreError` (409) so the whole unit of work rolls back (SQLAlchemy's pysqlite BEGIN recipe was tried and rejected: real read transactions on SQLite block the findings side-write pool, 13 failures). Regression test `test_an_unlock_request_rolls_back_with_its_unit_of_work`. Only the one-pending unique violation maps to 409 (other constraint errors propagate); the migration's cancel step also sets `updated_by`.
