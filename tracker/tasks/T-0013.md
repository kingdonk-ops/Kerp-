## Goal
A `teams` module (`backend/app/modules/teams/`) for **tenant-level** named groups of user
accounts. A `system_admin` manages them and links each team to one or more projects, with
**one role (persona) per project**. Every team member then gets that access on that project:
the teams service keeps the derived membership rows in step through the core API from T-0073
(diff §4.1 Teams, ADR 0008). Other modules use the service contract to ask "which teams of
this project is the user in?". This is what the `my_teams` filter op and saved-view visibility
`team` are built on (register-views §2, §3; T-0074). Teams appear in the Backbone nav group
(diff §6.1).

Scope (user decisions 2026-11-13: TD-228 overridden, TD-229 confirmed):
- Teams, members and links are tenant-level rows. Only `system_admin` (T-0014's
  `is_system_admin`) writes them. A PER-09 manages only the individual members of its project
  (T-0014) and has no team rights.
- Members are active user accounts of the tenant. Project membership is not required: team
  membership plus a link is what gives the access.
- A link carries one persona per (team, project). Allowed personas follow TD-251's default:
  PER-01 to PER-14 except PER-09. A PER-07 link names its `site_node_id`.
- Teams are for access only. Rosters, shifts, crews and people without a login belong to the
  planner resource pool (TD-073, TD-083). "Project team" in handover §2/§8 and planner §12
  means everyone with access to the project.
- No other module reads the teams tables (CLAUDE.md §6). The teams module never writes
  `auth_project_membership` directly. It calls `app.core.auth` (T-0073).

## Acceptance criteria
- [ ] Module `teams` follows the T-0011 manifest contract (`manifest.py`, `models.py`, `router.py`, `service.py`, `schemas.py`, `README.md`), depends on `projects`, routes mount at `/api/v1/teams`. It is not toggleable per project: a link grants project access, so turning the module off for one project must not silently keep or drop grants. The README documents why
- [ ] Tables, all `BaseRecordMixin`, tenant-level (`project_id IS NULL`, CHECK), additive migration (next free revision; re-point `down_revision` if another branch takes it first):
  - `oe_teams_team` (`name`, `description`): `name` is unique per tenant among non-deleted teams, case-insensitively (409)
  - `oe_teams_member` (`team_id`, `user_id`): unique among non-deleted rows
  - `oe_teams_project_link` (`team_id`, `linked_project_id`, `persona`, `site_node_id`): one non-deleted link per (team, project). Persona is CHECKed against the allowed set. `site_node_id` is required if and only if persona = PER-07
- [ ] RLS (PostgreSQL), following T-0014's tenant-level policy pattern: `app.is_system_admin` sessions read and write all three tables. Any other session reads a team, its members and its links only when the team is linked to a project in its scope (bound project or `app.allowed_project_ids`) or the caller (`app.current_user_id`) is a member. Nobody else inserts, updates or deletes
- [ ] Admin API under `/api/v1/teams` (all writes `system_admin` only; others get 403, or 404 where the team is not visible to them):
  - `GET /teams`, `GET /teams/{team_id}` (members, links), `POST /teams`, `PATCH /teams/{team_id}`, `DELETE /teams/{team_id}` (soft delete: ends memberships and links and revokes their derived grants)
  - `PUT /teams/{team_id}/members/{user_id}` (idempotent, 204) and `DELETE` (204). An unknown, deactivated or other-tenant user gets 422 with the same body every time (no user enumeration)
  - `PUT /teams/{team_id}/projects/{project_id}` with `{persona, site_node_id?}` creates the link or changes its role (idempotent when unchanged). `DELETE /teams/{team_id}/projects/{project_id}` unlinks. A deleted or other-tenant project returns 404
- [ ] Project read API: `GET /api/v1/teams/projects/{project_id}/teams` lists the teams linked to the project, with their role and member count, for anyone with access to the project (individual or team-derived). `GET /api/v1/teams/projects/{project_id}/teams/mine` lists the caller's teams on that project (for the `my_teams` UI) and is declared before `/{team_id}`. The path project is bound like `uploads` (`_bind_project` via `resolve_scope`) until TD-122. A caller without access gets 404
- [ ] Derived access stays in step. Every member add/remove, link create/re-role/remove and team delete calls `app.core.auth.sync_team_link_grants` / `revoke_team_link_grants` (T-0073) for each affected link, in the same transaction. Tests: a user added to a team linked to P as PER-04 gets `project_access(P)` with PER-04, and a portfolio persona link puts P in `allowed_project_ids`. Removing the user, unlinking or deleting the team takes the access away. An individual membership on P is never touched
- [ ] `teams reconcile` (CLI or service function, used by tests): recomputes the expected derived rows from the teams tables, compares them with the core store through the T-0073 API, and reports drift (`--fix` repairs it)
- [ ] Every team create/edit/delete, member add/remove and link create/re-role/remove is written to the audit ledger on chain `team:<id>`, with the actor. An idempotent no-op writes no audit row. The derived-grant changes are audited by T-0073
- [ ] Service contract in `teams/service.py`, documented in the README as the public API. Soft-deleted teams, members and links are ignored, and a member counts only while their account is active:
  - `project_team_ids(session, project_id) -> frozenset[UUID]`: teams linked to the project
  - `user_team_ids(session, user_id) -> frozenset[UUID]`: the user's teams **linked to the session's bound project** (empty without a bound project)
  - `is_member(session, team_id, user_id) -> bool`: False for an unknown or deleted team
  - `team_member_ids(session, team_id) -> frozenset[UUID]`
  - `team_exists(session, team_id) -> bool`
- [ ] Access errors: cross-tenant team, user or project ids return 404 (422 for member user ids, as above). No endpoint takes or returns a tenant id
- [ ] Tests:
  - API role matrix: `system_admin` manages. PER-09 of a linked project reads the project list but cannot write (403). A user without access to the project gets 404 on the project list
  - Duplicate team name returns 409. Re-adding a member or re-linking with the same role is a no-op. A deleted team disappears from every list and contract function
  - Contract: a user in team A (linked to P and Q) is in `user_team_ids` in a session bound to P and to Q, but not in one bound to R, where A is not linked
  - PostgreSQL as `kerp_app`: a non-admin session cannot insert or update team, member or link rows. A non-member session bound to an unlinked project reads none. Another tenant's rows are invisible
  - Contract with a test-only consumer model: a record shared to team X is visible to a member of X and invisible to a project member outside X (the behaviour T-0074 builds on)
- [ ] `docs/` updated where the module list or nav mapping names teams; `npm run gen:api` re-run and committed if the OpenAPI schema changed
- [ ] Module/README.md and docs updated
- [ ] All quality gates green (see CLAUDE.md §Quality gates)
