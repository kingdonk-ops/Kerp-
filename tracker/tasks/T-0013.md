## Goal
A `teams` module (`backend/app/modules/teams/`) that holds **named groups of KERP users inside
one project** and gives other modules one way to ask "which teams is this user in?" and "is
this user in team X?". This is what the saved-view visibility `team` (register-views §3,
acceptance §5.4) and the register filter op `my_teams` (register-views §2) are built on.
Teams appear in the Backbone nav group (diff §6.1).

Scope (planner defaults, TD-228, TD-229):
- Teams are **project-scoped** (project RLS, `project_id` NOT NULL). No tenant-level or
  cross-project teams.
- Only users with an active membership on the project (T-0010 membership store) can be team
  members. A team holds login users only. Rosters, shifts, crews and people without a login
  belong to the planner resource pool (TD-073, TD-083). The "project team" in handover §2/§8
  and planner §12 means every member of the project, not a team from this module.
- Holders of the `admin` capability on the project (PER-09) manage teams. Every project
  member can read them.
- "Entity visibility" here means the **service contract** only. Each module that owns a record
  with `visibility = team` stores a `team_id` and filters its own rows using the team ids it
  gets from this module's `service.py`. No other module reads the teams tables (CLAUDE.md §6).
  The first consumer is saved views (T-0020, TD-230).

## Acceptance criteria
- [ ] Module `teams` follows the T-0011 manifest contract (`manifest.py`, `models.py`, `router.py`, `service.py`, `schemas.py`, `README.md`), is toggleable, depends on `projects`, and its routes mount at `/api/v1/teams`
- [ ] Tables `oe_teams_team` (`name`, `description`) and `oe_teams_member` (`team_id`, `user_id`) use `BaseRecordMixin`, `project_id` NOT NULL, the standard project RLS policy. Additive migration (next free revision; re-point `down_revision` if another branch takes it first). Team `name` is unique per project among non-deleted teams, case-insensitively (409 on a clash). `(team_id, user_id)` is unique among non-deleted rows
- [ ] API under `/api/v1/teams/projects/{project_id}/teams`, binding the path project the same way as `uploads` (`_bind_project` via `resolve_scope`, a deleted project returns 404), until TD-122 binds projects generally:
  - `GET` list (with member count) and `GET /{team_id}` (with members): `V` on the project; members and counts apply the same "still an active project member" filter as the contract functions
  - `POST` create, `PATCH /{team_id}` rename or edit description, `DELETE /{team_id}` (soft delete, which also ends its memberships): `admin` capability (PER-09)
  - `PUT /{team_id}/members/{user_id}` (idempotent, 204) and `DELETE /{team_id}/members/{user_id}` (204): `admin` capability
  - `GET /mine`: the caller's own teams in the project (for the `my_teams` UI); declared before `/{team_id}` so it is not parsed as a UUID
- [ ] Access errors: a non-member of the project, a team in another project, and a cross-tenant id all return 404. A project member without `admin` who tries to write gets 403. Adding a user with no active membership on the project returns 422, with the same body for an unknown, other-tenant or non-member user (no user enumeration). No endpoint takes or returns a tenant id
- [ ] Every create, edit, delete, member add and member remove is written to the audit ledger on chain `team:<id>`, with the actor; an idempotent no-op (re-adding an existing member) writes no audit row
- [ ] Service contract in `teams/service.py`, documented in the module README as the public API (all inside the session's bound project, ignoring soft-deleted teams and memberships):
  - `user_team_ids(session, user_id) -> frozenset[UUID]`
  - `is_member(session, team_id, user_id) -> bool` (False for an unknown, deleted or other-project team)
  - `team_member_ids(session, team_id) -> frozenset[UUID]`
  - `team_exists(session, team_id) -> bool`, which consumers use to check a `team_id` before storing it
- [ ] Removing a user's project membership (T-0014) does not need a teams call: `user_team_ids` / `is_member` / `team_member_ids` only count users who still hold an active membership on the project, read through the core membership store (`app.core.auth`), not another module's tables
- [ ] Tests:
  - API: role matrix (PER-09 manages; a PER-14 or PER-15 member reads but cannot write: 403; a non-member gets 404)
  - Duplicate name returns 409. Adding the same member twice is a no-op. A deleted team disappears from list, `mine` and every contract function
  - Contract unit tests, including "user in team A of project P is not a member of a same-named team in project Q"
  - PostgreSQL test as `kerp_app`: a session bound to project A cannot read or write project B's team or member rows
  - Contract test with a test-only consumer model: a record with `visibility = team`, `team_id = X`, filtered with `team_id IN user_team_ids(...)`, is visible to a member of X and invisible to a project member outside X. This is the behaviour T-0020 builds on
- [ ] `docs/` updated where the module list or nav mapping names teams; `npm run gen:api` re-run and committed if the OpenAPI schema changed
- [ ] All quality gates green (see CLAUDE.md §Quality gates)
