## Goal
Jobs, mail and uploads must survive deploys, timeouts, crashes and client retries (audit items 8, 13, 14, 15, 16): a cancelled retryable job is requeued, a `running` row left by a hard crash is recovered, mail that never reached the queue is settled, one upload gets one scan, and a slow mail server cannot cause duplicate sends.

## Acceptance criteria
- [ ] Item 8: in the worker's cancel branch (`jobs/worker.py`), a retryable job (`ctx["job"].retryable`) is requeued via `_requeue`, like the `RetryLaterError` branch, not marked `failed`; the test at `test_jobs.py` (cancel → failed) is changed to assert the requeue, and a new test proves a scan cancelled during a deploy is retried and the clean file is accepted (not `verify_failed`)
- [ ] Item 14: `sweep` (`jobs/service.py`) also picks up `running` rows older than their timeout plus a margin that SAQ no longer knows, and requeues them (attempts left) or fails them; `create_single_run_job` then no longer returns a dead row (tests for both outcomes and for a running row SAQ still knows, which is left alone)
- [ ] Item 13: a scheduled job marks mail send-log rows still `queued` after the 24-hour payload lifetime `failed` with reason `payload_expired`, reusing `fail_unavailable` (`core/mail/service.py`, `jobs/mail.py`) (test); TD-336 resolved
- [ ] Item 15: `/complete` (`uploads/service.py`) locks the file row (`session.refresh(file, with_for_update=True)`) before the status check, so a client retry cannot create a second scan job; `verify_upload` does nothing if `file.job_id` is not the running job (tests: two concurrent `/complete` calls create one job (PostgreSQL); a stale job for the file is a no-op)
- [ ] Item 16: the SES client (`core/mail/transport.py`) uses `Config(connect_timeout=5, read_timeout=20, retries={"total_max_attempts": 2})` so one send attempt ends well inside the mail job timeout (test asserts the config)
- [ ] Module/README.md and docs updated (jobs, uploads and mail READMEs)
- [ ] All quality gates green (see CLAUDE.md §Quality gates)
