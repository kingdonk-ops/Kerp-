## Goal
Jobs, mail and uploads must survive deploys, timeouts, crashes and client retries (audit items 8, 13, 14, 15, 16): a cancelled retryable job is requeued, a `running` row left by a hard crash is recovered, mail that never reached the queue is settled, one upload gets one scan, and a slow mail server cannot cause duplicate sends.

## Acceptance criteria
- [x] Item 8: in the worker's cancel branch (`jobs/worker.py`), a retryable job (`ctx["job"].retryable`) is requeued via `_requeue`, like the `RetryLaterError` branch, not marked `failed`; the test at `test_jobs.py` (cancel → failed) is changed to assert the requeue, and a new test proves a scan cancelled during a deploy is retried and the clean file is accepted (not `verify_failed`)
- [x] Item 14: `sweep` (`jobs/service.py`) also picks up `running` rows older than their timeout plus a margin that SAQ no longer knows, and requeues them (attempts left) or fails them; `create_single_run_job` then no longer returns a dead row (tests for both outcomes and for a running row SAQ still knows, which is left alone)
- [x] Item 13: a scheduled job marks mail send-log rows still `queued` after the 24-hour payload lifetime `failed` with reason `payload_expired`, reusing `fail_unavailable` (`core/mail/service.py`, `jobs/mail.py`) (test); TD-336 resolved
- [x] Item 15: `/complete` (`uploads/service.py`) locks the file row (`session.refresh(file, with_for_update=True)`) before the status check, so a client retry cannot create a second scan job; `verify_upload` does nothing if `file.job_id` is not the running job (tests: two concurrent `/complete` calls create one job (PostgreSQL); a stale job for the file is a no-op)
- [x] Item 16: the SES client (`core/mail/transport.py`) uses `Config(connect_timeout=5, read_timeout=20, retries={"total_max_attempts": 2})` so one send attempt ends well inside the mail job timeout (test asserts the config)
- [x] Module/README.md and docs updated (jobs, uploads and mail READMEs)
- [x] All quality gates green (see CLAUDE.md §Quality gates)

- 2026-11-21 (implementer): Decisions and deviations:
  - Item 8: both cancel paths of `run_job` (cancelled in the handler, and cancelled while the start commit was in flight) go through `_settle_cancelled`: requeue (`Job timed out or was cancelled; it is retried`, kept in `message`) when `ctx["job"].retryable`, else fail with `Job timed out or was cancelled`. A `max_attempts=1` kind still fails on a cancel even though SAQ re-runs any job after a shutdown; the task asks for the `retryable` rule only. The old cancel test is now parametrised (retryable → `queued`, last attempt / no SAQ job → `failed`). Deploy test: `tests/test_uploads.py::test_a_scan_cancelled_by_a_deploy_is_retried_and_the_clean_file_is_accepted` (the sweep in between leaves the file alone; SAQ's retry publishes it).
  - Item 14: `RUNNING_MARGIN` = 5 min past the kind's `timeout_s` since `started_at`; `_recover` re-checks the row under a lock (still `running`, same `attempts`) before it writes. Requeued rows get `message` "The worker stopped while running the job; it is retried"; on the last attempt `error` is the worker's `Job timed out or was cancelled` (queue monitor class `Cancelled`; `service.TIMED_OUT` is now the single source, `worker.CANCELLED` points at it). `sweep` still returns only the re-enqueued ids. A row whose SAQ record SAQ itself already finished (failed/aborted) is recovered only after that record's TTL; documented in the jobs README.
  - Item 13: the cron `expire_mail_cron` (hourly at :41, batch worker, `registry.CRON_SCHEDULES`, so the queue monitor lists it) runs `core.mail.service.expire_queued` per deployment scope, which calls `fail_unavailable(..., "payload_expired")` per row. Cut-off: the 24 h payload TTL **plus one hour** (`scheduler.MAIL_EXPIRE_AFTER`), so a payload put shortly after the row's commit has surely expired. `fail_unavailable` now only changes a row still `queued` (row lock): before, a re-run of a sent mail's job (payload already deleted) overwrote `sent` with `failed` (test added). TD-336 asked for `not_enqueued`; the audit and this task say `payload_expired`, used here.
  - Item 15: `complete_upload` uses `session.refresh(file, with_for_update=True)` after the uploader check; `verify_upload` takes `job_id` (keyword, `None` for direct calls that are not a job) and the handler always passes `job.job_id`; a mismatch returns the status without touching storage, and the final locked write re-checks it. PostgreSQL proof: `test_two_concurrent_completes_create_one_verify_job` (dated note on TD-307).
  - Item 16: `SES_CONNECT_TIMEOUT_S`/`SES_READ_TIMEOUT_S`/`SES_MAX_ATTEMPTS` in `transport.py`; the test also asserts attempts x (connect + read) < `MAIL_TIMEOUT_S`.
