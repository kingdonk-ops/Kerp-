## Goal
ADR 0004 §4 and §6: when a default changes, projects are offered the change and accept it rule by
rule; admins can test a rule before enabling it.

## Acceptance criteria
- [x] When a system or tenant default set gains a new version, `GET .../rule-sets/{key}/updates` on a project returns a per-rule diff (new, changed, removed) against the project copy; nothing is applied automatically (ADR 0004 §4)
- [x] Accepting one rule from the diff applies only that rule, versions it and audit-ledgers it; a rule the project soft-deleted is shown as removed-by-project and not re-added (ADR 0004 §3–§4)
- [x] New projects created after the upgrade get the latest defaults (ADR 0004 §4)
- [x] Tenant report lists project rules that differ from the tenant defaults (ADR 0004 Consequences, risk mitigation)
- [x] "Try it": evaluating a rule against a supplied sample context returns the result and any finding without persisting a finding (ADR 0004 §6)
- [x] Module `README.md` and docs updated
- [x] All quality gates green (see CLAUDE.md §Quality gates)

## Notes

- Code in `backend/app/modules/validation/upgrades.py` (service.py was already ~1200 lines); it
  reuses the store's private helpers (`_reset_to`, `_parent_set`, lock guard, `_record_change`).
  `_reset_to` gained an `event` + extra ledger fields; `_message` takes key + params.
- Routes use the set **id**, like T-0034's (`.../rule-sets/{set}/updates`, `.../updates/{key}/accept`,
  `.../rules/{key}/try`, `GET /drift-report`), on both the project and the tenant layer (the tenant
  layer is offered system upgrades the same way, §4 "system or tenant default").
- Diff semantics: matched by `rule_key` (`origin_rule_key` only tells copied from own rules);
  `changed` only when the default's version is newer than `origin_version` and values differ;
  `removed_by_project` listed only once the default has changed since the copy (otherwise it
  would be a permanent "update"; once listed it stays until reset); a project-added rule
  under a new default's key is `key_in_use` (not acceptable). Accept writes `rule_update_accepted`.
  Tenant-layer accept keeps the two-person-unlock guard of reset (TD-268 logic).
- "New projects get the latest defaults": they copy the tenant layer at creation (already true);
  additionally `sync_system_defaults` now copies a system set shipped for the **first** time into
  the tenant layer, so new projects get brand-new sets. Changed sets are only offered.
- Drift report scope is RLS: projects in the caller's `allowed_project_ids` (portfolio personas).
- Try it never persists (asserted: finding count, set version and ledger unchanged); a draft is
  compiled first; regex kinds take `{"text": ...}` (20 000-char cap, 100 matches).
- Permissions and the interpretations above: spec-gap TD-281. Follow-ups: TD-278 (Try it on a
  recent real context), TD-279 (offer whole sets a running project lacks), TD-280 (frontend).
- `frontend/src/api` regenerated (`npm run gen:api`).
- 2026-11-15 review round 1 (PR #88, approved with suggestions): CEL "Try it" sample now capped
  at 32 nesting levels and 64 KiB compact JSON (as job payloads) → 422, tested; README/TD-281
  wording fixed (match by `rule_key`; `removed_by_<layer>` = default changed since the copy, stays
  until reset). Raised from the review: TD-287 (deleted own rule blocks a new default as
  `key_in_use`), TD-288 (`pending_updates` 409 without a parent default), TD-289 (drift report N+1).
