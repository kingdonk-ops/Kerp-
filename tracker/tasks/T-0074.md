## Goal
Saved views with `visibility = team` are shared with **one or more teams**, all linked to the
view's project, and are visible only in that project (register-views §3 team visibility, user
2026-11-13, TD-230/TD-244). Wire saved views to the teams service contract (T-0013) in place of
the fail-closed stub left by T-0020 (absorbs TD-242).

## Acceptance criteria
- [x] Additive migration: link table `oe_saved_view_team` (`saved_view_id`, `team_id`; `BaseRecordMixin`, project RLS like `oe_saved_view`; unique among non-deleted rows). Every existing `oe_saved_view.team_id` is copied into it. The `team_matches_visibility` CHECK is relaxed so new rows keep `team_id` NULL. The column stays, nullable and unused, documented as deprecated. Dropping it later is destructive and needs an ADR (raise a `later` TODO)
- [x] API: create/update takes `team_ids: list[UUID]`. It is required and non-empty when `visibility = team`, and must be empty otherwise (422). Every id must be in `teams.service.project_team_ids(project_id)` of the bound project, else 422 with the same body for unknown, other-project and other-tenant ids. Responses return `team_ids` (only teams still linked to the project)
- [x] Visibility: the router passes `teams.service.user_team_ids(session, user_id)` into the viewer. A team view is visible to its owner, the project's PER-09 and any member of a named team that is still linked to the project. A team that is deleted or unlinked stops seeing it. With no named team left, the view is visible to owner and PER-09 only (no error)
- [x] Who may share: any user who may create a view in the project may share it to any team linked to the project; they need not be a team member (planner default; the spec only restricts edit of shared views to owner or PER-09, which stays as T-0020 built it)
- [x] The saved_views module manifest depends on `teams`, and the `team` visibility returns 422 when the teams module is unavailable
- [x] No saved_views code reads teams tables (service contract only, CLAUDE.md §6)
- [x] Tests: shared to teams X and Y; a member of Y sees it, a project member in neither does not. Unlinking X from the project hides it from X-only members. A team id linked only to another project is rejected with 422. Migrated legacy `team_id` rows behave the same as link rows. Owner/PER-09 fallback when all teams are gone
- [x] Module/README.md and docs updated; `npm run gen:api` re-run and committed if the OpenAPI schema changed
- [x] All quality gates green (see CLAUDE.md §Quality gates)

  - Migration `0032`: `oe_saved_view_team` (`BaseRecordMixin`, `tenants` FK, FK to `oe_saved_view`, no FK to the teams table since it belongs to the teams module, partial unique `(saved_view_id, team_id)` over live rows, standard project RLS). Legacy `team_id` values are copied with RLS lifted (`NO FORCE` ... `FORCE`, as in `0012`). CHECK relaxed to `team_id IS NULL OR visibility = 'team'`. The column stays, deprecated: never read, cleared on the next write, NULL on new rows. Dropping it is TD-381 (`later`, needs an ADR). The downgrade writes the lowest live team back into `team_id` and makes a team view with no team left `private` (narrower, logged).
  - Decisions (planner defaults where the spec is silent): leaving `visibility = team` drops the view's teams, and coming back needs `team_ids` again. Repeated ids count once. Sharing needs `C` but not team membership. PER-09 sees every team view. The API replaces `team_id` with `team_ids` (request and response). Deleting a view retires its link rows. Visibility relies on the contract: `user_team_ids` returns only teams linked to the bound project, so unlinked or deleted teams stop matching with no extra lookup. Responses filter `team_ids` through `project_team_ids`.
  - "Teams module unavailable" means not in the app's registry, or `is_enabled` false for the project (teams is not toggleable, so in practice only tests hit it). The caller then has no teams and `team` visibility answers 422 `team views need the teams module`.
