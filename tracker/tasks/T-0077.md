## Goal
Product-owner decision 2026-11-14: external users sign in with e-mail + password and reset it themselves by e-mail (diff §4.2 *Local passwords*, *Self-service password reset*). One password policy for every password set.

## Acceptance criteria
- [x] Core password policy function (public core-auth API, with a core set-password function, so modules such as T-0059 never write the users table) used by every password set (reset, first password at invite acceptance in T-0059, change, admin-created accounts): minimum `KERP_PASSWORD_MIN_LENGTH` (default 8, product owner 2026-11-14; config refuses < 8), accepted up to 256 characters, NFKC-normalised before hashing, Unicode and spaces allowed, no composition rules, no expiry; rejects passwords on a bundled common/compromised blocklist and context words (e-mail, its local part, `kerp`, deployment name); optional breached-password range lookup behind `KERP_PASSWORD_BREACH_CHECK` (default off; lookup failure never blocks); rejection codes `PASSWORD_TOO_SHORT`, `PASSWORD_TOO_COMMON`, translated
- [x] `POST /api/v1/auth/password-reset/request` (e-mail) returns the same 202 body, status and headers for unknown, deactivated and active accounts; delivery is an enqueued T-0058 send (never synchronous) and every path does equal work inside the request (equal hash/store calls or the store write deferred with the send); for an active account (with or without a password) the e-mail carries `/reset-password#<token>`
- [x] Reset token: ≥ 256-bit random, stored only as a hash, single-use, expires after `KERP_PASSWORD_RESET_TTL_MINUTES` (default 60), a new request invalidates earlier tokens; logs and Sentry scrub `token` / `new_password` fields
- [x] `POST /api/v1/auth/password-reset/confirm` (token, new password): enforces the policy, sets the scrypt hash, **revokes every session and refresh token of the user** (all devices; enrolment and PIN kept), applies T-0037's same-second password-change token rejection, also invalidates the user's outstanding magic links and other reset tokens; does not sign in; sends a "your password was changed" notice; PIN unlock on a device that is already offline keeps working within the offline grace (diff §4.2), revocation applies at its next server contact; an invalid, used or expired token gets one neutral 410
- [x] Rate limits: request per e-mail address (the same per-mailbox cap as magic links, keyed by tenant + e-mail as decided by the product owner 2026-11-15, T-0068 / TD-224) and per client; confirm attempts per token limited; request, confirm and refusals audited (no token)
- [x] Tests: neutral responses (unknown, deactivated, active) with spies showing no synchronous send on any path; token single use under concurrency (two confirms: one 200, one 410); expiry; earlier token invalidated by a new request; all sessions revoked after confirm (old refresh token refused); policy cases (7 vs 8 chars at the default, a raised `KERP_PASSWORD_MIN_LENGTH` honoured, config < 8 refused at start-up, blocklisted, e-mail as password, Unicode NFKC); account without a password sets its first password through reset
- [x] Module `README.md` (core auth) and deploy docs (new settings) updated
- [x] All quality gates green (see CLAUDE.md §Quality gates)

(The 15-character minimum mentioned here was superseded the same day, see below.)

- 2026-11-18 (implementer): **Where things are.** Policy: `app/core/auth/password_policy.py` + bundled `data/common_passwords.txt`; public API `check_password` and `service.set_user_password` / `set_password` / `create_user(password=...)` (T-0059 calls `set_user_password`, never the users table). Reset: `password_reset.py` + `password_reset_router.py`. Scrubbing: `app/core/logging.py`. Docs: core auth README (*Passwords*, *Self-service password reset*), `docs/deploy/passwords.md`.
- 2026-11-18 (implementer): **Decisions.** (1) Reset tokens live in the auth store (Redis; SHA-256 only, TTL = link lifetime), like magic links: no new table or migration. One live token per account through a `pwreset:user:<tid>:<uid>` pointer, so a newer request always wins, even when two requests race; the token is taken with `GETDEL` (single use under concurrency). (2) The request does only the two rate-limit counts and schedules one identical job; lookup, token, store writes, mail and audit run after the response (the T-0057 pattern). (3) Session revocation is `password_changed_at` (T-0037 / T-0061, exact to the microsecond); magic links now carry `iat` and are refused when older than the password change. (4) Sign-in checks the NFKC form of the typed password and, if different, the text as typed, so passwords stored before the policy keep working. (5) A refused password answers 422 with the code and keeps the link; a dead link is always the same 410. (6) "Translated": the API returns codes plus an English `detail`; the translated texts come with the screens (T-0078, TD-365).
- 2026-11-18 (implementer): **Deviations / follow-ups.** TD-361 (spec-gap: per-mailbox cap on its own counter, not shared with magic links), TD-362 (spec-gap: `PASSWORD_TOO_LONG`, context-word matching, audit of unknown-address and throttled requests, rate-limit numbers), TD-363 (no Sentry in the codebase yet: only the `before_send` hook exists), TD-364 (larger blocklist), TD-365 (frontend translations, policy in `/auth/config`), TD-366 (change-password endpoint and admin-set passwords must use `set_user_password`), TD-376 (risk: the deferred half of the request runs as a background task on the same connection; timing on a kept-alive connection not measured, applies to magic links too). The API changed: `frontend/src/api/` regenerated with `npm run gen:api`.
- 2026-11-19 (implementer, PR #125 review round 1): **Password change vs. token issuing is ordered by a row lock.** `service.lock_user` (`FOR NO KEY UPDATE`; on SQLite a no-op write takes the write lock). `apply_checked_password` (confirm, `set_password`, `set_user_password`) stamps under it; `start_session` re-reads under it and, for password and magic-link sign-ins (`credential_bound=True`), refuses when the account or its password changed while the credential was checked; `_rotate` (refresh, PIN unlock) runs `load_active_user(for_update=True)`. SSO sign-ins take the lock but are not refused on a password change: their proof is not the password, the lock alone orders them, and `sso_router.py` stays untouched (T-0052 edits it). Confirm also refuses (410) an account deactivated while it ran. Tests: login, magic link and refresh racing a confirm, and a login that issued first (confirm waits, tokens revoked), on SQLite and PostgreSQL. Also folded in: free-text scrub of `Bearer <token>` and `password_hash`; TD-362 (audit of invalid-token confirms) and TD-366 (reset link survives other password sets) extended.
