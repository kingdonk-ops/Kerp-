## Goal
Product-owner decision 2026-11-14: external users sign in with e-mail + password and reset it themselves by e-mail (diff §4.2 *Local passwords*, *Self-service password reset*). One password policy for every password set.

## Acceptance criteria
- [ ] Core password policy function used by every password set (reset, first password at invite acceptance in T-0059, change, admin-created accounts): minimum `KERP_PASSWORD_MIN_LENGTH` (default 15, config refuses < 8), accepted up to 256 characters, NFKC-normalised before hashing, Unicode and spaces allowed, no composition rules, no expiry; rejects passwords on a bundled common/compromised blocklist and context words (e-mail, its local part, `kerp`, deployment name); optional breached-password range lookup behind `KERP_PASSWORD_BREACH_CHECK` (default off; lookup failure never blocks); rejection codes `PASSWORD_TOO_SHORT`, `PASSWORD_TOO_COMMON`, translated
- [ ] `POST /api/v1/auth/password-reset/request` (e-mail) returns the same 202 body, status and headers for unknown, deactivated and active accounts; delivery is an enqueued T-0058 send (never synchronous) and every path does equal work inside the request (equal hash/store calls or the store write deferred with the send); for an active account (with or without a password) the e-mail carries `/reset-password#<token>`
- [ ] Reset token: ≥ 256-bit random, stored only as a hash, single-use, expires after `KERP_PASSWORD_RESET_TTL_MINUTES` (default 60), a new request invalidates earlier tokens; logs and Sentry scrub `token` / `new_password` fields
- [ ] `POST /api/v1/auth/password-reset/confirm` (token, new password): enforces the policy, sets the scrypt hash, **revokes every session and refresh token of the user** (all devices; enrolment and PIN kept), applies T-0037's same-second password-change token rejection, does not sign in; sends a "your password was changed" notice; an invalid, used or expired token gets one neutral 410
- [ ] Rate limits: request per e-mail address (same mailbox-flood cap as magic links, T-0068 / TD-224) and per client; confirm attempts per token limited; request, confirm and refusals audited (no token)
- [ ] Tests: neutral responses (unknown, deactivated, active) with spies showing no synchronous send on any path; token single use under concurrency (two confirms: one 200, one 410); expiry; earlier token invalidated by a new request; all sessions revoked after confirm (old refresh token refused); policy cases (14 vs 15 chars, blocklisted, e-mail as password, Unicode NFKC); account without a password sets its first password through reset
- [ ] Module `README.md` (core auth) and deploy docs (new settings) updated
- [ ] All quality gates green (see CLAUDE.md §Quality gates)
