## Goal
Product-owner decision 2026-11-14 (TD-136; diff §4.2 *Magic links for Field Workers only*): only users with a PER-14 Field Worker grant on at least one project (or a valid pending invite naming PER-14) can sign in by magic link; everyone else uses password or Entra ID SSO, without the API revealing which accounts or personas exist.

## Acceptance criteria
- [ ] Eligibility = an active account with at least one effective PER-14 grant (direct or team-derived, T-0073) on a project that is not soft-deleted, read in core auth with `load_grants` (`app/core/auth/access.py`; after T-0073 it returns direct plus team-derived grants and skips soft-deleted projects and deactivated users) or another core-level helper, never through a module service: magic-link sign-in lives in core auth and **core never imports `app.modules`**. The check sits behind one core eligibility function with a **registration extension point** (e.g. a registry of additional eligibility providers, empty by default) that the admin module registers at start-up in T-0052 for the invite branch (a valid pending invite naming PER-14 for the account's e-mail); core reads no module table
- [ ] `POST /api/v1/auth/magic-link` for an ineligible or deactivated user returns the **same 202 body, status and headers** as for an unknown e-mail and an eligible user; no usable magic-link record is stored and no mail is sent (fake mail transport asserts nothing queued); the existing request lockout / mailbox-flood cap (T-0068, TD-224) applies unchanged
- [ ] The refusal is logged and audited with reason `magic_link_not_field_worker` (no token, no e-mail in plain logs beyond what the audit ledger already records)
- [ ] Redeem re-checks eligibility: a link issued while the user held PER-14 is refused with the neutral invalid-link error once the last PER-14 grant was removed (or the project soft-deleted) before redeem
- [ ] No timing oracle (diff §4.2): link **delivery moves off the request path** (SAQ interactive-queue job, or a post-response task) so the 202 never waits for the mail transport; inside the request every path (unknown, inactive, ineligible, eligible) does equal work: either the magic-link store write moves into the job too, or the unknown/inactive/ineligible paths do an equal dummy write. Tests (spies, not wall-clock): on every path the request handler never calls the mail sender synchronously; every path performs the same store/hash calls; the eligible path enqueues exactly one delivery job, the others none (or an indistinguishable no-op job). The refusal audit write is also deferred or done equally on every path
- [ ] Tests: PER-14 direct grant → link issued; PER-14 only via a team link → issued; PER-14 only on a soft-deleted project → neutral 202, nothing issued; other persona only (e.g. PER-06) → neutral 202, nothing issued; no membership at all → neutral 202; PER-14 removed between request and redeem → redeem refused; deactivated user holding PER-14 → neutral 202, nothing issued; user deactivated between request and redeem → redeem refused; core auth has no import of `app.modules` (import-boundary test or lint rule)
- [ ] Module `README.md` (identity) documents the rule and the neutral response; docs updated
- [ ] All quality gates green (see CLAUDE.md §Quality gates)
