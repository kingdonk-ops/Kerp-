## Goal
The invite link in the SPA (diff §4.1 Invites): join confirmation for signed-in users, token carried through sign-in for everyone else, then straight into the project.

Also (absorbed from T-0078): the password screens of the invite and self-service reset flows — create your password at invite acceptance (T-0059), forgot password and reset password (T-0077). Both halves are the same invite/sign-in journey on merged backends.

## Acceptance criteria
- [x] Route `/invite` reads the token from the URL fragment (`/invite#<token>`), removes it from the address bar and sends it only in POST bodies; the route is served with `Referrer-Policy: no-referrer`. Signed in → preview (T-0052) and a one-click **"Join project"** confirmation; accepting opens the project and makes it the remembered project (T-0042)
- [x] Not signed in → the sign-in screen with the token kept only for this flow (memory / `sessionStorage`, cleared after use or failure, never in `localStorage` or logs) and passed as `invite_token` to password login, the magic-link request and the SSO start (T-0055); on `joined_project_id` the app opens that project and skips the lobby
- [x] The sign-in screen reached from an invite is the normal one (T-0055: "Sign in with Microsoft" primary when enabled, password secondary); the magic-link request is offered too, but only PER-14 invites get a link (server-side, neutral response; T-0052, T-0057), so the screen tells the user to use their password (or Microsoft, company staff only) if no e-mail arrives. A brand-new invitee without credentials gets the "Create your password" / "Send me an e-mail to set my password" screens of T-0078 instead of the sign-in form (diff §4.1; externals never use SSO)
- [x] Wrong user, expired, revoked or used invites show a neutral message with a link to the lobby (and sign-out for the wrong-user case)
- [x] Pending invites panel on the project's members screen (PER-09 of the project or System admin; the members screen is T-0026, which this task depends on, and the panel is added to it): lists the open invites from the T-0052 list endpoint (pending and expired never accepted: e-mail, persona(s), `expires_at`, `last_sent_at`; Resend disabled until `resend_available_at`) with **Resend** and Revoke (T-0052); Resend asks for confirmation ("the previous link stops working"), then shows the new copyable link once (`invite_token` only) and states that a new e-mail was sent; a 429 shows when re-sending is possible again; accepted and revoked invites offer no Resend
- [ ] All strings through `t()`; component tests (including Resend: confirmation, new link shown once, 429 message) and one e2e journey (PER-09 creates an invite → an existing user follows the link and signs in → lands in the project; the brand-new external journey with first-password set is T-0078's), synthetic data only
- [x] Module `README.md` and docs updated
- [ ] `/invite#<invite_token>.<setup_token>` (T-0053 route): when `setup-preview` says a first password can be set, show "Create your password" (e-mail shown read-only, password + confirm, live length hint from the server policy, show/hide toggle, paste allowed) as the primary action; submit `accept-with-password`; on success open `joined_project_id`; policy errors shown translated; no Microsoft button on this screen — from T-0078
- [x] Copied link (no `setup_token`) for an account without credentials → "Send me an e-mail to set my password" (T-0077 request), keeping the `invite_token` for the carry-through after sign-in — from T-0078
- [x] Sign-in screen: "Forgot password?" link → e-mail form → the same neutral confirmation for every address; `/reset-password#<token>` reads the token from the fragment, removes it from the address bar (no referrer), sets a new password, then routes to sign-in with a translated success message — from T-0078
- [ ] Same screens in the Capacitor Android build (App Link `https://<deployment>/invite` and `/reset-password`, verified via `assetlinks.json`; T-0143) — from T-0078
- [ ] All strings through `t()`; component tests with a mocked server; e2e journeys against the fake mail transport: (1) PER-09 invites a brand-new external user → invite e-mail → create password → lands in the project; (2) forgot password → e-mail → reset → old session refused → sign in with the new password — from T-0078
- [x] All quality gates green (see CLAUDE.md §Quality gates)

Decisions:
  - **Token storage:** the tab's `sessionStorage` (`kerp.invite.pending`, new optional `AppServices.session`), written once from the fragment, cleared on use / refusal, on the SSO return and when `/login` is opened outside the invite flow (router state `{ invite: true }` marks the flow). Kept after a **wrong-user** refusal only so "Sign out" leads into the invite sign-in as the invited address; the lobby link clears it. The reset token stays in component memory. The URL is replaced without the fragment before anything is sent.
  - **Referrer:** the app-wide `<meta name="referrer" content="no-referrer">` covers `/invite` and `/reset-password`; an HTTP header from the SPA host waits for the SPA hosting (TD-334).
  - **Copied link:** the client cannot tell whether the account has credentials, so the invite sign-in always offers "Send me an e-mail to set my password" (the neutral reset request). The pending invite survives only within the tab (TD-461).
  - **Magic link:** requested from the invite sign-in only (the general request and the SPA landing of the link are TD-147).
  - `INVITE_CONFLICT` (accepted in parallel) shows the "used" message; any unknown code the generic one; a server `detail` is never rendered.
  - **Not ticked:** "Create your password" — the e-mail cannot be shown read-only and the length hint shows the minimum only after a refusal, because `setup-preview` returns neither (TD-460, TD-365); everything else of that criterion is built. Android App Links: TD-458 (needs T-0141/T-0143). Playwright journeys: TD-459 (needs T-0027, as TD-446/TD-448); the same journeys run as component tests with a mocked server.
  - The panel overlaps T-0331's "open invites listed / re-sent / revoked": T-0331 should reuse `PendingInvites`.
