## Goal
Remove the copied helpers and dead code listed in audit item 20, after the other audit tasks have landed on the same branch, so each helper has one copy and one behaviour.

- [x] One SHA-256 hex helper replaces the copies in `field.py`, `password_reset.py`, `sso.py` and `devices.py` (same output; existing tests pass unchanged)

## Notes
- 2026-11-21 (planner): Created from the 2026-11-21 codebase audit; runs last in the one PR (T-0341..T-0349) so the clean-up sees the code the other tasks change.
- 2026-11-22 (implementer): Done on top of T-0341..T-0348 (integration head b8fba1e); every duplicate re-located by grep.
  - **SHA-256:** `app/core/digest.py::sha256_hex`. `field.magic_link_digest`, `password_reset.reset_digest`, `sso.digest`, `devices.wipe_secret_digest` and the identical fifth copy `admin.invites.token_digest` are now aliases of it (public names kept, so callers and tests are unchanged; `test_core_helpers.py` pins identity and test vectors). The inline compositions over normalised values (lockout subject, mail address, admin e-mail) are left: TD-569.
  - **Session re-binding:** `app/core/tenancy/rebind.py` (`SessionRebinding`, `project_binding`); `invites._SystemPath` is a thin subclass that only sets the target. Divergences resolved to the safer side, each pinned in `tests/test_tenancy_rebind.py`: (1) a failing closing flush still restores the caller's scope and re-attaches the held objects (validation and access_requests left the session in the project scope); (2) a failed restore on a *good* transaction propagates (access_requests swallowed it, leaving the connection in the target scope while the session claimed the caller's); on a failed transaction it falls back to `session.info` (the rollback makes the connection agree); (3) `site_node_ids` is kept, never cleared (access_requests cleared it; a tenant-level context carries `None` from `resolve_scope` anyway, so no current caller changes). `project_binding` now requires a tenant-level session, as both callers already did.
  - **`_aware`/`_utc`:** seven copies found (five `_aware`/`_utc` functions plus the access-request schema validator and the device schema validator) → `app/core/timestamps.py::aware_utc`. Test-local copies in `tests/` are untouched.
  - **503:** one handler, `app/core/auth/revocation.py::revocation_unavailable_handler`, registered in `app.main`. Body chosen: `{"detail": "Authentication temporarily unavailable"}` (the `AUTH_UNAVAILABLE` text router.py, password_reset_router.py, bearer.py, device_api.py and invites_router.py already used); dropped: SSO's `"Authentication unavailable"`. Nothing in `frontend/`, `e2e/` or the tests depended on either text (grep); the SSO, password-reset, core-auth and device tests now assert the body. All per-endpoint `except RevocationUnavailableError → HTTPException(503)` mappings (router ×6, sso_router ×4, password_reset_router ×2, bearer, device_api ×2, invites_router) are gone; `AUTH_UNAVAILABLE` moved from `bearer.py` to `revocation.py`. `admin/system_router._unavailable(what)` ("… is not configured") is a different thing (no database / no queue monitor) and stays. Behaviour changes, all intended: device enrol/revoke and `resolve_request_device` 500 → 503 (TD-290; the revoke test asserted 500 "pending TD-290" and now asserts 503); the SSO body text.
  - **TD-525:** fixed with `redis_unavailable_handler`: `redis.ConnectionError`/`redis.TimeoutError` that reach the app are 503 `{"detail": "Service temporarily unavailable"}` (logged as a warning, never the driver message); any other Redis error stays 500 (a bug). Every request path checked already wraps or catches Redis (revocation store, settings cache, queue monitor, abort); post-response work (job dispatch, mail payloads) never reaches a request. Tests: `tests/test_service_unavailable.py`.
  - **Tenant scope:** `app/core/tenancy/rls.py::tenant_level_context(session, what)` (core, so no module reaches into another); the jobs (×2) and uploads copies use it with identical error messages. Ten more copies of the same guard elsewhere: TD-568.
  - **Dead code:** no production code read `current_tenant_id`/`current_project_id`/`current_user_id` (grep over `backend/`, `scripts/`); the only readers were tests asserting that they were set. Deleted with their only writer `use_tenancy` (`db.unit_of_work`, `jobs/worker.py`) and the sets in `deps.get_principal` (`current_device_id` stays: the audit ledger reads it). Tests adjusted: `test_tenancy.py` loses `test_use_tenancy_sets_and_resets_context_vars`; `test_auth_api.py`'s `/_whoami` drops the two context-var fields; `test_jobs.py`'s echo handler reports `job.tenancy.tenant_id`; `test_rls_bypass.py` (Redis-only) drops the ambient `use_tenancy(CTX_C)` and its context-var assertion (the job-scope checks on `JobContext.tenancy`, PostgreSQL settings and visible rows stay). `_VALIDATION_KEYS` assigned once.
