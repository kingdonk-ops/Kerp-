## Goal
Users find lobby-visible projects (internal staff only) or enter a project code, as the entry point to an access request (diff §4.1). The request lifecycle itself is T-0050.

## Acceptance criteria
- [x] Projects gain `visible_in_lobby` (default false, additive migration); only PER-09 of that project (or a `system_admin`) can change it (master §4.1 amendment)
- [x] `GET /api/v1/lobby/projects` returns id, code and name of lobby-visible projects only, and only to internal users (`is_internal`, T-0049; product owner, 2026-11-14); an external user gets 403 with `code: LOBBY_INTERNAL_ONLY` and no project data; it reads through a narrow path (security-definer function or security-barrier view) that itself returns no rows for a non-internal caller (defence in depth, edge §6 amendments), and the membership-based `projects` policy is not widened; PostgreSQL test as `kerp_app` shows a non-member still cannot fetch the full project row (edge §6 amendments)
- [x] `GET /api/v1/lobby/projects/by-code/{code}` returns the one project with that exact code (id, code, name) whether or not it is lobby-visible, to internal and external users alike; unknown code → 404; rate-limited per user and deployment-wide, per-client-IP limits follow TD-138 (user, 2026-11-13; TD-202: a code never grants access by itself); the response carries a short-lived **lookup ticket** (signed, bound to user and project, 15 minutes, planner default) that T-0050 requires on a user's **first** request for a project when the user is external or the project is not lobby-visible; re-requests after an earlier rejected or withdrawn request need none (diff §4.1)
- [x] Both endpoints mark projects the caller already belongs to (effective access, incl. team-derived grants once T-0073 lands) so the UI can open them instead of offering a request
- [x] Tests: internal user lists lobby-visible projects only; external user gets 403 on the list but finds a non-visible project by code; a code lookup never creates a membership
- [x] Module `README.md` and docs updated
- [x] All quality gates green (see CLAUDE.md §Quality gates)

- 2026-11-16 (implementer): Built.
  - **New `lobby` module** (no table, platform, depends on `projects`). The module loader mounts each module at `/api/v1/<name>`, so `/api/v1/lobby/...` needs a module named `lobby`; `admin` was not usable for that path. T-0050 can put `access_requests` here.
  - **`visible_in_lobby`** (migration `0021`, additive, default false) is changed through `PUT /api/v1/projects/{id}/lobby` (PER-09 of the project or a System admin; non-member 404, member without PER-09 403; audited as an update). `PATCH /projects/{id}` keeps its PER-09-only rule and refuses the field (422). `ProjectRead` now returns it.
  - **Narrow read**: `SECURITY DEFINER` functions `kerp_lobby_projects()` and `kerp_lobby_project_by_code(text)` return id, code, name only. They check the caller themselves against `auth_user` (bound tenant and user, active; internal for the list). The membership policy on `oe_projects_project` is unchanged. In CI the definer is `kerp_app`, which `FORCE` RLS also binds (TD-056). So each function sets `app.is_system_admin` for its own read only and puts the caller's value back before it returns. The PG test checks that the flag is not left set and that the full row stays hidden before and after the call. `EXECUTE` is granted only to the migrating role; the split-role deploy step is TD-311. SQLite runs the same rule as a Core query past the ORM scope (`projects.service`).
  - **Lookup ticket**: an EdDSA/RS256 JWT signed with the deployment token keys. It carries `type: lobby_lookup`, `typ: kerp-lookup+jwt` and the claims `sub`, `tid`, `pid`, and it lasts 15 min. It is checked against the token service's clock. It is never accepted as an access token, and an access token is never accepted as a ticket (both tested). `lobby.service.verify_lookup_ticket` is the entry point for T-0050. A ticket is returned on every hit, including for projects the caller is already a member of.
  - **Rate limits** (planner defaults, `ProgressiveLockout` on the shared auth store; every lookup counts, hit or miss): 30 per user, then 1 min doubling to 15 min, per hour. Deployment-wide: 1000 per hour with the same escalation. The user limit is checked first, so a locked user does not spend the deployment budget. The per-client-IP limit stays with TD-138.
  - Code match is exact and case-sensitive (codes are unique per tenant as stored). A deleted project's code is 404. The list is sorted by name, then code. `member` comes from `CallerGrants`, so team-derived grants are included automatically once T-0073 writes them to the membership store (ADR 0008).
  - The OpenAPI diff includes a reorder: adding `lobby` changes the loader's dependency mount order, so `jobs` paths moved. Apart from the reorder, the only changes are the 3 new paths, 4 new schemas and `ProjectRead.visible_in_lobby`.
