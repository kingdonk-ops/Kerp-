## Goal
Users without a project find lobby-visible projects or enter a project code, and ask that project's PER-09 holders for access (diff §4.1).

## Acceptance criteria
- [ ] Projects gain `visible_in_lobby` (default false, additive migration); only PER-09 of that project (or a `system_admin`) can change it (master §4.1 amendment)
- [ ] `GET /api/v1/lobby/projects` returns id, code and name of lobby-visible projects only, to any signed-in user of the deployment; it reads through a narrow path (security-definer function or security-barrier view) and the membership-based `projects` policy is not widened; PostgreSQL test as `kerp_app` shows a non-member still cannot fetch the full project row (edge §6 amendments)
- [ ] `GET /api/v1/lobby/projects/by-code/{code}` returns the one project with that exact code (id, code, name) whether or not it is lobby-visible; unknown code → 404; rate-limited per user (user, 2026-11-13; TD-202: a code never grants access by itself)
- [ ] `POST /api/v1/access-requests` (project id, optional message) creates a pending request; one open request per user per project (409); requests for a project the user already belongs to → 409; the requester can list and withdraw their own
- [ ] The project's PER-09 holders are notified in-app (T-0019) and can list, approve (choosing persona(s) and site scope) or reject; approval creates the membership; a non-admin gets 403; the requester is notified of the outcome
- [ ] Request, decision, decider and resulting membership are written to the audit ledger
- [ ] Tables use `BaseRecordMixin` and RLS; access requests are visible to the requester, the project's PER-09 holders and `system_admin`s only
- [ ] Module `README.md` and docs updated
- [ ] All quality gates green (see CLAUDE.md §Quality gates)
