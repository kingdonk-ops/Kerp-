## Notes

- 2026-11-09: ADR 0001: rewrite — Inspection-ERP core/auth/ratelimit.py is in-memory per-worker; KERP needs Redis-backed progressive lockout.
- 2026-11-11 (implementer): Built in `backend/app/core/auth/` (where T-0008 put auth), new `field.py` + `lockout.py`; no DB migration (all state is session-scoped Redis entries). Interpretation of "PIN as a local session unlock only" (spec-gap TD-135): a magic link (15 min, single use, only its SHA-256 stored, `GETDEL`) starts a new session on the device and sets that session's PIN (scrypt hash in Redis under `pin:<sid>`, set before any refresh token is registered). `/auth/refresh` refuses PIN-gated sessions without consuming the token; only `/auth/pin/unlock` (refresh token + PIN) rotates them, and the PIN entry is re-armed with the refresh TTL + 1 day. A PIN alone never starts or refreshes a session; a contract test asserts every request schema with `pin` also requires `token` or `refresh_token`. Weak PINs (repeated digit, straight runs) are refused with 422 before the link is spent.
- 2026-11-11 (implementer): Progressive lockout in Redis (shared by all workers), attempt counted before the secret is checked so parallel requests cannot race past it; locked attempts are refused with 429 + `Retry-After` without checking the secret. PIN: 4 immediate tries, then 30 s doubling to 15 min, 10th wrong PIN revokes the session (new magic link needed). Also applied to password login per tenant+email (ADR 0001 assigns the login-throttle rewrite to T-0009; covers TD-123 except the IP key, see TD-138) and to magic-link requests per tenant+email. Unknown addresses lock exactly like real ones (no enumeration); subjects are hashed in Redis keys.
- 2026-11-11 (implementer): Follow-ups: persona restriction of magic links after T-0010 (TD-136); field-worker sign-in UI (TD-137); IP-based throttling (TD-138). E-mail delivery is TD-084: development logs the link, production logs "not delivered" without the token. Coordinator: TD-123 can be resolved by this PR (IP part moved to TD-138).
- 2026-11-11 (implementer, review round 1): PIN failure counter window is now the refresh lifetime + `PIN_TTL_MARGIN` (default policy 91 d), so the 10-guess cap holds for the whole session, not per 24 h; Redis `count_failure` runs SET NX EX + INCR in one MULTI/EXEC so a counter can never lose its TTL; boundary tests for the 9th/10th wrong PIN and a >24 h gap; lockout wording fixed ("N immediate tries"); size set to M. Risk TD-142: PIN gate fails open if Redis evicts `pin:<sid>`.
