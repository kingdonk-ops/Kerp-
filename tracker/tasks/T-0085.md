## Goal
A System admin must not be able to deactivate their own account. T-0331 hides Deactivate on the caller's own row, but the client never asserts authority: `admin.service.update_user` refuses only the last active System admin (TD-274). Enforce the rule on the server and show a clear message if the screen ever sends it (stale list, second tab).

## Acceptance criteria
- [x] `PATCH /api/v1/admin/users/{id}` with `{"is_active": false}` where `id` is the caller answers 409 `{"code": "CANNOT_DEACTIVATE_SELF", "detail": ...}` and writes nothing, also when other active System admins exist (test); the last-admin 409 is unchanged (existing test kept green)
- [x] Deactivating another user, renaming oneself and reactivating are unchanged (tests)
- [x] The refusal is audited: one ledger entry on the `admin-user:{id}` stream with `{"action": "update_refused", "reason": "self_deactivation"}` that survives the refused request's rollback (test reads the ledger after the 409)
- [x] The check lives in `admin.service.update_user` (one place; the router only maps the error), so any future caller of the service gets it
- [x] Admin -> Users maps 409 `CANNOT_DEACTIVATE_SELF` to an i18n message (`admin.users.*`, via `t()`) and re-reads the list; vitest covers the mapping; the own-row button stays hidden (existing test green)
- [x] OpenAPI documents the 409 code; `npm run gen:api` re-run and committed if the schema changed
- [ ] TD-463 resolved by this task
- [x] Module/README.md and docs updated (`backend/app/modules/admin/README.md`, `frontend/src/admin/README.md`)

- 2026-11-21 (planner): from TD-463 (raised by T-0331, review of PR #154 asked to schedule it with the next admin-backend task). Refusal-audit pattern: write the ledger entry in its own unit of work, as the admin module's other audited refusals do; if none exists yet, add the smallest helper in `admin/service.py`.
- 2026-11-21 (implementer): order of checks in `update_user`: the last-admin check runs first, then the self check. The last active System admin deactivating themselves still gets the unchanged T-0211 409 (plain `detail`, no `code`, nothing audited: `test_the_last_active_system_admin_cannot_deactivate_themselves` asserts an empty chain); every other self-deactivation gets `CANNOT_DEACTIVATE_SELF`. Reactivating or renaming oneself is untouched; `is_active: false` on an already inactive account is not a deactivation and is not refused.
- 2026-11-21 (implementer): no admin refusal was audited in its own unit of work yet (invite refusals are flushed in the request's transaction, which commits because the router returns a response). Added `_append_refusal` in `admin/service.py`: it writes on the `Database`'s side-write pool (the pattern of `validation._persist_findings`), bound to the caller's tenancy, before the request writes anything. The router rolls the request session back and answers the `UserUpdateRefusal` body `{detail, code}`; the last-admin 409 stays an `HTTPException`. OpenAPI documents the 409 with `UserUpdateRefusal`; its description names both variants.
