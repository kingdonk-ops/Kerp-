## Goal
TD-120 3a and TD-184 1a: System admins appoint Project Admins (the tenant-level `create_projects` grant); only Project Admins create projects, and the creator is PER-09 on the new project.

## Acceptance criteria
- [x] `GET/POST/DELETE /api/v1/admin/grants` lists, grants and revokes `system_admin` and `create_projects` for a user; only a `system_admin` may call it (else 403); the last `system_admin` cannot be revoked (409) (diff §4.1)
- [x] `POST /api/v1/projects` needs `create_projects` (else 403), replacing the interim 'admin on any project' rule of T-0012 (TD-184)
- [x] Creating a project grants the creator a PER-09 membership on it in the same transaction; a test creates a project and immediately reads and edits it as the creator
- [x] Revoking `create_projects` keeps the user's existing PER-09 memberships
- [x] `load_grants` and the allowed project list ignore memberships on soft-deleted projects; a test shows a PER-09 whose only project was deleted has no admin capability (TD-184)
- [x] Neither grant confers hold release, sign-off, `A` or `S`: a test shows a `system_admin` + `create_projects` user without a qualified persona is refused an `A`-capability check on a project (diff §4.1, edge §5 Admins)
- [x] Grant and revoke are written to the audit ledger
- [x] Module `README.md` and docs updated
- [x] All quality gates green (see CLAUDE.md §Quality gates)

## Notes
- 2026-11-13 (planner): The grants table itself is created in T-0014 (needed there for the System admin RLS exemption); this task adds the appointment API and the creation rule.
- 2026-11-15 (implementer): API `GET /api/v1/admin/grants[?user_id=]`, `POST /api/v1/admin/grants` `{user_id, grant}` (201; 200 if already held; 404 unknown user), `DELETE /api/v1/admin/grants/{user_id}/{grant}` (204; 404 not held; 409 last `system_admin`); all `system_admin` only. `service.revoke` refuses non-`system_admin` sessions up front and locks the live rows of the kind (`FOR UPDATE`), so two admins revoking each other at once cannot both pass the last-admin check (PostgreSQL test in `test_rls_admin.py`).
- 2026-11-15 (implementer): `POST /api/v1/projects` reads the caller's own grants through the new core dependency `access.CallerAdminGrants` (cached on `request.state` by `resolve_request_scope`, like the memberships). The creator's PER-09 is written by `projects.service.create_project(..., creator_id=)` through `app.core.auth.memberships` in the creating transaction; service callers without `creator_id` (provisioning) get none. The create audit entry carries `creator_grants: ["PER-09"]`.
- 2026-11-15 (implementer): "Memberships on soft-deleted projects are ignored" is implemented by revoking (soft-deleting) every membership on a project when it is deleted (`memberships.revoke_project`, audited as `revoked_memberships`), the "drop" option of TD-184; `load_grants` (core) cannot join the projects table without reading a module table. Restore and pre-existing rows: TD-294.
