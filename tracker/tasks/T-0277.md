## Goal
A `system_admin` starts a time-boxed, audited session as a non-admin user, sees exactly that user's projects, personas and site scope and acts as that user (records attributed to the target; the T-0278 guardrail blocks the reserved actions); exit or expiry ends it at once and the target is told by e-mail (diff §4.2 *Support impersonation*, ADR 0015, accepted 2026-11-22, option (a)).

## Acceptance criteria
- [x] `POST /api/v1/admin/users/{user_id}/impersonate` `{reason}`: `system_admin` only (else 403); `reason` non-blank, ≤ 500 characters (422); unknown user 404; deactivated target 422 `USER_DEACTIVATED`; target holding `system_admin` 403 `CANNOT_IMPERSONATE_SYSTEM_ADMIN`; self 422; a caller who is itself impersonating 403 `IMPERSONATION_ACTION_FORBIDDEN` (no nesting)
- [x] Token: new type `impersonation` (distinct `typ` header) signed with the T-0008 key set; claims `sub` = target, `tid` = the admin's tenant, own `sid` and `jti`, `imp` = admin user id, `imp_sid` = the admin's session id; `exp` = now + min(`impersonation_max_minutes`, the admin session's remaining time); **no refresh token**, `/auth/refresh` refuses it; not bound to a device (`did` absent) and refused by device-bound field endpoints (sync download, PIN unlock)
- [x] Runtime setting `impersonation_max_minutes` declared in the T-0230 registry: int, default 30, bounds 5–60 (planner), not client-visible; out of bounds 422
- [x] Verification (`bearer.py`): an impersonation token is rejected (401) when its `jti` or `sid` is revoked, when the admin's `imp_sid` is revoked (admin logout or force sign-out ends the impersonation), or when the admin no longer holds `system_admin` or is deactivated (checked per request in the same unit of work that loads grants)
- [x] RLS context: `resolve_request_scope` builds it from the **target's** memberships (`app.current_user_id` = target, `app.allowed_project_ids`, `app.member_project_ids`, `app.admin_project_ids`, `app.current_project_id`, `site_node_ids`) with `app.is_system_admin` **false**; `Principal` exposes `impersonator_user_id` and `impersonation_read_only` (true when the target holds a PER-15 membership on any project, computed per request from the memberships loaded with the grants; enforced by T-0278)
- [x] Attribution (option (a)): a record created or updated while impersonating carries the **target** in `BaseRecordMixin.created_by` / `updated_by` (test: an allowed project-scoped mutation as the target stores `created_by`/`updated_by` = target, never the admin)
- [x] A target holding `create_projects` can be impersonated (planner default, ADR 0015 §8); the grant is not usable while impersonating (project creation is refused by T-0278)
- [x] A target holding PER-15 (Client Representative) can be impersonated (planner default, ADR 0015 §9); the session is flagged `impersonation_read_only` (test)
- [x] `POST /api/v1/auth/impersonation/exit` (impersonation token only): revokes its `jti` and `sid` in Redis (TTL = remaining lifetime) and returns 204; the SPA then resumes the admin's own session (its access token / refresh cookie were never touched); expiry needs no call
- [x] Ledger (T-0006), tenant chain `admin-impersonation:<tenant>`: `impersonation.started` (admin, target, reason, client IP, user agent, `expires_at`, admin device id), `impersonation.ended` (`reason: exit | expired | revoked`; `expired` written lazily on the first refused use or by a batch cron sweep), never the token
- [x] Target notice (planner default, ADR 0015 §10): when `impersonation.ended` is written (any reason), exactly one e-mail is enqueued to the target through core mail `send_mail` (T-0058) after commit on the interactive queue; i18n template with the admin's display name, start and end time and the sentence that actions were recorded under the target's name and audited as impersonated; never the reason, the token or a link with a secret; a failed or suppressed send does not affect the session or the ledger (tests with the fake transport: one mail per session for exit, expired and revoked; none while the session is live)
- [x] Impersonation sessions do not update the target's `last_login_at`, `last_active_at`, presence or last-used project (T-0243, T-0042), and are listed in neither user's session index as a normal session
- [x] Tests: RLS exactness (target member of A only → admin-as-target 404 on B although the admin sees B normally); revocation on exit, on admin logout and on removal of the admin's grant; expiry cap; no refresh; attribution to the target; PER-15 read-only flag; target e-mail
- [x] Module `README.md` and docs updated
- [x] All quality gates green (see CLAUDE.md §Quality gates)

- 2026-11-22 (implementer): Done on `task/T-0277-impersonation-token`. Decisions and deviations:
  - **Session row** `auth_impersonation_session` (core auth, tenant-level, standard RLS, migration `0039`, additive): `id` = the token's `sid`; no token, no reason text. It makes the end exactly-once across the three paths (exit, lazy refused use, cron sweep: one `UPDATE ... WHERE ended_at IS NULL` wins and only that caller writes `impersonation.ended` and queues the notice) and lets the batch sweep find expired / revoked sessions. Migration number collides with T-0226's `0039` (TD-581).
  - **Admin session end**: access tokens now carry `sxp` (the login session's end); the impersonation expiry is min(registry max, `sxp`). An access token issued before this change has no `sxp`; its own expiry is then the cap (conservative).
  - **Admin re-check** runs in `resolve_request_scope`'s unit of work: bound to the admin (admin-grant own-rows policy), then rebound to the target for the memberships (column reads only). A failed re-check ends the session (`revoked`) and leaves the request unbound; `get_current_user` refuses an impersonation token without the per-request `ImpersonationScope` marker (fail closed).
  - **Lazy end**: a signature-valid impersonation token refused in `bearer.py` (expired: verified again without the `exp` check; revoked `jti`/`sid`/`imp_sid`) ends its session in a short unit of work (`expired` / `revoked`). The cron `impersonation_sweep` (jobs module, batch worker, every 5 min) covers sessions nobody uses again; it also revokes the token's `sid` when it ends one as `revoked`.
  - **Logout with the impersonation token** ends only the impersonation (as exit) and keeps the admin's refresh cookie (the cookie is the admin's session, not the token's). UI decision left to T-0280 (TD-579).
  - **create_projects target**: `CallerAdminGrants` is empty while impersonating, so project creation already answers plain `403` here; T-0278 will give it `IMPERSONATION_ACTION_FORBIDDEN`. **PER-15**: `Principal.impersonation_read_only` is set; enforcement is T-0278.
  - **Not enforced here (T-0278)**: device enrolment / PIN change, A/S authority, admin mutations while impersonating; the start endpoint itself refuses nesting.
  - **Notice e-mail**: template `auth.impersonation_ended` registered from `app/core/auth/impersonation.py`; its three strings were added to core mail's `locales/en-AU.json` (the only catalog; no core mail code changed). Queued in a SAVEPOINT; a refused send is logged and changes nothing. `recipient_user_id` follow-up after T-0226: TD-577.
  - **Side effects on the target**: none here (no device lookup or `last_seen_at`, no `auth_user` write). Telemetry, presence and session index do not exist yet: TD-578 (T-0243); SPA last-used project / storage: TD-579 (T-0280); sync download refusal: TD-580 (T-0147).
