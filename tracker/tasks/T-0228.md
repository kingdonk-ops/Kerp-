## Goal
Admins e-mail a targeted audience; PER-09 can never reach users outside its projects (diff §4.7 Broadcast e-mail).

## Acceptance criteria
- [x] `oe_notifications_broadcast` (`BaseRecordMixin`, tenant RLS): sender, scope (`tenant` or project ids), audience filter, subject, plain-text body, status `draft | queued | sending | sent | failed`, counts; a PER-09 reads only broadcasts targeting its projects
- [x] Audience: System admin — all active users, project(s), category (`internal`, `external`, `client` = PER-15), personas PER-01–PER-16; PER-09 — only users with a live membership on its own PER-09 projects (any other project id → 404); resolved through core auth / admin service calls, never by reading their tables
- [x] `POST /api/v1/notifications/broadcasts/preview` returns the recipient count only; `POST .../broadcasts` queues a `batch` job calling `send_mail` per recipient with `broadcast_id`; deactivated and suppressed addresses excluded; rate limit (planner default 5 broadcasts per sender per 24 h)
- [x] Template `notifications.broadcast`: body escaped plain text; `List-Unsubscribe` + `List-Unsubscribe-Post` (one-click) headers; the unauthenticated one-click endpoint takes an opaque token only: random, single-purpose (broadcast opt-out only), stored hashed at rest (or an HMAC-signed value with a server key), no user id or e-mail in clear in the URL; an unknown, used or malformed token gets the same response as a known one (no oracle; test); never `?user_id=`; opt-out table `oe_notifications_broadcast_optout` (`BaseRecordMixin`, RLS); opted-out users skipped; transactional mail never affected
- [x] `GET .../broadcasts/{id}` with delivery counts from the send log (T-0226)
- [x] Audited (sender, scope, filter, count; never addresses). Tests: PER-09 cannot target or count a foreign project's users; persona and category filters; opt-out
- [x] Module `README.md` and docs updated
- [x] All quality gates green (see CLAUDE.md §Quality gates)

- Decisions: (1) a third table `oe_notifications_broadcast_recipient` (tenant-level, standard RLS) holds the resolved audience as user ids plus each recipient's opt-out token **hash** (SHA-256, unique), so the token store is hashed at rest and the job is resumable. (2) The audience is resolved at queue time under the sender's own RLS (what the preview counted) and re-checked per recipient at dispatch (deactivated / opted out / suppressed / no address → `skipped`). (3) An audience of nobody is 422. (4) `draft` is in the status CHECK but nothing creates drafts yet (composer: T-0229). (5) Two opt-out routes: the SPA page posts `{token}` in the JSON body to `POST /broadcasts/unsubscribe` (in the generated client); the RFC 8058 one-click URI `POST /broadcasts/unsubscribe/one-click?token=` must carry the token, so it is in the query string (never logged; paths are) and the route is kept out of the OpenAPI schema like the SNS endpoint (mail providers call it, not API clients). This keeps `test_invites.py::test_the_invite_token_is_never_taken_from_a_url` (no API operation takes a token from a URL) true without changing it; the reviewer should confirm this reading. The body link is the SPA page `/unsubscribe#<token>` (fragment). (6) The unauthenticated endpoint reads under `KERP_DEFAULT_TENANT_ID` like the SNS endpoint. (7) Core changes, additive: `MailTemplate.multiline_param` and `list_unsubscribe_path`, `RenderedMail.headers` (SES `Simple.Headers`), `mail.service.suppressed_addresses`, `auth.memberships.member_grants`. (8) `POST /broadcasts` is refused while impersonating (403 `IMPERSONATION_ACTION_FORBIDDEN`) until T-0278 classifies it (TD-602). (9) Notifications now declares `jobs` in `depends_on`; this reorders the generated OpenAPI paths (large but mechanical diff in `frontend/src/api/`).
