## Goal
In-app notifications.

## Acceptance criteria
- [x] In-app notification model + API (create, list, mark-read), project-scoped
- [x] Delivery test: a created notification is listable by its recipient and can be marked read
- [x] Notification carries `priority` (`low|normal|high|critical`), an optional `label` and a `pinned` flag that stays until a caller-defined action (e.g. handover acknowledged) clears it; the list returns pinned first, then priority, then newest (needed by E-04-11)
- [x] Delivery goes through a channel interface (`NotificationChannel`: deliver(notification, recipient) → result); `in_app` is the only channel built here; channels are registered by configuration so FCM push (T-0144) and e-mail (TD-084) plug in without changing callers (TD-168)
- [x] A test registers a fake second channel and shows one notification delivered to both; a failing channel does not block in-app delivery
- [x] All quality gates green (see CLAUDE.md §Quality gates)

## Notes

- 2026-11-10: priority / label / pinned criterion added for the handover epic E-04-11 (docs/spec/modules/handover.md §6).

- 2026-11-13 (planner): TD-168 decision 5a: T-0019 stays in-app only, with a pluggable channel interface; FCM push is T-0144.

- 2026-11-13 (implementer): Built `backend/app/modules/notifications/` (migration `0010`; renumber at merge if T-0020 lands first). Decisions:
  - No text is stored: `kind` is a message key with `params`, `label` a label key, so the client renders them with `t()` (CLAUDE.md §6 i18n).
  - Pins: a pin carries a `pin_key` naming the action that clears it; the owning module calls `service.clear_pins(pin_key=..., recipient_id=...)`. Reading does not unpin. The API cannot pin (no API action could clear it).
  - The recipient must hold a membership in the project (else 422). A caller only sees and marks their own notifications; anybody else's is 404.
  - API create needs the `admin` capability (PER-09); confirm or widen in TD-237. Modules notify through `service.notify`.
  - Channels: registry in `channels.py`, switched on by `KERP_NOTIFICATION_CHANNELS` (must contain `in_app`). `in_app` always runs first; a raising, refusing or unregistered channel yields a failed result and a log line (exception type only), never blocks in-app or later channels.
  - Follow-ups: TD-238 (remote channels as an after-commit SAQ job with delivery log/retry), TD-239 (client inbox, unread count, mark-all-read, retention), TD-237 (API sender permission).
