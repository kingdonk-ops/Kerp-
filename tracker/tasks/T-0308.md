## Goal
Requests made with an API key act as the service account under the key's scopes (diff §4.9, ADR 0017).

## Acceptance criteria
- [ ] `Authorization: Bearer kerp_<prefix>_<secret>`: tenant bound from `KERP_DEFAULT_TENANT_ID`, hash looked up under tenant RLS, constant-time compare; unknown, expired or revoked → the same 401
- [ ] Capabilities = key scopes (`read` → `V`; `write` → `V`, `C`, `E`) ∩ the service account's memberships, limited to the key's `project_ids`; `A` and `S` are always removed, so every sign-off, approval, hold release, co-sign and attestation is refused (contract test over all routes classified `A`/`S`)
- [ ] Key-authenticated requests ignore admin grants and ADR 0016 `system_admin` visibility: authorization comes only from the key's scopes ∩ memberships ∩ `project_ids` (test: a service account given an admin grant directly in the database still sees only its member projects and gets 404 elsewhere, and admin read routes refuse the key)
- [ ] Interactive-only routes refuse API keys: `/auth/*`, `/signing/reauth`, devices, PIN, invites acceptance, admin grants, `/admin/*` mutations, SCIM (test)
- [ ] A rotated key's old secret authenticates only until its overlap ends (T-0307), then the same 401
- [ ] Per-key rate limit (registry `api_key_rate_per_minute`, default 600, 60–6000; 429 with `Retry-After`); `last_used_at` throttled
- [ ] Records and ledger entries written by a key carry `created_by` = the service account (`account_type = service`) and `api_key_id` in the audit payload; this pair, not `source="api"` (also the default on human JWT paths, `backend/app/core/db.py`), identifies a machine write (test)
- [ ] AI rules unchanged: a key never confirms a `source="ai"` proposal
- [ ] Module `README.md` and docs updated
- [ ] All quality gates green (see CLAUDE.md §Quality gates)
