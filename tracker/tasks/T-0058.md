## Goal
Diff §4.6 (TD-084; user 2026-11-10: SES with company DKIM, i18n templates, bounces, send log): one core e-mail service that core auth (magic links, password reset) and modules (invites, access-request decisions) use. A Pilot-0 dependency since the product owner put invite and reset e-mails into the gate (2026-11-14).

## Acceptance criteria
- [ ] `app/core/mail/` exposes `send_mail(template_key, to, context, locale)` that only **enqueues** (after commit) on the SAQ interactive queue; core never imports `app.modules`: the enqueue reaches core through a hook the `jobs` module registers at start-up (or a core-level queue client), and an import-boundary test proves it
- [ ] Transport protocol with three implementations: SES (`boto3` imported lazily; region from the deployment setting §4.4; sender address and SES configuration set from deployment configuration; credentials from the instance role / secret store, never the repo), a fake in-memory transport for tests, and a log transport for development; production start-up fails when mail is not configured, and the log transport refuses to run in production
- [ ] Retries with back-off on transient SES errors; permanent failures logged as `failed`; a failed send never rolls back the caller's business action
- [ ] Templates through the i18n layer (`t()` keys, recipient locale or deployment default), plain text plus simple HTML, no remote images or tracking pixels; secrets appear only inside link fragments; a test renders every registered template in `en-AU` without missing keys
- [ ] Send-log table (`BaseRecordMixin`, RLS; System admins read it via an admin-only endpoint): template key, recipient hash + masked display form, status `queued | sent | bounced | complained | failed | suppressed`, provider message id, timestamps; never the link, token or body
- [ ] Bounce and complaint notifications (SES → an SQS poll job, or SES → SNS to a public HTTPS endpoint) put the address on a suppression list (table with `BaseRecordMixin` and RLS, like the send log); sends to a suppressed address are skipped and logged `suppressed`; System admins can remove an address from the list (audited)
- [ ] SNS endpoint hardening (diff §4.6; a valid signature alone does not prove the message is ours): accepts only messages whose `TopicArn` equals the configured `KERP_MAIL_SNS_TOPIC_ARN`; verifies the signature (SignatureVersion 2) with a signing certificate fetched only from an `https://sns.<region>.amazonaws.com/` URL (exact host check, deployment region; certificates cached); honours `SubscriptionConfirmation` only for the configured topic, refuses and logs any other; writes suppression and send-log rows under the deployment's hidden tenant from settings (`KERP_DEFAULT_TENANT_ID`), never a tenant or account value from the payload; refusals logged without the body
- [ ] The existing magic-link sender of T-0009 (`app/core/auth/field.py`, which refuses to send in production without a transport) uses this service
- [ ] Tests with the fake transport: enqueue only (no synchronous send from a request), retry, permanent failure, suppression, bounce webhook signature check, a correctly signed message from a foreign topic refused (nothing suppressed), a foreign `SubscriptionConfirmation` refused (subscribe URL never fetched), a signing-certificate URL on a non-`sns.<region>.amazonaws.com` host refused, a payload carrying another tenant id still writes under the deployment tenant, template rendering, send-log contents never include the token
- [ ] Deploy docs: verified sending domain with DKIM and SPF/DMARC alignment, SES production access (out of the sandbox) in the deployment region, bounce/complaint wiring, configuration variables; `app/core/mail/README.md` written
- [ ] All quality gates green (see CLAUDE.md §Quality gates)
