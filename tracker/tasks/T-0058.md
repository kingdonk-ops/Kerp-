## Goal
Diff §4.6 (TD-084; user 2026-11-10: SES with company DKIM, i18n templates, bounces, send log): one core e-mail service that core auth (magic links, password reset) and modules (invites, access-request decisions) use. A Pilot-0 dependency since the product owner put invite and reset e-mails into the gate (2026-11-14).

## Acceptance criteria
- [x] `app/core/mail/` exposes `send_mail(template_key, to, context, locale)` that only **enqueues** (after commit) on the SAQ interactive queue; core never imports `app.modules`: the enqueue reaches core through a hook the `jobs` module registers at start-up (or a core-level queue client), and an import-boundary test proves it
- [x] Transport protocol with three implementations: SES (`boto3` imported lazily; region from the deployment setting §4.4; sender address and SES configuration set from deployment configuration; credentials from the instance role / secret store, never the repo), a fake in-memory transport for tests, and a log transport for development; production start-up fails when mail is not configured, and the log transport refuses to run in production
- [x] Retries with back-off on transient SES errors; permanent failures logged as `failed`; a failed send never rolls back the caller's business action
- [x] Templates through the i18n layer (`t()` keys, recipient locale or deployment default), plain text plus simple HTML, no remote images or tracking pixels; secrets appear only inside link fragments; a test renders every registered template in `en-AU` without missing keys
- [x] Send-log table (`BaseRecordMixin`, RLS; System admins read it via an admin-only endpoint): template key, recipient hash + masked display form, status `queued | sent | bounced | complained | failed | suppressed`, provider message id, timestamps; never the link, token or body
- [x] Bounce and complaint notifications (SES → an SQS poll job, or SES → SNS to a public HTTPS endpoint) put the address on a suppression list (table with `BaseRecordMixin` and RLS, like the send log); sends to a suppressed address are skipped and logged `suppressed`; System admins can remove an address from the list (audited)
- [x] SNS endpoint hardening (diff §4.6; a valid signature alone does not prove the message is ours): accepts only messages whose `TopicArn` equals the configured `KERP_MAIL_SNS_TOPIC_ARN`; verifies the signature (SignatureVersion 2) with a signing certificate fetched only from an `https://sns.<region>.amazonaws.com/` URL (exact host check, deployment region; certificates cached); honours `SubscriptionConfirmation` only for the configured topic, refuses and logs any other; writes suppression and send-log rows under the deployment's hidden tenant from settings (`KERP_DEFAULT_TENANT_ID`), never a tenant or account value from the payload; refusals logged without the body
- [x] The existing magic-link sender of T-0009 (`app/core/auth/field.py`, which refuses to send in production without a transport) uses this service
- [x] Tests with the fake transport: enqueue only (no synchronous send from a request), retry, permanent failure, suppression, bounce webhook signature check, a correctly signed message from a foreign topic refused (nothing suppressed), a foreign `SubscriptionConfirmation` refused (subscribe URL never fetched), a signing-certificate URL on a non-`sns.<region>.amazonaws.com` host refused, a payload carrying another tenant id still writes under the deployment tenant, template rendering, send-log contents never include the token
- [x] Deploy docs: verified sending domain with DKIM and SPF/DMARC alignment, SES production access (out of the sandbox) in the deployment region, bounce/complaint wiring, configuration variables; `app/core/mail/README.md` written
- [x] All quality gates green (see CLAUDE.md §Quality gates)

- 2026-11-17 (implementer): Built in `backend/app/core/mail/` (README there; deploy steps in `docs/deploy/outbound-email.md`). Entry point is `send_mail(session, template_key, to, context, locale=None)`: the caller's session is needed to write the `queued` send-log row and to enqueue only after that unit of work commits (TD-340). The jobs module installs the post-commit enqueuer at start-up (`app/modules/jobs/mail.py`, API lifespan + worker); `tests/test_mail.py` walks every `app/core` import (none of `app.modules`) and checks in a subprocess that importing core mail loads no module and no boto3.
- Secrets: the template context (with the link token) travels through a Redis payload key (`kerp:mail:<send id>`, 24 h TTL, deleted once settled), never through the SAQ job kwargs (SAQ logs those on errors / at DEBUG), the database or a log line. SAQ retries transient SES errors with exponential back-off (6 attempts, 15 s doubling to 10 min); the last attempt or a permanent error records `failed`.
- Region: new `KERP_AWS_REGION` (deployment region, §4.4) for SES and the SNS certificate host; S3 still has `KERP_S3_REGION` (TD-338). Production start-up (API and worker) fails unless `KERP_MAIL_TRANSPORT=ses`, sender, topic (in the region), `KERP_WEB_ORIGIN` and the tenant are set; CI's image smoke test now passes synthetic mail settings and has a new negative check (production without mail must fail fast).
- Magic link: `MailMagicLinkSender` replaces the dev-log / "undeliverable" senders; the link is `<KERP_WEB_ORIGIN>/magic-link#<token>` (route: TD-337). Only permanent bounces and complaints suppress; locale falls back to `KERP_MAIL_DEFAULT_LOCALE` (TD-340). Follow-ups: stuck `queued` rows (TD-336), `LoopDispatcher.drain` spin (TD-339).
- Migration `0024` (additive): `mail_send_log`, `mail_suppression` (standard RLS). Size: ~1.1k lines of app code + docs, ~1k of tests; not split because the SNS half is an acceptance criterion of this task and its hardening tests depend on the send log.
