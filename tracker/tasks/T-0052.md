## Goal
Token-based project invites (product owner, 2026-11-14; diff §4.1 Invites): existing users join with one click; brand-new users get the membership straight after their first authentication, without the lobby.

## Acceptance criteria
- [ ] `project_invites` table (`BaseRecordMixin`, RLS: the project's PER-09 holders and `system_admin` sessions only): project, invited e-mail (normalised), persona(s) and site scope, inviter, `token_hash` (SHA-256 of a ≥ 256-bit random token; the token itself is never stored or logged), `expires_at`, status `pending | accepted | revoked | expired`, accepted by/at
- [ ] `POST /api/v1/projects/{id}/invites` by a PER-09 of the project or a `system_admin` (else 403/404): creates the account (no credentials) if none exists for the e-mail, revokes any earlier pending invite for the same e-mail and project, and returns the invite link once (`/invite#<token>`: token in the URL fragment, diff §4.1 Invites) so the inviter can pass it on until e-mail delivery exists (T-0056, TD-084); no membership is created yet; the PER-09 + hold-authority `sod_warning` / `confirm_sod` rule of T-0014 applies at creation
- [ ] Expiry `KERP_INVITE_TTL_HOURS` (deployment configuration, default 168; planner default); PER-09 lists and revokes pending invites of the project
- [ ] `POST /api/v1/invites/preview` (signed in; token in the body) returns project code and name and the inviter's name for the "Join project" confirmation; `POST /api/v1/invites/accept` (signed in; token in the body) creates the direct membership and marks the invite accepted in one transaction; single use under concurrency (test with two parallel accepts: one 200, one 409)
- [ ] Bound to the invited e-mail: preview or accept from a session whose user e-mail differs → 403 `code: INVITE_WRONG_USER`, nothing granted; expired, revoked or used token → 410 with a neutral message; every refusal is audited
- [ ] Carry-through for users who are not signed in: `POST /auth/login`, the magic-link request (the server stores the invite reference next to the hashed magic-link record and re-checks it on redeem; the invite token never appears in the magic-link URL), the first-password set (T-0059), and the Entra SSO start (company members only) (stored with `state`, T-0054) accept an optional `invite_token`; after successful authentication the invite is accepted in the same request and the token response carries `joined_project_id`; an invalid token never blocks the sign-in itself (the response carries `invite_error` instead). Because login, magic-link redeem and the SSO callback live in core auth, acceptance runs through a **core post-authentication hook** (defined in `app/core/auth`, empty by default; receives the authenticated user and the opaque `invite_token`, returns `joined_project_id` / `invite_error`) that the admin module registers at start-up, like the T-0057 eligibility hook; core never imports `app.modules` or reads an admin table, and T-0057's import-boundary test covers it; with no hook registered, sign-in works and `invite_token` is ignored
- [ ] Magic-link carry-through only for Field Worker invites (product owner, 2026-11-14; TD-136; diff §4.2): the admin module **registers** an invite eligibility provider at start-up through the core extension point of T-0057 (core auth never imports the admin module and reads no admin table); with it, the eligibility check also accepts a magic-link request whose `invite_token` is a valid pending invite for that e-mail naming PER-14 (so a new Field Worker without any membership yet can sign in by magic link and join); an invite naming only other personas gets the neutral 202 and no link, and that invitee joins through password login (existing accounts with a password) or SSO (company Entra members)
- [ ] External invitees never use SSO (product owner, 2026-11-14; diff §4.1, §4.5): a brand-new invitee without credentials sets their first password at acceptance from the **e-mailed** link (`invite_token` + `setup_token`), built in T-0059; this task stores the invite so T-0059 can add the `setup_token`, and the copied link in the invite response carries the `invite_token` only (it can never set a password); the module README states this
- [ ] The token never appears in a server-visible URL path or query; request logging and Sentry scrub `invite_token` fields (a test asserts that log records of preview, accept and login carrying a token do not contain it)
- [ ] Re-send (product owner, 2026-11-14; diff §4.1 Re-send): `POST /api/v1/projects/{id}/invites/{invite_id}/resend` by a PER-09 of the project or a `system_admin` (same rule as list/revoke; else 403/404) for an invite in `pending`, or `expired` and never accepted; keeps e-mail, persona(s) and site scope, replaces `token_hash` with a fresh token (old link → the neutral 410), resets `expires_at` to now + `KERP_INVITE_TTL_HOURS` and status to `pending`, and returns the new copyable link once (`invite_token` only); the `setup_token` rotation and the new e-mail are T-0059's; `accepted` or `revoked` → 409 `code: INVITE_NOT_RESENDABLE`; rate limit per invite 1 per 60 s and 5 per 24 h (planner defaults) → 429 with `Retry-After`; audited (actor, invite id, no token)
- [ ] Invite creation, acceptance, refusal, revocation and re-send are written to the audit ledger
- [ ] Team links need no invite or user action (ADR 0008): stated in the module README
- [ ] Tests: existing signed-in user one-click accept; existing user without a session accepts through password login, and a PER-14 invitee through magic link (fake mail transport); a magic-link request with a non-PER-14 invite → neutral 202, nothing sent; brand-new user (no credentials) accepts through SSO (fake OIDC provider of T-0054; first-time password set from an e-mailed invite is T-0056); wrong user; expired; revoked; reused; a re-invite revokes the old token; re-send: old token refused with 410 and the new one accepted, expired invite re-sent becomes pending with a new expiry, accepted/revoked → 409, PER-09 of another project → 404, rate limit → 429
- [ ] Module `README.md` and docs updated
- [ ] All quality gates green (see CLAUDE.md §Quality gates)
