## Goal
The client side of diff §4.2–§4.3: work offline on local unlock, independent of the 12-hour server session.

## Acceptance criteria
- [ ] On first sign-in the app enrols the device (T-0043) and sets the PIN (T-0038)
- [ ] Local unlock verifies the PIN on the device against the keystore-held key without any network call and without a valid access or refresh token: a test with an expired session and no network unlocks, reads downloaded work and queues a change (diff §4.2)
- [ ] Offline lockout uses the same numbers as the server; the 10th wrong PIN ends PIN unlock until an online sign-in; failures are reported on the next contact; PIN failures never delete data (user, 2026-11-13)
- [ ] Once the deployment's offline window (T-0044) passes without a successful contact, **or** the offline grace below has passed, whichever comes first (TD-257, confirmed by the product owner 2026-11-14: the grace binds, the window is only an upper bound), the app keeps queued data, blocks new edits and asks for an online sign-in; before both limits it does not (user, 2026-11-13, TD-206; interim until the native Android app, TD-210; grace: product owner, 2026-11-14)
- [ ] **Offline grace** (product owner, 2026-11-14; diff §4.2): when the server session (`session_expires_at`, T-0038) ends while the device is offline, PIN unlock keeps opening cached work and queueing changes until `session_expires_at + offline_grace_hours` (T-0044, default 24 h), measured with the non-decreasing elapsed-time counter of diff §4.2 (persisted `offline_elapsed_ms` + `last_seen_wall_time`; monotonic time within a clock session, T-0172; after a reboot `max(0, wall_now − last_seen_wall_time)`; persisted at every unlock, every queued action and at least once a minute) so a wall clock moved back never extends it and a reboot neither blocks work nor resets it. After it, new edits are blocked (downloaded work stays readable, queued mutations are kept) and the app asks for a fresh sign-in; tests with a fake clock at grace − 1 min and + 1 min, wall clock moved back, a reboot inside the grace (work continues, elapsed time kept), and a reboot plus wall clock moved back (no time added)
- [ ] On reconnect with an expired session the user must sign in again (magic link, SSO or password) before anything syncs, also inside the grace; the queued mutations are kept and the outbox drains under the new session (same user and device)
- [ ] The Android sign-in screen follows T-0055: "Sign in with Microsoft" is the primary, default option when SSO is enabled; password sign-in stays available (no lockout by domain); magic-link request for Field Workers (T-0057)
- [ ] Android sign-in with Microsoft (T-0054, diff §4.5 Native handoff): the app generates a verifier (kept in the keystore-backed store), opens the SSO start URL in the system browser (Custom Tabs) with its `device_id` and the verifier's S256 hash, receives only a single-use exchange code through the verified Android App Link `https://<deployment>/app/sso-return` (`assetlinks.json`; no custom URL scheme), redeems it at `/auth/sso/entra/exchange` with the verifier and `device_id`, and gets the native body transport (T-0043); lands as in T-0055. Tests: no token ever appears in a redirect URL; a code delivered without the stored verifier is refused
- [ ] A `DEVICE_REVOKED` response wipes the local store (`wipe()`), confirms the wipe to the server when possible and returns to sign-in
- [ ] All strings through `t()`; tests with a fake clock and fake network
- [ ] Module `README.md` and docs updated
- [ ] All quality gates green (see CLAUDE.md §Quality gates)
