## Goal
Admin side of access requests (diff §4.1, §6.1): PER-09 holders see and decide pending requests for their projects.

Also the UI for the device registry of diff §4.3 (TD-164, Pilot-0; absorbed from T-0048): see enrolled field devices and revoke a lost one. Both are small Admin-group screens on finished backends (T-0050, T-0043) using the same list + confirm-dialog patterns.

- 2026-11-21 (implementer): Screens in `frontend/src/admin/` (README there). Decisions: (1) System-admin detection: `/auth/me` has no flag, so the client probes `GET /admin/grants?user_id=<self>` (System admin only); TD-393 asks for `is_system_admin` on `/auth/me`. (2) Admin device list = users in scope (`/admin/users` for a System admin, `/admin/projects/{p}/members` per PER-09 project), then `GET /users/{id}/devices` per user; TD-392 for a scoped backend list. (3) PER-07 site scope is an asset node id field (no asset-hierarchy API yet); TD-394 for a picker. (4) The cross-project revoke warning is server-driven: the first revoke goes without the flag; the backend's `409 cross_project_warning` (PER-09 acting, user has other projects) makes the dialog state the extra loss, and only its confirm button sends `confirm_cross_project_wipe: true`. Same pattern for the SoD warning on approve. (5) Dialogs are in-flow confirmation panels (no overlay): axe cannot measure contrast through a fixed overlay; `admin.a11y.test.tsx` audits both screens with dialogs open. (6) After a revoke the row is updated from the response (`revoked`); the wipe time shows once the device has confirmed it, on the next load. Nav items `system` (`/admin/system/devices`) and `accessRequests` got paths with `requires: "projectAdmin"`.
