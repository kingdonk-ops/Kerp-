## Goal
Co-sign modes (i) and (ii) as ledger entries carrying the signer's identity (user R1a; co-sign redesign 2026-11-13). Mode (iii) is T-0174.

## Acceptance criteria
- [ ] A co-signature is its own sign-off ledger entry: signer user id and name, persona PER-15, `verification_mode`, record version and hash covered, the five time-evidence values from T-0177, geolocation, the inspector's `device_id`, and `key_id` for mode ii
- [ ] Mode i (`online_pin`) requires a valid unused co-sign token (T-0162)
- [ ] Mode ii (`client_device_signed`): the QR assertion (`v`, inspection id, record version and hash, step id, signer id, key id, decision, nonce, time evidence; canonical JSON + ES256, planner default) is verified at sync: signature against the key, key active at `occurred_at` (T-0173), nonce never used before, record hash equal to the server's hash of that version, signer an active PER-15 with the anchor in their granted subtree; any failure fails that mutation and notifies the inspector; tests for each failure
- [ ] Assertion schema and verification are shared with the client (fixtures with signed sample assertions used by T-0164 and T-0175)
- [ ] A co-signature covers one record version: editing answers afterwards marks it superseded and a new co-signature is needed
- [ ] A template with `requires_client_signature` makes `inspection.submit` fail with `CLIENT_SIGNATURE_MISSING` until a co-signature for the current version exists
- [ ] The inspection report (T-0158) prints each co-signature with its mode
- [ ] `signing` `README.md` and docs updated
- [ ] All quality gates green (see CLAUDE.md §Quality gates)
