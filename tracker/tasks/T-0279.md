## Goal
Every ledger entry written while impersonating names both identities, inside the hash, so the attribution can never be edited away (ADR 0015 §Audit; ADR 0010 precedent).

## Acceptance criteria
- [x] Additive migration on `audit_ledger` (core table, ADR 0015): nullable `impersonated_by_user_id` (UUID, no FK); CHECK `hash_version >= 3 OR impersonated_by_user_id IS NULL`; `hash_version IN (1, 2, 3)`
- [x] Hash v3 = v2 body + `"impersonated_by_user_id"` with `"v": 3`; v1 and v2 entries keep verifying (known-answer tests for v1, v2, v3; a mixed chain verifies)
- [x] `audit.append` takes the impersonator from the request context only (set by T-0277's principal), never from arguments of callers or the request body; `created_by` stays the acting (target) user (= `acted_as_user_id`); outside impersonation entries are written exactly as today (v2)
- [x] Option (a) (test): an allowed mutation made while impersonating writes its module ledger entry with `created_by` = target and `impersonated_by_user_id` = admin at hash v3, and the chain verifies; the same mutation outside impersonation writes v2 with the column null
- [x] Ledger reads (T-0222 audit explorer API) expose `impersonated_by_user_id`; filter by it; display string "{target} (impersonated by {admin})" key added to the i18n catalogue
- [x] Downgrade documented as development-only (like ADR 0010)
- [x] Module `README.md` and docs updated
- [x] All quality gates green (see CLAUDE.md §Quality gates)

## Notes
- 2026-11-21 (planner): Pasted "acted_as_user_id" is the existing `created_by`; only `impersonated_by_user_id` is new. `BaseRecordMixin` rows get no second column (rejected in ADR 0015: a core-mixin change on every table); the ledger is the attribution record. Was blocked by TD-426.
- 2026-11-22 (planner): TD-426 resolved by the user: **option (a) full impersonation**; ADR 0015 accepted; unblocked. Ordinary mutations are written during impersonation, so every module entry written then carries both identities; this ledger column is the only record of the admin on those rows.
- 2026-11-22 (implementer): Migration `0044_audit_ledger_impersonator` (revises T-0228's `0043_notifications_broadcast`; renumbered after #188 and #190 merged). New `current_impersonator_id` context var (`app/core/tenancy/context.py`), published by `get_principal` next to `current_device_id` (the ADR 0010 pattern); `audit.append` has no argument for it. `HASH_VERSION` stays 2 for ordinary entries; `IMPERSONATION_HASH_VERSION` = 3 only when an impersonator is set. Option (a) test uses asset-node creation (saved views write no ledger entry). The exit's `impersonation.ended` entry is written under the impersonation token with `actor_id` = admin, so it names the admin in both columns (v3); tested and documented. Downgrade fails while any v3 entry exists (stricter than ADR 0010, never strips the admin silently); documented in ADR 0015 Consequences and the audit README. Frontend: `gen:api` regenerated, i18n key `admin.system.audit.impersonatedBy` added, fixture gained the field; the display is T-0280. Updated two existing tests that used version 3 as "unknown" (now 4). Follow-up TD-600 (route contract, for T-0278).
- 2026-11-22 (implementer, review round 1): `test_the_downgrade_keeps_v1_and_v2_entries` now reads the ledger inside `db.unit_of_work(CTX_T1)` (on PostgreSQL the runtime role saw no rows through RLS on an unbound connection) and checks the column is gone. The refused downgrade is now `pytest.raises(IntegrityError, match="hash_version")` and is followed by asserts that the revision, the v3 entry and its admin are unchanged. Both migration tests upgrade to a pinned `AFTER = "0043"` rather than `head`, so T-0228's 0044 cannot change them. Reverted the formatting-only changes to unrelated tests in `test_audit_explorer.py`. TD-600 notes that worker jobs enqueued during impersonation write entries without the admin.
- 2026-11-22 (implementer, CI fix): `test_rls_bypass.py::test_migration_0035_widens_only_project_isolation_policy_and_downgrades` (PostgreSQL only) upgrades to `0035` and wrote its project-B ledger row through `audit.append`. The ORM now maps `impersonated_by_user_id`, which does not exist at `0035`, so the tail SELECT failed. The ADR 0010 `device_id` column never hit this because it dates from `0016`, before `0035`. The test now inserts the same row (a valid v2 entry, hash computed) with raw SQL in the `0035` schema; its assertions are unchanged.
- 2026-11-22 (implementer, rebase onto #190): rebased onto T-0228 and renumbered the migration to `0044_audit_ledger_impersonator` (revises `0043_notifications_broadcast`, which does not touch `audit_ledger`). The tests now pin `BEFORE = "0043"` and `AFTER = "0044"`. T-0228's broadcast `audit.append` calls are not reachable under impersonation: `POST /broadcasts` answers 403 while impersonating, and the dispatch entry is written by the worker, so it carries no impersonator (see TD-600).
