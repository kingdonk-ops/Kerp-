## Goal
Make **effective project access = individual memberships ∪ team-derived grants** (diff §4.1
Teams, ADR 0008) in core auth, without core importing the teams module. Team-derived grants are
stored in the core project membership table (`auth_project_membership`), keyed by **(project,
user, source_type, source_id)**: `direct` rows are today's individual memberships, `team_link`
rows carry the team link id (ADR 0008, accepted by the product owner). Then `load_grants`, `resolve_scope`, `project_access`, the
allowed project list and T-0014's membership-based RLS all count them automatically. Core
exposes a narrow API that the teams module (T-0013) calls to keep those rows in step. The PER-09
membership admin (T-0014) shows derived rows but cannot change them.

## Acceptance criteria
- [ ] Additive migration on the core table `auth_project_membership` (ADR 0008):
  - `source_type` (NOT NULL, server default `'direct'`, CHECK in `direct`, `team_link`) and `source_id` (UUID, nullable, no FK, indexed), plus CHECK `(source_type = 'direct') = (source_id IS NULL)`. Every existing row becomes `direct`
  - `uq_auth_project_membership_grant` is replaced by a constraint on `(tenant_id, member_project_id, user_id, source_type, source_id, persona, site_node_id)` with `NULLS NOT DISTINCT` (PostgreSQL 16). Persona and site stay in the key because a user may hold several personas on a project from one source
  - Partial unique index `(tenant_id, member_project_id, user_id, source_id) WHERE source_type = 'team_link' AND deleted_at IS NULL` (the product owner's key, exact for team rows: one live persona per user per link). The sync soft-deletes the old row before it inserts the re-roled one. The persona/site columns in the main constraint are the ADR's refinement, confirmed by the product owner on 2026-11-13 (multiple roles per project for direct grants)
  - SQLite does not enforce NULLS NOT DISTINCT. The write paths look up an existing row (soft-deleted included) before inserting, so they stay idempotent there too. The duplicate-rejection test runs on PostgreSQL
  - The downgrade is destructive and documented as such: it deletes the `team_link` rows first, then restores the old constraint and drops the columns
- [ ] `app.core.auth` public API (documented in `app/core/auth/README.md`), callable only in a `system_admin` tenant-level session. Any other session gets a 403 error or a refused write under RLS:
  - `sync_team_link_grants(session, *, link_id, project_id, persona, site_node_id, user_ids, confirm_sod=False) -> None`: makes the non-deleted derived rows of `link_id` exactly one row per user in `user_ids`, with that persona/site. Rows that are gone, or that carry an old persona/project, are soft-deleted. Unchanged rows are not rewritten. A matching soft-deleted row (same link, user, project, persona and site) is restored rather than duplicated
  - `revoke_team_link_grants(session, *, link_id) -> None`: soft-deletes every derived row of the link
  - `team_link_grants(session) -> Mapping[UUID, frozenset[tuple[UUID, UUID, str, UUID | None]]]`: for **every** `source_id` of non-deleted `team_link` rows in the tenant, the full set of `(user_id, project_id, persona, site_node_id)` tuples. Reconcile (T-0075) uses it, so it must also return link ids unknown to the teams tables (orphans)
  - The persona is validated with the same CHECKs as individual memberships, plus the TD-251 link rule (product owner, 2026-11-13): PER-01 to PER-14 except PER-09, and PER-16 (T-0076) are accepted. PER-09 and PER-15 are refused with `ValueError`
  - **Separation of duties across sources (ADR 0008):** when the sync would give a hold-authority persona (PER-02, PER-06, PER-07, PER-11) on the project to a user who holds individual PER-09 there, it raises `SodConfirmationRequired` (carrying the affected user ids) unless `confirm_sod=True`. With confirmation, the audit entry carries `sod_warning: true`
  - Each call that changes rows writes one audit entry on chain `membership:<project_id>`, with the link id, added/removed user ids and the actor. A no-op writes none
- [ ] `load_grants` returns the union of the active rows for (project, user), whatever their `source_type`. Duplicate `Grant`s (same project/persona/site from both sources) collapse. `resolve_scope` / `project_access` / `allowed_project_ids` need no caller change. Memberships on soft-deleted projects and of deactivated users are ignored as before
- [ ] T-0014 membership administration: the project member list returns every row with its `source_type`/`source_id` (`team_link` rows marked `source: team` with the link id). The team name is `null` here (T-0013 adds the name once the teams module exists; core never imports a module). PUT/DELETE on a derived row returns 409 ("managed through a team"). A PER-09 assigning an individual persona that a user already holds through a team creates the individual row, so removing the team later keeps it. `GET /api/v1/me/projects` includes projects reached only through a team. **SoD on the individual side:** T-0014's PER-09/hold-persona check counts team-derived grants. Assigning individual PER-09 to a user who holds a team-derived PER-02/06/07/11 on the project returns 409 `sod_warning` unless `confirm_sod: true`, and the confirmed assignment is audited with `sod_warning: true`
- [ ] Deactivating a user (T-0014) leaves their derived rows in place. A deactivated account cannot authenticate. `sync_team_link_grants` never filters `user_ids` by account status: it stores exactly the users it is given, and the caller (T-0013) passes every non-deleted team member. Reactivation restores team access with no re-sync (ADR 0008)
- [ ] Fail closed if teams is disabled: at startup, when the `teams` module is not loaded and non-deleted `team_link` rows exist, the app refuses to start with an error naming the revoke procedure (core reads the loader's loaded-module list and its own table, and imports no module). The check runs before any tenant is bound, so it calls a `SECURITY DEFINER` function created by the migration (owned by the migration role, `search_path` pinned, `EXECUTE` granted to `kerp_app`). The function returns only the count of live `team_link` rows across **all tenants**, never row data. On SQLite the check is a plain count
- [ ] Tests:
  - Partial index (PostgreSQL): a second live `team_link` row for the same user, project and link with a different persona is rejected. A re-role sync (soft-delete then insert) succeeds. A live `direct` row with the same persona beside it is allowed
  - Migration: existing rows become `direct`. A `direct` row with a `source_id`, or a `team_link` row without one, violates the CHECK. The same user, project and persona can exist as one `direct` and one `team_link` row, and a second identical `direct` row is rejected (PostgreSQL)
  - A PER-16 link grants `V` only on its project. A PER-09 or PER-15 link is refused
  - Unit: sync adds, removes, re-roles and is idempotent. Revoke clears the link. Individual rows are never touched by either. Removing a user and adding them back restores the soft-deleted row (no unique-constraint error, no second row)
  - `team_link_grants` returns full tuples for every link id with live derived rows, including one that the caller does not know about
  - SoD: a user with individual PER-09 on P synced into a PER-02 (also PER-06, PER-07 with a site, PER-11) link on P gets `SodConfirmationRequired`. With `confirm_sod=True` it succeeds and is audited `sod_warning: true`. A user with PER-09 on Q only is not affected. Reverse: individual PER-09 assigned via the T-0014 API to a user with team-derived PER-06 on P returns 409 without `confirm_sod`, 200 with it, and is audited
  - Startup check: teams not loaded with live derived rows gives a startup error. With no derived rows it starts
  - A user with only a derived PER-04 grant on P gets `project_access(P)` with PER-04 and 404 on Q. A derived PER-01 (portfolio) grant puts P in `allowed_project_ids`. A derived PER-07 grant sets the site filter
  - Individual PER-04 + derived PER-04 on P: revoking the link keeps access. Removing the individual row keeps access while the link exists
  - PostgreSQL as `kerp_app`: a non-`system_admin` session cannot insert, update or delete derived rows. A user with only a derived grant on A can read project A's row (membership-based `projects` policy) and not B's
  - API: PER-09 gets 409 when editing or removing a derived row; the member list shows `source: team`
- [ ] Module/README.md and docs updated (`app/core/auth/README.md`, `app/core/tenancy/README.md` membership paragraph)
