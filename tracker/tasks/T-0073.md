## Goal
Make **effective project access = individual memberships ∪ team-derived grants** (diff §4.1
Teams, ADR 0008) in core auth, without core importing the teams module. Team-derived grants are
stored as derived rows in the core membership store (`auth_project_membership`) and tagged with
the team link they come from. Then `load_grants`, `resolve_scope`, `project_access`, the
allowed project list and T-0014's membership-based RLS all count them automatically. Core
exposes a narrow API that the teams module (T-0013) calls to keep those rows in step. The PER-09
membership admin (T-0014) shows derived rows but cannot change them.

## Acceptance criteria
- [ ] Additive migration on the core table `auth_project_membership` (ADR 0008): nullable `via_team_link_id` (UUID, no FK, indexed). `uq_auth_project_membership_grant` is replaced by one that includes `via_team_link_id` (nulls not distinct). Existing rows stay individual (`NULL`). The downgrade drops only what this migration added
- [ ] `app.core.auth` public API (documented in `app/core/auth/README.md`), callable only in a `system_admin` tenant-level session. Any other session gets a 403 error or a refused write under RLS:
  - `sync_team_link_grants(session, *, link_id, project_id, persona, site_node_id, user_ids) -> None`: makes the non-deleted derived rows of `link_id` exactly one row per user in `user_ids`, with that persona/site. Rows that are gone, or that carry an old persona/project, are soft-deleted. Unchanged rows are not rewritten
  - `revoke_team_link_grants(session, *, link_id) -> None`: soft-deletes every derived row of the link
  - `team_link_grant_user_ids(session, *, link_id) -> frozenset[UUID]` (for T-0013's reconcile)
  - The persona is validated with the same CHECKs as individual memberships, plus TD-251's link default: PER-09 and PER-15 are refused with `ValueError`
  - Each call that changes rows writes one audit entry on chain `membership:<project_id>`, with the link id, added/removed user ids and the actor. A no-op writes none
- [ ] `load_grants` returns individual and derived grants. Duplicate `Grant`s (same project/persona/site from both sources) collapse. `resolve_scope` / `project_access` / `allowed_project_ids` need no caller change. Memberships on soft-deleted projects and of deactivated users are ignored as before
- [ ] T-0014 membership administration: the project member list returns derived rows marked `source: team` with the link id. The team name is filled in by the admin module through `teams.service` when the teams module is loaded, else `null` (core itself never imports a module). PUT/DELETE on a derived row returns 409 ("managed through a team"). A PER-09 assigning an individual persona that a user already holds through a team creates the individual row, so removing the team later keeps it. `GET /api/v1/me/projects` includes projects reached only through a team
- [ ] Deactivating a user (T-0014) soft-deletes their derived rows too. Reactivating does not restore them; T-0013's reconcile does
- [ ] Tests:
  - Unit: sync adds, removes, re-roles and is idempotent. Revoke clears the link. Individual rows are never touched by either
  - A user with only a derived PER-04 grant on P gets `project_access(P)` with PER-04 and 404 on Q. A derived PER-01 (portfolio) grant puts P in `allowed_project_ids`. A derived PER-07 grant sets the site filter
  - Individual PER-04 + derived PER-04 on P: revoking the link keeps access. Removing the individual row keeps access while the link exists
  - PostgreSQL as `kerp_app`: a non-`system_admin` session cannot insert, update or delete derived rows. A user with only a derived grant on A can read project A's row (membership-based `projects` policy) and not B's
  - API: PER-09 gets 409 when editing or removing a derived row; the member list shows `source: team`
- [ ] Module/README.md and docs updated (`app/core/auth/README.md`, `app/core/tenancy/README.md` membership paragraph)
- [ ] All quality gates green (see CLAUDE.md §Quality gates)
