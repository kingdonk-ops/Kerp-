## Goal
A production API or worker must refuse to start when the database role it connects as can bypass tenant isolation or the audit-ledger guard, or when Redis or the JWT signing key is missing (audit items 2 and 17). Today `rls_enforcement_problems`, `rls_coverage_problems` and `ledger_guard_problems` are only called by tests and the Redis/JWT checks run on the first signed-in request.

## Acceptance criteria
- [ ] In `app/main.py` `lifespan`, when `KERP_ENVIRONMENT=production`, the app calls `rls_enforcement_problems` (`core/tenancy/rls.py`), `rls_coverage_problems` and `ledger_guard_problems` (`core/audit/guard.py`) against `KERP_DATABASE_URL` and raises (startup fails, clear log line naming each problem) if any reports a problem; outside production it logs a warning only
- [ ] The SAQ worker startup runs the same three checks with the same production rule (one shared function, not a copy)
- [ ] `lifespan` calls `app_auth_runtime(app)` so a missing or invalid JWT signing key fails startup; in production `KERP_REDIS_URL` is required (settings validation error) for API and worker
- [ ] Tests: production startup with a superuser / `BYPASSRLS` role, with a role that owns an RLS table without `FORCE`, with `audit_ledger` UPDATE/DELETE granted, without `KERP_REDIS_URL`, without a signing key each fail; a correctly set-up runtime role starts (PostgreSQL tests for the role checks; SQLite/dev skips the DB checks with a logged reason)
- [ ] `/health` stays a liveness check; `docs/deploy/first-run.md` states the startup refusals and how to read the error
- [ ] TD-124 resolved; TD-059 gets a dated note (startup assert done here, grants in T-0343); TD-056 gets a dated note (startup assertion done here, role split in T-0343)
- [ ] Module/README.md and docs updated
- [ ] All quality gates green (see CLAUDE.md §Quality gates)
