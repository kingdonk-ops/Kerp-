## Goal
System admins see uploads that failed or are stuck in the check, with the scanner signature or rejection reason, and can nudge stuck ones (diff §4.7 Upload quarantine monitor).

## Acceptance criteria
- [ ] Every endpoint is `system_admin` only: any other caller, PER-09 included, gets 403 (test per endpoint, including a PER-09 of every project)
- [ ] `GET /api/v1/admin/system/uploads?status=verifying|rejected|expired&reason=&project=`: rows (project code, file id, original filename, size, SHA-256, status, reason code, scanner signature, uploader id, created/updated times; paged) of **every project** of the tenant, read under the normal project RLS of `oe_uploads_file` (a `system_admin` sees all projects, ADR 0016)
- [ ] `GET /api/v1/admin/system/uploads/counts`: for every project the number of uploads per status and reason code (project, status and reason filters), a `GROUP BY` under the same normal RLS; no `SECURITY DEFINER` function
- [ ] No uploads-specific policy change and **no bypass role** (`BYPASSRLS`, superuser): visibility comes only from the ADR 0016 policy of T-0274; the RLS-bypass contract tests stay green
- [ ] Contract test (PostgreSQL, as `kerp_app`): a `system_admin` without a membership on project B sees B's rows and counts and can re-check a B file; a non-admin (PER-09 of B included) gets 403 on every endpoint
- [ ] Media-probe reasons of T-0169 appear once that task lands (reason codes are passed through, not enumerated here)
- [ ] `POST .../uploads/{file_id}/recheck` (any project of the tenant) re-queues the check of a file stuck in `verifying` whose staging object still exists (else 409 `OBJECT_GONE`); audited
- [ ] `POST .../uploads/sweep?project=` queues T-0215's orphan sweep for that project now (housekeeping that returns no rows; any project); audited
- [ ] Rejected rows show 'object deleted' (bytes are removed at rejection, TD-397); there is no purge action
- [ ] Module `README.md` and docs updated
- [ ] All quality gates green (see CLAUDE.md §Quality gates)
