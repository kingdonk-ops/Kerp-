## Goal
System admins see uploads that failed or are stuck in the check, with the scanner signature or rejection reason, and can nudge stuck ones (diff §4.7 Upload quarantine monitor).

## Acceptance criteria
- [x] Every endpoint is `system_admin` only: any other caller, PER-09 included, gets 403 (test per endpoint, including a PER-09 of every project)
- [x] `GET /api/v1/admin/system/uploads?status=verifying|rejected|expired&reason=&project=`: rows (project code, file id, original filename, size, SHA-256, status, reason code, scanner signature, uploader id, created/updated times; paged) of **every project** of the tenant, read under the normal project RLS of `oe_uploads_file` (a `system_admin` sees all projects, ADR 0016)
- [x] `GET /api/v1/admin/system/uploads/counts`: for every project the number of uploads per status and reason code (project, status and reason filters), a `GROUP BY` under the same normal RLS; no `SECURITY DEFINER` function
- [x] No uploads-specific policy change and **no bypass role** (`BYPASSRLS`, superuser): visibility comes only from the ADR 0016 policy of T-0274; the RLS-bypass contract tests stay green
- [x] Contract test (PostgreSQL, as `kerp_app`): a `system_admin` without a membership on project B sees B's rows and counts and can re-check a B file; a non-admin (PER-09 of B included) gets 403 on every endpoint
- [x] Media-probe reasons of T-0169 appear once that task lands (reason codes are passed through, not enumerated here)
- [x] `POST .../uploads/{file_id}/recheck` (any project of the tenant) re-queues the check of a file stuck in `verifying` whose staging object still exists (else 409 `OBJECT_GONE`); audited
- [x] `POST .../uploads/sweep?project=` queues T-0215's orphan sweep for that project now (housekeeping that returns no rows; any project); audited
- [x] Rejected rows show 'object deleted' (bytes are removed at rejection, TD-397); there is no purge action
- [x] Module `README.md` and docs updated
- [x] All quality gates green (see CLAUDE.md §Quality gates)

All reads run on the caller's tenant-level request session under normal RLS (ADR 0016); re-check and sweep create their job in the file's / project's own scope (the worker's scope, no bypass) and are audited on `admin-system:<tenant>` (`upload_rechecked`, `upload_sweep_queued`) after the job commits, as the queue monitor does (TD-455).
- 2026-11-21 (implementer): Re-check accepts a `verifying` file whose bytes exist in staging **or** in the quarantine copy a scanner outage keeps (T-0218); neither → 409 `OBJECT_GONE`; not `verifying` → 409 `NOT_VERIFYING`. The new job becomes the file's `job_id` and `updated_at` restarts the 6 h stuck clock. Spec-gap TD-488.
- 2026-11-21 (implementer): `object_deleted` is true for `rejected` and `expired` rows (the sweep that expires a pending row deletes its staging object in the same run). Rows of a project soft-deleted since stay listed without a `project_code`; the sweep of a deleted project is 404. `project=` takes a project id. Reason codes are passed through unvalidated (≤ 200 chars), so T-0169's media-probe codes appear without a change here.
- 2026-11-21 (implementer): Tests `backend/tests/test_uploads_quarantine.py` (SQLite + PostgreSQL); the PostgreSQL contract test also asserts the runtime role is `NOSUPERUSER NOBYPASSRLS`, `oe_uploads_file` carries exactly the standard policies, and no `SECURITY DEFINER` function references it.
- 2026-11-21 (implementer, PR #159 review round 1): "Stuck" now means: the file is `verifying` **and** its current verify job (read in the file's own scope through `jobs.service.job_status`) is not `queued` or `running`, i.e. it `failed` (aborted included), `succeeded` without deciding, or is unknown. Otherwise 409 `CHECK_RUNNING`. A second verify job next to a live one is not harmless (the round-1 text was wrong): both share the quarantine object and each deletes it before writing, so the later writer can reject a clean file as `missing_object` and the other leaves an orphan content object. A worker that died leaves its job `running`: abort it in the queue monitor, then re-check. Overlap still possible after a queue-monitor abort of a job whose thread is mid-check, or a queue-monitor retry of the replaced failed job: risk TD-497 (fail-safe). `recheck_upload` resolves storage itself, so the admin router imports only `uploads.service` / `uploads.schemas`; T-0221 added to TD-455.
