## Goal
System admins see uploads that failed or are stuck in the check, with the scanner signature or rejection reason, and can nudge stuck ones (diff §4.7 Upload quarantine monitor).

## Acceptance criteria
- [ ] Every endpoint is `system_admin` only: any other caller, PER-09 included, gets 403 (test per endpoint, including a PER-09 of every project)
- [ ] `GET /api/v1/admin/system/uploads?status=verifying|rejected|expired&reason=&project=`: project code, file id, size, SHA-256, status, reason code, scanner signature, uploader id, created/updated times; paged
- [ ] Narrow path: the read goes through an uploads service function returning only those fields (count/metadata pattern of the lobby lookup); the original filename and linked record appear only for projects where the caller holds a membership (TD-396 default; test with a non-member admin)
- [ ] Media-probe reasons of T-0169 appear once that task lands (reason codes are passed through, not enumerated here)
- [ ] `POST .../uploads/{file_id}/recheck` re-queues the check of a file stuck in `verifying` whose staging object still exists (else 409 `OBJECT_GONE`); audited
- [ ] `POST .../uploads/sweep?project=` queues T-0215's orphan sweep for that project now; audited
- [ ] Rejected rows show 'object deleted' (bytes are removed at rejection, TD-397); there is no purge action
- [ ] Module `README.md` and docs updated
- [ ] All quality gates green (see CLAUDE.md §Quality gates)
