## Goal
Close three auth gaps from the audit: a PIN change can clear a `PIN_EXHAUSTED` lockout from any live session (item 6, against the TD-301 ruling); a lost or failed refresh response ends the whole session (item 7); magic-link requests and SSO start have no per-client limit (item 12).

## Acceptance criteria
- [x] `PUT /api/v1/devices/{id}/pin` (`core/auth/device_api.py`): when the device is at the PIN-failure limit (`PIN_EXHAUSTED`), the change needs a session created by password or magic-link sign-in (or SSO) within the last 5 minutes and not renewed by PIN unlock; otherwise 401 with a distinct code (e.g. `FRESH_SIGN_IN_REQUIRED`) and nothing changes; below the limit the TD-301 behaviour is unchanged (tests: fresh sign-in clears the lock; a 6-minute-old session, a PIN-renewed session and a refreshed session older than 5 minutes get 401; below the limit any bound session works)
- [x] The session records how and when it was started (sign-in method + time) in a way that survives refresh rotation; PIN unlock does not reset it (test)
- [x] Refresh (`core/auth/service.py` refresh path): the DB lock and active-user check run before `consume_refresh`; a retry of an already-consumed refresh token within 30 seconds of its consumption gets a plain 401 (`REFRESH_RETRY` or the existing invalid code) without revoking the session; a replay after the grace still revokes the whole session (tests: lock timeout / failed commit leaves the token unconsumed; retry within grace does not end the session; replay after grace does; tests use an injected clock, not the wall clock (TD-509))
- [x] `POST` magic-link request (`core/auth/router.py`) gets the same per-client lockout as `PasswordResetService.request` (`password_reset.py`), checked before the per-address limit; 429 with `Retry-After` (test: one client posting many different addresses is limited; a second client is not)
- [x] `GET /auth/sso/entra/start` (`sso_router.py`) gets a per-client limit before it stores a state entry (test); TD-323 resolved
- [x] TD-301 resolved (point (2) amendment built here; points (1), (3), (4) confirmed as built); README of `core/auth` documents fresh sign-in, the refresh grace and the per-client limits
- [x] Module/README.md and docs updated
- [x] All quality gates green (see CLAUDE.md §Quality gates)

## Notes
- 2026-11-21 (planner): Created from the 2026-11-21 codebase audit; one PR with T-0341..T-0349. Module `identity`, as for the other `core/auth` tasks (T-0008, T-0009, T-0037, T-0038). TD-301 asks for this before T-0143 builds the client.
- 2026-11-21 (implementer): Sign-in method and time are JWT claims `auth_time` + `amr` (`pwd` / `magic_link` / `sso`, `pin` appended by a PIN unlock), set by `start_session` (now takes a required `method`) and copied by every rotation, so no store key or migration. Both claims are optional on verify: tokens issued before this change keep working and never count as fresh (fails closed only for the at-limit PIN change). "At the limit" = the device's PIN counter holds `PIN_POLICY.max_attempts` (10), read without counting (`RevocationStore.failure_count`, `ProgressiveLockout.at_limit`). 401 body `{detail, code: FRESH_SIGN_IN_REQUIRED}` like the PIN codes.
- 2026-11-21 (implementer): Refresh retry grace: `consume_refresh(jti, spent_at=, remember=)` writes `refresh-spent:<jti>` in the same Redis transaction (WATCH/MULTI) as the delete; a spent token presented within `REFRESH_RETRY_GRACE` (30 s, by the token service's injectable clock) is the existing plain 401 without revoking; later it revokes as before. Applies to `/auth/pin/unlock` too (same `_rotate`). Reading of "failed commit leaves the token unconsumed": the lock and active-user check now run before the consume, so a lock timeout / DB error there leaves it unconsumed (tested); the request's commit itself runs after the service returns (DbSession), so a failure there is covered by the grace instead (tested: the retry is a plain 401 and the session lives). Existing tests that replayed a token immediately now assert the grace (`test_auth_api`), and the revoking replay tests moved past the grace on the injected clock (`test_auth_sessions`, `test_auth_field`).
- 2026-11-21 (implementer): Per-client limits keyed by `client_subject(tenant, request.client.host)` (the password-reset derivation): `MAGIC_LINK_CLIENT_POLICY` (= `PASSWORD_RESET_CLIENT_POLICY` numbers) before the per-mailbox lock; `SSO_START_CLIENT_POLICY` (60 back to back) on GET and form-POST start before the state entry. Generated client regenerated (docstrings + 401/429 responses).
