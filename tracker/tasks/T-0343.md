## Goal
Make the documented two-role database setup work (audit item 3): migrations run as the schema owner, the app and worker run as a separate runtime role that owns nothing, has no `BYPASSRLS`, and has only the rights it needs. Prove it in CI by migrating as the owner and running the backend tests as `kerp_app`.

## Acceptance criteria
- [ ] Migration `0039` (next free after `0038_project_legal_hold.py`) grants a runtime role named by a setting (e.g. `KERP_RUNTIME_DB_ROLE`, default `kerp_app`; skipped with a log line when unset or the role does not exist, so dev setups keep working) SELECT, INSERT, UPDATE, DELETE on every table, USAGE on sequences and EXECUTE on the app's functions (including the lobby and access-request functions of `0021_project_lobby.py` and `0023`, today granted only to `CURRENT_USER`), plus `ALTER DEFAULT PRIVILEGES` for future tables, sequences and functions created by the owner
- [ ] `audit_ledger` gets SELECT, INSERT only for the runtime role (no UPDATE, DELETE, TRUNCATE), as TD-059 requires; test that the runtime role cannot update or delete a ledger row
- [ ] The downgrade revokes exactly what the upgrade granted; SQLite skips the migration body
- [ ] ADR `docs/decisions/0019-owner-and-runtime-database-roles.md` (accepted) is written in this PR: it changes the security model of every table (who owns, who may grant), even though it is grants-only and additive
- [ ] A new CI job (or a mode of the PostgreSQL job) creates an owner role and a `NOSUPERUSER NOBYPASSRLS` runtime role, migrates as the owner, runs the backend test suite (or the RLS/ledger/lobby subset if the full suite needs owner rights for fixtures; the choice is recorded in Notes) as `kerp_app`, and asserts `rls_enforcement_problems`, `rls_coverage_problems` and `ledger_guard_problems` report nothing for that role; it is added to `ci-gate` and `scripts/ci_gate.py` `EXPECTED`; no existing job, step, floor or check is removed or weakened (`scripts/tests/test_workflows.py` updated)
- [ ] `docs/deploy/first-run.md` documents creating both roles and the setting; the "permission denied" path from the audit is gone
- [ ] TD-056 resolved; TD-059 resolved (startup assert by T-0342, grants here)
- [ ] Module/README.md and docs updated
- [ ] All quality gates green (see CLAUDE.md §Quality gates)
