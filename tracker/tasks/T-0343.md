## Goal
Make the documented two-role database setup work (audit item 3): migrations run as the schema owner, the app and worker run as a separate runtime role that owns nothing, has no `BYPASSRLS`, and has only the rights it needs. Prove it in CI by migrating as the owner and running the backend tests as `kerp_app`.

## Acceptance criteria
- [x] Migration `0039` (next free after `0038_project_legal_hold.py`) grants a runtime role named by a setting (e.g. `KERP_RUNTIME_DB_ROLE`, default `kerp_app`; skipped with a log line when unset or the role does not exist, so dev setups keep working) SELECT, INSERT, UPDATE, DELETE on every table, USAGE on sequences and EXECUTE on the app's functions (including the lobby and access-request functions of `0021_project_lobby.py` and `0023`, today granted only to `CURRENT_USER`), plus `ALTER DEFAULT PRIVILEGES` for future tables, sequences and functions created by the owner
- [x] `audit_ledger` gets SELECT, INSERT only for the runtime role (no UPDATE, DELETE, TRUNCATE), as TD-059 requires; test that the runtime role cannot update or delete a ledger row
- [x] The downgrade revokes exactly what the upgrade granted; SQLite skips the migration body
- [x] ADR `docs/decisions/0019-owner-and-runtime-database-roles.md` (accepted) is written in this PR: it changes the security model of every table (who owns, who may grant), even though it is grants-only and additive
- [x] A new CI job (or a mode of the PostgreSQL job) creates an owner role and a `NOSUPERUSER NOBYPASSRLS` runtime role, migrates as the owner, runs the backend test suite (or the RLS/ledger/lobby subset if the full suite needs owner rights for fixtures; the choice is recorded in Notes) as `kerp_app`, and asserts `rls_enforcement_problems`, `rls_coverage_problems` and `ledger_guard_problems` report nothing for that role; it is added to `ci-gate` and `scripts/ci_gate.py` `EXPECTED`; no existing job, step, floor or check is removed or weakened (`scripts/tests/test_workflows.py` updated)
- [x] `docs/deploy/first-run.md` documents creating both roles and the setting; the "permission denied" path from the audit is gone
- [x] TD-056 resolved; TD-059 resolved (startup assert by T-0342, grants here)
- [x] Module/README.md and docs updated
- [x] All quality gates green (see CLAUDE.md §Quality gates)

## Notes
- 2026-11-21 (planner): Created from the 2026-11-21 codebase audit; one PR with T-0341..T-0349. The migration is grants-only and additive (no destructive change), but it defines the owner/runtime split for every table, so an ADR (0019) is required rather than just a note. If another PR takes `0019` first, use the next free ADR number.
- 2026-11-21 (planner): Today CI's `kerp_app` owns the tables by design (TD-056); the existing PostgreSQL shards keep that setup, the new job adds the split.
- 2026-11-21 (implementer): Migration `0039_runtime_role_grants.py`: two `DO` blocks over the catalog (works offline too; the role checks run when applied), on objects the migrating role owns in the current schema, extension members excluded. Tables/views get only the `SELECT, INSERT, UPDATE, DELETE` the owner itself holds, `audit_ledger` at most `SELECT, INSERT` (explicit too), `alembic_version` nothing; sequences `USAGE, SELECT`; functions `EXECUTE`; schema `USAGE`; `ALTER DEFAULT PRIVILEGES FOR ROLE <migrator>` for tables, sequences, functions. Setting `KERP_RUNTIME_DB_ROLE` (`Settings.runtime_db_role`, default `kerp_app`, empty = none, validated as a plain role name). Skipped with a `kerp.migrations` log line when empty, missing, or equal to the migrating role (local dev and the `backend-pg` shards migrate as `kerp_app`: granting to oneself is a no-op and the downgrade would revoke the owner's own rights). The downgrade revokes the same set; it leaves the `EXECUTE` that `0025`/`0029` give `kerp_app` themselves.
- 2026-11-21 (implementer): CI job `backend-pg-roles` (single job, same services as `backend-pg`): init script, then `infra/postgres/owner-runtime-split.sql` (`kerp_owner` owns `public`); pre-flight on a copy migrated as `kerp_owner`: `python -m app.core.startup_safety` as `kerp_app` (new pre-flight entry point of the T-0342 checks) and psql asserts (owns 0 objects, no `CREATE`, no ledger `UPDATE`/`DELETE`); then the **full** PostgreSQL suite with the pyproject coverage floor, templates migrated by `kerp_owner` (`KERP_TEST_MIGRATION_URL`, `tests/pg_databases.py:migration_url`). Scope choice: the full suite, because every test on `migrated_database` then exercises the grants (reads, writes, lobby/census functions, ledger appends, jobs, uploads ...); a subset would leave most grant paths unproved. Only for that suite and after the pre-flight, `kerp_app` gets `CREATE` on the test source schema: about 180 tests build scratch tables or migrate an empty database as the runtime role (tenancy contract tests, migration tests); `CREATE` gives no right on `kerp_owner`'s tables. Scratch tables over a migrated schema reference `tenants`, so `tests/tenancy_support.py:seeded_database` creates them as the schema owner there (0039's default privileges grant them to `kerp_app`); unchanged in the other layout. The two ledger tests that assumed `kerp_app` owns `audit_ledger` now act through the actual table owner (`migration_url`), so they hold in both layouts; nothing is skipped or deselected. Added to `ci-gate`, `scripts/ci_gate.py` `EXPECTED` and `backend-publish` needs; no existing job, step, floor or check changed (tests in `scripts/tests/test_ci_gate.py`, `test_workflows.py`).
- 2026-11-21 (implementer): ADR 0019 written (accepted). `docs/deploy/first-run.md` documents both roles, the SQL to create them, the setting and the pre-flight; `docs/WORKFLOW.md`, `backend/README.md` updated. TD-056 and TD-059 resolved.
