## Goal
The two new-record mechanics of issues.md §7. Nothing is converted, re-dated or rewritten; there is no downgrade.

## Acceptance criteria
- [ ] `POST /api/v1/issues/{id}/upgrade` (QA authority; non-terminal punch only, else 409): new NCR from the project's NCR template for the punch's category (or a chosen NCR template of that category), dated now, `raised_by` = caller; answers copied where field keys and types match; photos keep the same attachment ids, `captured_at` and sha256 (test); the punch becomes `upgraded`; `upgraded_from_issue_id` / `successor_issue_id` set
- [ ] An upgrade never widens visibility: the NCR keeps the punch's visibility (internal → internal, client → client) whatever the NCR template's `default_visibility` is; test: internal punch + NCR template with `default_visibility = client` → internal NCR; widening to `client` only through raise-external
- [ ] `POST /api/v1/issues/{id}/raise-external` (QA authority or PER-09; non-terminal `internal` issue of either type): the payload lists the carried items (description, answer keys, photo attachment ids); only those are copied (test); comments, root-cause notes, actions and history are never copied (test); the new NCR is `client`, dated now, raised by the caller; the source becomes `escalated`; `escalated_from_issue_id` is hidden from external callers (test)
- [ ] No downgrade: there is no NCR → punch endpoint; voiding remains the way to correct a mistake
- [ ] Only appends to the ledger: both chains get an entry and the chain verification still passes (test)
- [ ] Upgraded and escalated sources are not open in `open_issues` / `gate_facts`; the successor counts (test)
- [ ] The new NCR's assignee is notified (T-0019)
- [ ] Module `README.md` and docs updated
- [ ] All quality gates green (see CLAUDE.md §Quality gates)
