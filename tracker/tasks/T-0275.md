## Goal
The API side of ADR 0016: a `system_admin` lists and opens every live project of the tenant and gets PER-09-equivalent rights there, but never approval or signing authority.

## Acceptance criteria
- [ ] `ProjectAccess` for a `system_admin` on any live project of the tenant includes `V`, `C`, `E` and `admin` (PER-09 equivalent) without a membership; `A` and `S` come only from the caller's own qualified personas on that project (PER-02, PER-06, PER-07, PER-11 for `A`; PER-15 for `S`); `can_release_hold` is false without such a persona (tests per capability, including an admin with no membership and an admin who also holds PER-06)
- [ ] `GET /api/v1/projects` and `GET /api/v1/me/projects` return every live project of the tenant for a `system_admin`, each with `access: member | system_admin` (the latter where the caller holds no membership); non-admins unchanged (tests)
- [ ] `GET /api/v1/projects/{id}` and project-scoped endpoints answer a non-member `system_admin` as a PER-09 member would (no 404); a soft-deleted project stays 404 on project endpoints (admin surfaces such as the archive are unchanged)
- [ ] SoD: assigning a hold-authority persona (PER-02, PER-06, PER-07, PER-11; individual or team-derived) to a user who holds `system_admin`, and granting `system_admin` to a user who holds such a persona on any live project, return the SoD warning before commit and are audited with `sod_warning: true` (diff §4.1)
- [ ] OpenAPI updated (`access` field); frontend client regenerated in the same PR
- [ ] Module `README.md` and docs updated
- [ ] All quality gates green (see CLAUDE.md §Quality gates)
