# ADR 0011 — Tenants directory table and a `tenant_id` foreign key on every table

- **Status:** accepted (product owner, 2026-11-15, TD-271: split TD-032's FK out of T-0014)
- **Date:** 2026-11-17
- **Affects:** T-0079 (this change), `BaseRecordMixin` (`app/core/db.py`), every table
  (migrations `0026`, `0027`), `app/core/tenancy` (`models.py`, `provision.py`), API start-up
  (`app/main.py`), `migrations/env.py`, T-0023 (first-run provisioning writes through this path)

## Context

Master spec §1.1: "Every relational table must include a mandatory `tenant_id: UUID NOT NULL`
indexed foreign key referencing the `tenants` directory table." Until now `tenant_id` was NOT
NULL and indexed but referenced nothing: no tenants table existed (TD-032). A deployment has
exactly one tenant, hidden from users (diff §4.1, TD-120), named by `KERP_DEFAULT_TENANT_ID`.
Adding a foreign key to every table is a core-table change (CLAUDE.md §6), and every table
added later adds to the cost, so it is done early in phase 0.

## Decision

1. **`tenants` table** (`app/core/tenancy/models.py`, `Tenant`). It follows the record contract
   (`BaseRecordMixin`: UUID `id`, timestamps, soft delete, provenance, `custom_fields`) plus
   `display_name` (≤ 200). The row's own id is its tenant: CHECK `own_tenant`
   (`tenant_id = id`) and CHECK `tenant_level` (`project_id IS NULL`). The directory is under
   the **standard** RLS policies (T-0007), which therefore show and let a session write only
   its own tenant's row; no new policy kind. The display name and id are never shown to users
   (diff §4.1): no endpoint exposes the table.
2. **The FK lives on the mixin.** `BaseRecordMixin.tenant_id` declares
   `ForeignKey("tenants.id")` (name by the naming convention:
   `fk_<table>_tenant_id_tenants`, no `ON DELETE` action: tenants are only soft-deleted). A new
   model gets the FK by using the mixin, and its autogenerated migration contains it.
   `contract_violations` (the metadata contract test) reports a table whose `tenant_id` does
   not reference `tenants.id`, and `tenant_fk_problems(connection)` checks the live schema at
   head (`tests/test_tenants.py`): a table carrying `tenant_id` without the FK, or with one
   not yet validated on PostgreSQL, fails CI. The directory references itself, so the rule
   has no exception.
3. **Migration strategy (additive).**
   - `0026` creates `tenants`, backfills one row (display name `Default tenant`) for every
     `tenant_id` already stored in any table and for `KERP_DEFAULT_TENANT_ID` if set
     (`ON CONFLICT DO NOTHING`), puts the directory under RLS, then adds the FK to every table
     with `NOT VALID` on PostgreSQL: no scan, only a brief `SHARE ROW EXCLUSIVE` lock. The
     backfill read lifts `FORCE ROW LEVEL SECURITY` for the owner inside the transaction and
     restores it before the FKs are added (as `0012`/`0020`/`0025` do), because the migration
     role owns the tables and otherwise would see no rows. Lifting `FORCE` takes an
     `ACCESS EXCLUSIVE` lock on each table until `0026` commits, so `0026` holds it for the
     backfill read of the `tenant_id` values (one indexed column per table, no per-row FK
     check). Accepted: phase 0, one tenant per deployment, no populated production database yet;
     the per-row check itself (`VALIDATE`) runs in `0027` without that lock. The table list is fixed in the
     revision (not reflected), so `--sql` output is identical; on SQLite (the fast test
     backend only) the tables are rebuilt in batch mode, online only.
   - `0027` runs `VALIDATE CONSTRAINT` on every not-yet-valid FK to `tenants`
     (`SHARE UPDATE EXCLUSIVE`: reads and writes continue during the scan).
   - `migrations/env.py` now runs **one transaction per revision**
     (`transaction_per_migration=True`), so `0027`'s scan never runs inside `0026`'s
     transaction and its locks. Large deployments may run `alembic upgrade 0026` and
     `alembic upgrade 0027` as two separate deploy steps (`docs/deploy/tenants.md`).
4. **Provisioning order.** `ensure_tenant(db, tenant_id, display_name)`
   (`app/core/tenancy/provision.py`) is the one runtime path that writes a directory row: a
   tenant-level unit of work bound to that tenant (works under `FORCE ROW LEVEL SECURITY` as the
   runtime role), idempotent (an existing row, even soft-deleted, is left alone). The API start-up
   calls it for `KERP_DEFAULT_TENANT_ID` before serving; `python -m app.core.tenancy.provision`
   does the same from the command line; T-0023's first-run command writes its tenant through
   it. With migrations run first, the deployment tenant's row exists before any tenant-scoped
   insert.
5. **Rollback.** `0027`'s downgrade is a no-op (validation creates no object); `0026`'s
   downgrade drops every `fk_<table>_tenant_id_tenants` and then the table (its policies and
   indexes go with it). No data in other tables is touched. The upgrade/downgrade round trip
   is covered by `tests/test_tenants.py` and `tests/test_migrations.py`.

## Consequences

- An insert whose `tenant_id` names no directory row fails on PostgreSQL with an FK violation
  (SQLite does not enforce FKs; the PostgreSQL CI step does). Test fixtures seed synthetic
  directory rows for every tenant id they use (`tests/db_support.seed_tenants`; the scratch
  metadata has its own `tenants` table, `ScratchTenant`).
- Every new table must use `BaseRecordMixin` (already a rule) and so gets the FK; a hand-written
  migration that forgets it fails `alembic check` and the FK coverage test.
- Inserts pay an FK check on an indexed primary key of a one-row table: negligible.
- The cross-tenant model is unchanged: RLS still keys on `app.current_tenant_id`; cross-tenant
  access stays 404.

## Alternatives considered

- **No FK, documented (TD-032's other option).** Rejected: the spec requires it and the product
  owner chose the FK (TD-271).
- **FK added `VALID` in one step.** Rejected: it scans each table under a lock that blocks
  writes; fine on a fresh database, not on a populated one.
- **A dedicated RLS policy for `tenants` (`id = current tenant`).** Unnecessary: with
  `tenant_id = id` enforced by CHECK, the standard policies give exactly that.
