# Module Specs · Batch 11 (NEW): inspection_requests · forms/item_types/inspections/eligibility/rfi (capability extensions ported from Project-AIP)

> One **new module** (`inspection_requests`) plus **capability extensions** to existing modules, replicating the strongest Project-AIP capabilities (see [`../PROPOSAL-port-from-aip.md`](../PROPOSAL-port-from-aip.md)). Specified in the house format and **built on existing modules — reuse first.** Every table carries `BaseRecordMixin` (entity URI, `tenant_id`, hash, provenance, revision) + an RLS policy; heavy work runs in the ARQ worker (ADR-001), never in the web loop; verification is configuration via `run_checks(context, rule_set)`; AI-assisted steps carry `source="ai"` and need human confirmation. Table prefixes are `oe_<module>_*`. Grounded on the in-scope module set in [`../MODULE-SPECS.md`](../MODULE-SPECS.md).

**Reuse ethos:** `inspection_requests` *orchestrates* `inspections`/`qms`/`construction_control` (hold gates), `contacts`, `documents`+`closeout`/`workpacks` (the PDF + MDR), `reporting` (render), `notifications`, `signing` (notice co-sign), `portal` (client responses), `variations`/`changeorders` + `schedule`/`progress` (delay feed), `field_diary` (offline ledger) and `audit` — it introduces no second source of truth. The `forms`/`item_types` extensions **merge two designers into one engine**; the `inspections` extension adds record integrity; `eligibility` is a thin service over existing registers.

---

## 1 · `inspection_requests` — Request for Inspection (scheduling, notices, witness/no-show/delay capture)

Replaces the antiquated "email a PDF RFI" step with a seamless in-system request that **still ends in a PDF record for the MDR**, and turns every non-witnessed/no-show event into an attributable, change-notice-ready **delay record** — so "the client held progress up, not us" falls straight out of the data.

- **Identity:** core · prefix=`/inspection-requests` · **Depends on:** [projects, users, inspections, qms, construction_control, contacts, documents, reporting, notifications, portal, signing, field_diary, validation] · **Dependents:** variations, changeorders, schedule, progress, reporting/dashboards, closeout/workpacks (MDR).
- **Purpose:** raise a Request for Inspection (IR) against an inspection or an ITP hold/witness point, notify the witnessing party, agree a slot, capture the outcome (witnessed / waived / no-show / failed) with a reason, generate the signed PDF notice into the CDE/MDR, and — when a client fails to witness a hold — open an attributable delay that can feed a change notice/EOT and the delay dashboard. Distinct from `rfi` (*Request for Information*); cross-module lists show a disambiguating prefix.
- **Entities:**
  - `oe_inspection_requests_request`(project_id, request_number, inspection_id→inspections nullable, itp_step_ref[`qms_itp_item|cc_hold_gate`]+itp_step_id nullable, rsw_node_id/asset_item_id, discipline_code, required_party_role[`client|third_party|authority|internal`], required_contact_id→contacts nullable, notice_period_hours, waiver_rule[`allowed|not_allowed`], status[`draft|requested|acknowledged|confirmed|rescheduled|witnessed|waived|no_show|failed|cancelled`], raised_by, raised_at, confirmed_slot_id, hold_gate_id→construction_control nullable, blocks_rsw_node_id/blocks_activity_id→schedule nullable, outcome[`witnessed|waived|no_show|failed`] nullable, outcome_at, external_token (portal magic-link), synced_at).
  - `oe_inspection_requests_slot`(request_id, proposed_start, proposed_end, location_note, proposed_by_kind[`staff|client`], proposed_by_ref, status[`proposed|accepted|declined|superseded`], responded_by_ref, responded_at).
  - `oe_inspection_requests_attendee`(request_id, slot_id, party_role[`inspector|client_witness|third_party|authority`], user_id/contact_id, response[`pending|accepted|declined|tentative`], responded_at, reminded_at, attended bool).
  - `oe_inspection_requests_event`(request_id, event_type[`raised|notice_sent|acknowledged|slot_proposed|slot_responded|confirmed|reminder_sent|rescheduled|attended|no_show|waived|declined|cancelled|witnessed|failed|delay_opened|notice_generated`], actor_kind[`staff|client|third_party|system`], actor_user_id/actor_contact_id, reason_code→`_reason_code`, reason_note, occurred_at, **prev_hash**, **content_hash**) — **append-only; `REVOKE UPDATE/DELETE`** — the what/why/who ledger.
  - `oe_inspection_requests_reason_code`(code, label, category[`access|client_attendance|third_party|weather|permit|documentation|our_readiness|instrument|force_majeure`], cause_party_default[`client|third_party|authority|contractor|force_majeure`], is_builtin) — configuration.
  - `oe_inspection_requests_notice`(request_id, kind[`request|confirmation|outcome`], document_id→documents, signing_session_id→signing nullable, generated_at, generated_by) — the rendered PDF record(s).
  - `oe_inspection_requests_delay`(request_id, cause_party[`client|third_party|authority|contractor|force_majeure`], reason_code→`_reason_code`, delay_hours numeric, started_at, ended_at nullable, blocks_rsw_node_id/blocks_activity_id→schedule, evidence_refs jsonb (event ids, notice doc, photos), change_source[`none|change_notice|eot_candidate`], change_ref_kind[`variation|change_order`] nullable, change_ref_id nullable, status[`open|mitigated|closed`]).
- **Endpoints:**
  - Raise/register: `POST /inspection-requests` (optionally `from_itp_step`); `GET /inspection-requests?status=&party=&rsw=&overdue=`; `GET /inspection-requests/{id}`.
  - Slots: `POST /inspection-requests/{id}/slots`; `POST /inspection-requests/slots/{id}/respond`; `POST /inspection-requests/{id}/confirm`.
  - Lifecycle: `POST /inspection-requests/{id}/acknowledge` · `/reschedule` · `/remind` · `/record-outcome` (`witnessed|waived|no_show|failed` + reason_code) · `/cancel`.
  - Notice/PDF: `POST /inspection-requests/{id}/notice` (kind `request|confirmation|outcome` → `reporting` renders → `documents` files → auto-routed into the closeout/`workpacks` MDR via the `documents` VFS resolver); `GET /inspection-requests/{id}/notice/{document_id}`.
  - Delay: `POST /inspection-requests/{id}/delay` (auto-suggested on `no_show`/`declined` that blocks a hold); `POST /inspection-requests/delays/{id}/raise-change` (→ `variations`/`changeorders` with the evidence pack); `GET /inspection-requests/delays?cause_party=&from=&to=` (attribution query).
  - Portal (reuse): `GET /portal/inspection-requests`; `POST /portal/inspection-requests/{id}/respond` (client accepts/declines a slot via magic-link token).
- **Key logic / state:** `draft → requested → acknowledged → confirmed → [witnessed | waived | no_show | failed]`, with `rescheduled` looping back to `requested` and `cancelled` from any pre-outcome state. **Notice period:** `notice_met = confirmed_slot.start − now ≥ notice_period_hours`; if `waiver_rule=allowed` and the client does not attend after valid notice, the outcome may be `waived` and the work proceeds (entitlement preserved). **Witnessed** *enables* the linked hold gate but does **not** release it — release stays with `construction_control`/`qms`. **Every** transition writes an append-only hash-chained `_event` (prev_hash → content_hash) with actor + reason. A `no_show`/`declined` that blocks a hold **auto-opens a `_delay`** with `cause_party` from the reason code, linked to the blocked RSW/activity. Reason codes are data. Offline raise/respond/outcome flow through the `field_diary` idempotent sync ledger (`client_op_id`). An optional `erp_chat` tool can draft a notice or summarise a delay timeline (`source="ai"`, human-confirmed). Money is never computed here; a raised change references the external commercial mirror.
- **Verification (`run_checks`):** `inspection_request.raise` (references a live inspection/ITP step and a real witnessing party; notice period set) · `inspection_request.confirm` (a slot accepted; required attendees invited; notice period satisfiable) · `inspection_request.outcome` (outcome ∈ enum; `waived` requires `waiver_rule=allowed` ∧ `notice_met`; a `no_show`/`failed` blocking a hold opens a `_delay`) · `inspection_request.notice` (outcome notices require a recorded outcome; document rendered + filed) · `delay.raise_change` (delay has `cause_party` + evidence; change/EOT ref recorded).
- **Features:** [F1] raise IR from an ITP hold/witness point or ad-hoc · [F2] multi-slot proposal + client response via portal magic-link · [F3] notice-period + waiver rule · [F4] attendee invites/reminders/responses · [F5] **append-only hash-chained what/why/who event ledger** · [F6] configurable reason codes with cause-party attribution · [F7] outcome capture (witnessed/waived/no-show/failed) · [F8] **PDF Request/Confirmation/Outcome notice via `reporting` → `documents`, auto-filed to the MDR** · [F9] hold-gate enablement on witnessed (release stays with `construction_control`/`qms`) · [F10] **auto delay-event on client no-show/decline blocking a hold** · [F11] one-click raise change notice / EOT candidate from a delay · [F12] **client-vs-contractor delay-attribution dashboard** (delay-hours by cause party; planned-vs-actual on the blocked RSW) · [F13] offline raise/respond/outcome via the sync ledger · [F14] register with filters + ageing/overdue.
- **Removal impact:** no structured Request for Inspection — witness scheduling falls back to `portal` visit bookings + hand-made PDFs; the delay-attribution ledger and the change-notice/EOT feed are lost.

## 2 · `forms` (extension) — unify to one no-code engine

Replaces the thin `forms` with Project-AIP's designer; shares **one field-type registry** and **one sandboxed evaluator** with `item_types` (§3). *(Supersedes the standalone `oe_asset_layout` "Form/Inspection-Designer" note in `asset_management`.)*

- **Identity:** business · prefix=`/forms` · **Depends on:** [projects, item_types (field registry), documents, reporting, validation] · **Dependents:** inspections, qms, construction_control, workpacks, inspection_requests, item_types.
- **Entities:** `oe_forms_template`(code unique-per-tenant, name, kind[`inspection|itp|rfi|permit|test_report`], discipline_code, entity_type_id→item_types (applicable asset type), default_frequency jsonb, required_competency jsonb (certificate-type refs), status[`draft|approved|retired`], current_revision_id, archived_at) · `oe_forms_revision`(template_id, revision_no, status[`draft|approved|retired`], **schema jsonb** (sections, fields, layout, `visible_if`/`required_if`, formulas, validations), **schema_hash sha256 set at publish**, evaluator_version, change_note, published_at/by — *a trigger blocks UPDATE of `schema` once status≠`draft`*) · `oe_forms_option_set`(code, kind[`options|units`], items jsonb `[{value,label_key}]`) · `oe_forms_section_library`(code, version, schema jsonb) — reusable sections/questions · `oe_forms_template_seed`(pack_code, code, schema jsonb) — starter templates (vehicle pre-start, Take 5, SWMS, coating/blasting ITR, UTT survey, CUI…), unified with `item_types` starter packs.
- **Endpoints:** templates CRUD + `/clone` `/archive` `/export` `/import`; revisions `POST /forms/templates/{id}/revisions`, `POST …/{rev}/publish`, `GET …/compare`; `POST /forms/revisions/{rev}/test-fill` (run formulas/rules on sample answers); `POST /forms/import-assist` (spreadsheet/PDF → field detection, human review); option sets + section library CRUD.
- **Key logic / state:** `draft → approved → retired`; publishing **freezes** the revision as JSONB and sets `schema_hash`; inspections pin `template_revision_id`, so an in-flight record never shifts. **Field types** (shared registry): text, long text, number, decimal, date, datetime, boolean, dropdown, multiselect, radio, **measurement (value+unit)**, asset/user/document reference, photo, video, audio, **signature**, GPS, QR/barcode, repeating table, **calculated**, **instrument/calibration reference**. **Expressions** are declarative (CEL **or** JSONLogic — pick one in the rebuild) stored in the schema JSON, **never user scripts**, evaluated server-side by the **shared TS package / Python port tested on the same fixtures**. An instrument-reference field **blocks a reading on an out-of-calibration gauge** (via `eligibility`, §5) and the gauge enters the traceability chain. Report-slot mapping binds fields to designed PDF slots for `reporting`.
- **Verification (`run_checks`):** `forms.publish` (definition lint — field refs resolve, no calculation cycles, expressions parse; test-fill passes; broken refs block publish).
- **Features:** [F1] sections + grid/tabular custom layout · [F2] full field-type registry (incl. measurement, signature, instrument-ref, calculated) · [F3] conditional visibility/required · [F4] calculated fields (restricted formula + function allow-list) · [F5] per-field/per-row validation (sandboxed CEL/JSONLogic, server-side) · [F6] revision immutability (`schema_hash` + trigger; in-flight pins revision) · [F7] template kinds (inspection/itp/rfi/permit/test_report) · [F8] shared TS/Python evaluator parity · [F9] reusable section/question library (versioned) · [F10] instrument-reference + live calibration gate · [F11] context auto-fill (asset tag, RSW, location, procedure) · [F12] test-fill + publish checks + lint · [F13] print-accurate report-slot mapping · [F14] spreadsheet/PDF import assistant (AI-assisted, human-reviewed) · [F15] starter-pack seed library.
- **Removal impact:** falls back to flat, non-versioned checklists with no logic, no tamper-proof revisions and no shared evaluator.

## 3 · `item_types` / `asset_management` (extension) — the asset-schema half of the one engine

- **Identity:** core · prefix=`/item-types` (schema on `asset_management`) · **Depends on:** [asset_management, forms (shared field registry), validation].
- **Entities (added/extended):** extend `oe_asset_type` with `parent_type_id` (inheritance), `schema_version`, `status_set_id`, `auto_create_itp` bool + `default_itp_template_id→forms`, `auto_create_inspection` bool + `default_inspection_template_id→forms` · `oe_item_types_type_version`(type_id, version_no, schema jsonb, **immutable once published**, published_at/by) · `oe_item_types_attr_registry`(label, field_type, unit, tolerance, reference_scope — shared attributes auto-merged on same label+type) · `oe_item_types_status_set`(code, statuses jsonb mapping custom → neutral enum[`draft|scoped|planned|in_progress|on_hold|completed|cancelled|decommissioned`]) · `oe_item_types_starter_pack`(pack_code, schema jsonb) — unified with `oe_forms_template_seed`.
- **Endpoints:** content/item types CRUD; `POST /item-types/{id}/versions`, `POST …/{v}/publish` (with **migration preview** — impact counts on existing assets + completed inspections), `POST …/{v}/migrate`; attributes registry; status sets; starter-pack import.
- **Key logic / state:** attributes draw from the **same field registry as `forms`**. **Schema versioning**: versions are immutable; publishing shows a migration preview with impact counts; assets pin `item_type_version` and move only through a preview. **Inheritance** is add-and-tighten only (no removing/loosening inherited attributes); effective schema = parent + child. **Template field → asset attribute write-back** when an inspection is approved (e.g. measured wall thickness updates the asset). **Units/tolerances** on measurements raise out-of-range flags into the rules engine. Custom statuses map to the neutral enum so gates/reporting use stable codes.
- **Verification (`run_checks`):** `item_type.publish_version` (migration preview acknowledged; no orphaned refs) · `asset.attribute_validate` (values conform to the effective schema incl. units/tolerances).
- **Features:** [F1] content types with generated register pages · [F2] item types with shared-registry attribute schema · [F3] `is_component`/`allows_components` · [F4] **auto-create ITP/inspection from default templates** · [F5] **schema versioning + migration preview (impact counts)** · [F6] **type inheritance** · [F7] shared attributes registry (auto-merge) · [F8] **template-field write-back to asset attribute on approval** · [F9] units/tolerances → rules · [F10] custom status sets → neutral lifecycle enum · [F11] starter packs (versioned JSON, unified with form seeds).
- **Removal impact:** asset schemas revert to a separate, unversioned designer with no inheritance, migration safety or inspection write-back.

## 4 · `inspections` (extension) — record integrity

- **Identity:** core · prefix=`/inspections` · **Depends on:** [asset_management, forms, eligibility, signing, field_diary, validation].
- **Entities (added):** `oe_inspections_response`(inspection_id, field_key, value jsonb, **client_id** (idempotent push), **sync_version**, recorded_by, recorded_at — **append-only; current value = latest row per (inspection_id, field_key) via a view**; corrections are superseding entries) · `oe_inspections_signoff`(inspection_id, itp_step_ref nullable, signatory_role[`inspector|supervisor|client|third_party`], signer_user_id/signer_contact_id, decision[`approve|reject|witnessed|waived`], **auth_strength**[`password|mfa|pin|pades`], **eligibility_result jsonb** (snapshot), **content_hash**, **prev_hash**, comment, signed_at — **append-only; `REVOKE UPDATE/DELETE`**) · `oe_inspections_assignment`(inspection_id, assignee_id, assigned_by, **competency_ok** bool at assignment, created_at — append-only) · `oe_inspections_programme`(template_id→forms, asset_id/entity_type_id, `asset_path_scope` ltree, trigger_type[`calendar|cert_expiry|issue|ad_hoc`], frequency jsonb, last_done_at, **next_due_date** computed, lead_days, active).
- **Key logic / state:** lifecycle is a `forms`-pinned workflow (draft → … → completed with review chain); the **eligibility banner** (§5) runs before each gated step; sign-off builds a **hash chain** over responses+revision; programmes compute `next_due_date` and raise the next inspection on trigger.
- **Verification (`run_checks`):** `inspection.signoff` (signer eligible; verifier ≠ resolver where required; hash chain intact) · `inspection.close` (required photos/measurements present; no open blocking NCR).
- **Features:** [F1] append-only idempotent responses (offline `client_id`/`sync_version`) · [F2] **append-only hash-chained multi-party sign-off** (auth strength + eligibility snapshot) · [F3] inline eligibility banner · [F4] competency-aware assignment · [F5] programmes/recurrence (cert-expiry/issue/calendar triggers).
- **Removal impact:** inspections lose tamper-evidence, clean offline sync, the inline gate and self-driving recurrence.

## 5 · `eligibility` (new service) — one "valid right now?" gate

- **Identity:** core · prefix=`/eligibility` · **Depends on:** [credentials, wps, qms (calibration), compliance_docs] · **Dependents:** inspections, inspection_requests, forms (instrument field), construction_control, workpacks, portal.
- **Purpose:** one service answering *"is this person / instrument / material valid right now for this step?"* over the existing registers — it **holds no register of its own**, it reads them and returns a pass/fail + reasons, and is the substrate for the `run_checks` eligibility rules and the inspection banner.
- **Endpoints:** `GET /eligibility/check?subject_kind=person|instrument|material&subject_id=&context=` → `{eligible, failures[{register, item, reason, expires_at}]}`; `GET /eligibility/expiring?within_days=` (feeds `notifications`).
- **Key logic / state:** person → `credentials` + `wps` welder qualification (range/expiry/continuity); instrument → `qms` calibration (`valid_until`); material → `compliance_docs`/certificate use-by. Pure read + compose; cached per request, never trusted from a token.
- **Verification (`run_checks`):** exposes `eligibility.person`, `eligibility.instrument`, `eligibility.material` predicates reused by other modules' gates.
- **Features:** [F1] unified eligibility check (person/instrument/material) · [F2] expiring-soon query.
- **Removal impact:** each consumer re-implements its own validity check against three registers (today's duplication).

## 6 · `rfi` / `submittals` (extension) — parity with Project-AIP

- **Identity:** core · prefix=`/rfi`, `/submittals` · **Depends on:** [projects, documents, inspections, scope_work, variations].
- **Entities (added):** extend `oe_submittals_submittal` with `submittal_type` incl. inspection-paperwork types (`weld_procedure|nde_procedure|personnel_qual|calibration_record|itp_approval`), tenant-configurable `review_code`, `blocks_target_kind`[`inspection|rsw_task`]+`blocks_target_id` (the gate), and a resubmission chain; `oe_rfi_rfi` gains `converted_variation_id` and an evidence snapshot.
- **Key logic / state:** a required submittal **blocks** its linked inspection/RSW task until it reaches an accepted `review_code` (via `run_checks`). **Convert RFI → variation candidate** copies references/impact/attachments into a `variations` notice, preserving the evidence trail. Response-time is derived per party/discipline/area for analytics. Cross-module lists prefix RFI (*Information*) to disambiguate from an Inspection Request (§1).
- **Verification (`run_checks`):** `submittal.gate` (target blocked until accepted review code) · `rfi.convert` (variation candidate carries the evidence snapshot).
- **Features:** [F1] inspection-paperwork submittal types · [F2] **submittal-as-gate rule** · [F3] tenant-configurable review codes · [F4] resubmission history + comparison · [F5] **convert RFI → variation candidate** · [F6] response-time analytics.
- **Removal impact:** submittals/RFIs stay a plain register with no gating, no inspection-paperwork types and no variation hand-off.
